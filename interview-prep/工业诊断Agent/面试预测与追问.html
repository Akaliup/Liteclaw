00这本册子怎么用

项目一是「让 Agent 在组织里活着」，项目二是「让 Agent 在会死人赔钱的地方说话」。这家公司的面试官一半是行业老炮，他们不关心你懂不懂 LangChain，他们关心你知不知道一台挖机报警之后，钱是从哪里开始烧的。

这本册子的三个判断：
① 业务感 > 技术感。树根是工业互联网公司，面试官大概率是「平台技术负责人 + 服务业务负责人」双面。业务面不过，技术面没机会。所以前 90 分钟先啃业务场景和术语，再啃 Harness。
② 这个项目的技术不难，难在「你凭什么说它对」。工业场景的 Agent 不比数字员工复杂，但它每说错一句都要有人开车去现场。所以评测、证据、审批三条线要讲得比项目一更狠。
③ 你有一次被别人一句话打穿的风险：「你去过工地吗？」——这本册子给你 20 条现场细节和一段诚实答法，就为了这一句。

高危设备原理细节、真实客户名、根云内部接口、模型准确率的绝对承诺、现场经验不主动提；被问到用「边界 + 推理 + 平移」三段式「你懂液压系统吗？」

三条铁律

铁律一：先讲「谁在疼」，再讲「我做了什么」。工业客户不为技术买单，为「少出一次车、少停一天机、少拆错一个件」买单。每讲一个设计，先说它替谁省了什么。

铁律二：永远给「判据」，不给「结论」。这个行业的专业性是靠判据体现的：「油温 30 分钟从 45 升到 92 且负载没变，才叫异常」——这种话说出来，行业面试官立刻知道你不是纯外行。

铁律三：主动承认「我不懂设备原理」。你不懂液压是正常的，装懂才是致命的。正确的姿态是：我不懂设备，我懂怎么把老师傅的判断变成可执行的流程和可验证的证据。这句话本身就是这个岗位的定位。

唯一一次「事故」（必须背熟，它是可信度的压舱石）：

根因不是模型笨，是我的证据链有问题：手册 4.2 节的前提是「油品符合规格」，而这个前提从来没有被验证过。所以我在证据对象里加了 precondition（前提条件）字段，并要求「前提未验证的证据」必须在输出里标黄，不能作为首选结论的依据。

改法：①证据带前提，前提未验证要显式标注；②同一症状给出至少两个不同链路（散热 / 油品 / 负载）的假设，不许只给一个；③把这次 case 固化进 Eval，作为「单证据高置信」的反例。

09技术底座：这套 Harness 的同类开源实现（Craft Agents）

工业客户不会接受「我自己从零写了个 Agent 框架」，也不会相信一个 4 个月的试点能重造轮子。真实答案是：公司有自研的运行层，但机制与成熟的开源 Agent 工作台同构——而这类开源实现是公开的、你能逐行读的。这一节就是把「同构」讲清楚，让你在被追问实现细节时有真东西可讲。

怎么用这一节：面试时不要说「我用了 Craft Agents」——那是另一个产品。正确的说法是：
「我们自研了运行层，但我读过并改过 Craft Agents 这类开源工作台的权限层和会话层，机制是同一套：会话 + 工作区 + 技能 + 数据源 + 三档权限。所以我讲的是机制，不是某一个产品的功能。」

这句话有三个好处：①显得你读过真代码；②不承诺公司代码细节；③把追问引到你熟悉的机制上。

概念映射（左：开源工作台 / 右：我的诊断 Agent）

开源工作台的概念它解决什么在我的项目里对应什么
Session（会话）一次任务一个上下文，消息、工具调用、结果都可回放一次诊断 = 一个 Session；工单号就是会话的业务主键
Workspace（工作区）把技能、数据源、模型连接、权限策略绑在一起一个客户 / 一个机型系列一个工作区，手册版本按工作区隔离
Skill（技能）一段可复用的专业指令，按需挂载，不常驻上下文「五阶段诊断流程」「假报警判定」「多故障排序」各写成一个技能
Source（数据源）MCP 服务、REST API、本地文件统一成「可调用的能力」设备时序（API）、手册（本地文件 + 检索）、工单（MCP 服务）三类源
Permission Mode（权限模式）Explore（只读）/ Ask（逐次确认）/ Auto（自动）三档只读查询走 Explore；复位、改参数、锁机走 Ask，逐次人工确认
permissions.json（规则）用正则白名单放行「只读类」工具，其余拦下把 get_*、query_*、search_* 放行，control_* 一律进审批

Automation（自动化）事件触发自动建会话（标签变化、定时、工具调用）一级报警自动建诊断会话，人不用点
Background Task长任务后台跑、有进度批量诊断（一个车队 200 台设备夜间跑一遍）

为什么这套映射能撑住追问

因为这三件事在任何 Agent 工作台上都必须解决，解法高度收敛：
① 「模型能干什么」——能力必须来自声明式的清单（技能 + 数据源），不能靠提示词许愿；
② 「模型不许干什么」——必须有一层在执行前拦下来的权限门，而不是在提示词里写「请不要」；
③ 「刚才到底发生了什么」——必须有结构化的调用记录，否则没法评测、没法回放、没法追责。

你把这三件事讲透，面试官不会在意你用的是哪个框架。

被追问「为什么用开源 / 为什么不自己写」时的答法

三个原因。一是时间：4 个月的试点，重写运行层没有意义，价值在诊断逻辑和证据链上。二是可读性：这类工作台的权限层、会话层是公开的，出问题能读源码定位，比自己写的黑盒强。三是可替换：我们的工具全部走标准契约（MCP 或 REST），换运行时不用改工具。

但有一条我不让：权限判定必须在我们自己的代码里。开源实现的规则是通用规则，工业场景要加「设备归属」「工单状态」「是否保内」这些业务条件，这些必须写在我们的门里，不能靠配置凑。

04十个业务场景（业务面的弹药库）

业务负责人不会问「你的架构」，他会问「这个情况你们怎么办」。下面十个场景，每个都给出「谁在疼 / 流程 / Agent 能做什么 / 不能做什么」。至少背熟五个，面试时主动抛一个，效果远好于等他问。

场景 1：A 级报警停机 —— 最贵的那条链路

谁在疼机主（停机 = 台班损失）、服务商（响应时效考核）、厂家（投诉）
流程设备报警 → 平台推送到服务工程师 APP → 电话确认 → 远程看数据 → 判断要不要出车 → 派工 → 到场 → 维修 → 关单
Agent 做30 秒内给出「三件事」：是不是真故障、最可能是哪一路、要带什么件/工具；同时列出「现场要测哪两个值」
不能做不直接派工、不直接下发复位指令、不承诺「修好要多久」

场景 2：B/C 级告警 —— 误报的重灾区

B 级（降功率/限速）、C 级（提示/保养）占了报警总量的大头，也是最容易被当成噪音忽略的。这里的价值不是「修」，是「筛」：把 4,000 条里那 70% 的假报警挡掉，工程师才愿意看剩下 30%。

场景 3：假报警 —— 这个项目真正的第一价值

典型成因传感器漂移、冷启动油温、工况误判（怠速被当作业）、阈值设置过紧、CAN 丢帧导致值为 0、GPS 漂移
Agent 做查「同类工况下的历史分布」，判断这次是不是偏离；查「这个传感器近 30 天漂移趋势」；查「同机型同期误报率」
一句话「假报警识别不是靠看报警本身，是靠看报警之外的数据——工况、历史、漂移。」

场景 4：多故障并发 —— 主因与次因

一台设备同时报 7 个码，工程师最想知道的是「先修哪个」。这里的关键判断是因果链：液压油温高 → 油液粘度下降 → 主泵效率下降 → 压力不足 → 报「主泵压力低」。修主泵是白修。
Agent 的答法：给出「根因候选 + 因果假设 + 建议验证顺序」，而不是并列七个问题。

场景 5：备件与派工 —— 判断错一次，多跑一趟

约束备件在省会仓，调件 1–2 天；工程师车上只带常用件
Agent 做输出里带「可能涉及的部件 + 概率 + 是否常备件」，让工程师决定带什么
不能说不能说「更换 XX 件」——那是维修决策，不是诊断结论

场景 6：保内 / 保外 / 三包 —— 影响谁付钱

同一个故障，保内厂家付、保外机主付，所以工程师第一句话常是「这个在保吗」。Agent 不该做判定，但应该把保修状态作为上下文带出来，并在输出里提示「该结论涉及保内判定，需人工确认」。这就是「不做决策但提供决策依据」的典型。

场景 7：客户自己改过 / 副厂件 —— 手册对不上

手册是按原厂配置写的，现场经常是副厂件、改装、加装。所以 Agent 检索手册时必须带机型 + 配置版本，并且当「参数明显不符合该机型正常范围」时，要提示「可能存在非原厂配置」，而不是硬套手册判据。

场景 8：远程锁机 / 参数修改 —— 高风险控制类

为什么敏感锁机涉及租金风控，误锁直接激化矛盾；参数修改可能让设备带病运行
设计所有控制类操作走 PreToolUse 人工审批 + 二次确认 + 回执不明就不许重试，转人工核实

场景 9：现场没网 / 数据延迟 —— 降级

工地信号差，数据回传延迟 5–15 分钟是常态。所以 Agent 必须能回答「我现在拿到的数据是几点几分的」，并且在数据过期时降级成离线排查清单（按症状给步骤），而不是硬给结论。

场景 10：老师傅的经验怎么留下来

这是「经验流失」那条线。做法不是让 Agent 取代老师傅，而是把他们的排障路径变成可回放的 Trace：同一个报警码，老师傅先查什么、什么情况直接换件、什么情况必须拆检——这些进 Eval 集，也进检索库。

07三档自述：90 秒 / 3 分钟 / 8 分钟

90 秒（业务面开场，先讲钱）

我上一段在树根互联做设备报警后的故障诊断 Agent，做了 4 个月试点，覆盖 3 家客户、6 个机型、1.2 万台设备。

这个场景的痛点很具体：设备一天报几千条警，其中七成是假报警或者可以忽略的，但工程师没法判断，只能打电话问、或者直接出车。一次出车三五百块，误派工是服务经理最恨的浪费；更贵的是判断错——带错件、拆错地方，客户停机一天损失一两千。

我做的事是把这个判断过程做成 Agent：查设备实时状态、查报警历史、查手册、查相似工单，然后输出带证据引用的故障假设和排查步骤。注意是假设和步骤，不是结论——结论和动手还是工程师。

试点下来，根因 Top-1 命中 62%、Top-3 81%，误派工率在试点客户降了 18%，MTTR 从 6.5 小时到 4.2 小时。我最想聊的是「怎么保证它不瞎猜」，因为这块踩过坑。

3 分钟（技术面，加结构）

整个东西是一个 Harness 加一套工具，不是一个「会聊天的模型」。

流程是五阶段状态机：状态确认（设备在不在线、什么工况、报警还在不在）→ 异常定位（哪一路、偏离多少、时间窗）→ 假设生成（按故障树和历史工单排序）→ 证据验证（查趋势、查手册判据、查同类 case）→ 结论输出（假设 + 证据 + 排查步骤 + 备件提示）。

模型只负责两件事：当前阶段选哪个工具、证据够不够。阶段切换是 Harness 判的，不是模型自己说「我进入下一阶段」。这么做是为了可归因——出了问题我能定位到「是假设生成错了，还是证据验证不足」。

工具是一套统一契约：设备档案、实时时序、报警历史、SCADA 告警、MES 记录、手册检索、工单检索，全部按「设备号 + 报警码 + 时间窗」对齐，参数和返回结构固定，异常返回固定错误码（超时、无数据、数据过期、无权限），不让模型去猜一段 JSON。

证据是结构化对象：来源类型、来源 ID、版本、时间戳、片段、可靠性，还有前提条件——这个字段是我踩坑之后加的。

安全边界：工具分只读和控制两类，控制类（复位、改参数、锁机）走人工审批，回执不明就暂停转人工，绝不自动重试。

评测：四类场景的数据集、Trace 回放、Contract Test、只读 Reviewer 复核，关键用例进回归门禁。

8 分钟（终面，讲一个判断错误）

（前 3 分钟同上，然后转入这个故事。）

试点第二个月，一台泵车报「液压油温高」。Agent 给了「散热器堵塞」，证据是手册 4.2 节，置信度很高。工程师照着洗了散热器，问题没解决。真实原因是液压油加错型号，粘度不对导致温升。

代价：一次出车、客户停机 5 小时、工程师对 Agent 的信任直接崩了，之后两周调用量腰斩。

我复盘下来，问题不在模型，在我的证据设计：手册 4.2 节的前提是「油品符合规格」，而这个前提从来没有被验证过。我把「一段正确的知识」当成了「一个成立的证据」。

改了三件事：证据对象加 precondition 字段，前提没验证的证据必须标黄，不能当首选结论的依据；同一症状必须给至少两条不同链路的假设（散热 / 油品 / 负载），不许只给一条；这次 case 固化进评测集，作为「单证据高置信」的反例。

这件事让我对工业 Agent 有个基本判断：在互联网，胡说一句的代价是一次刷新；在这里，代价是一次出车和一次停机。所以这类系统的核心不是「答得多好」，是「知道自己什么时候不该下结论」。

L1业务与现场 · Q01–Q14

这一层决定后面还有没有技术面。目标：让业务负责人相信「这个人虽然不懂液压，但他知道我们在为什么付钱」。

Q01先说说这个项目是干什么的，假设我不懂 AI。
设备一报警，服务工程师就得判断三件事：是真故障还是假报警、是哪一路的毛病、要不要出车带什么件。以前这个判断靠老师傅的经验加打电话问。

我做的是一个「副驾」：工程师在手机上点一下，它去查这台设备的实时数据、报警历史、维修手册、还有历史上类似故障是怎么修的，然后给出一页纸——最可能的三个原因、每个原因凭什么这么判断（点开能看数据曲线和手册条款）、现场先测哪两个值。

它不是替人下结论，是让人少打两个电话、少跑一趟空车。
追问：那和「设备自带的故障诊断」有什么区别？

设备自带的是「码 → 一句话提示」，比如「E-0213 液压油温过高」。它不告诉你为什么高、也不告诉你该怎么办。我做的是把「码」变成「一条可验证的推理链」——这台机器的油温在什么工况下、多快升到多少、和同机型比偏了多少、手册里这个码有几种成因、历史上哪种最常见。

可用锚点：三个问题（真/假、哪一路、带什么件）/ 一页纸 / 点开能看证据
Q02为什么做这个？之前的做法有什么问题？
之前的做法三层，一层比一层贵。

第一层是看报警文本：工程师看码，凭经验猜。问题是 1,800 多个码，高频的 120 个之外，剩下的没人记得住。第二层是打电话：打给老师傅或者厂家技术支持，一天几十个电话，老师傅就那么几个。第三层是出车：判断不了就上门，一次三五百，到了发现是假报警或者带错件，白跑。

所以真正的痛点是两个：经验不可复制，和误判的成本太高。前者决定规模上不去，后者决定客户不满意。
追问：那为什么以前不做？现在能做了？

两个条件成熟了：一是数据齐了，这几年设备联网率上来了，有实时数据、有历史工单；二是模型能读长文档了，手册这种又长又碎的文本以前只能靠人翻。缺任何一条，这事都做不成。

可用锚点：1,800 码 / 高频 120 / 一天几十个电话 / 一次出车 300–800
Q03你在这个项目里具体负责什么？
我负责 Agent 这一层，三块：诊断流程的编排（五阶段状态机、什么时候该补查、什么时候该转人工）、工具与证据（设备数据、手册、工单怎么封装成工具，证据怎么带引用和前提）、评测与回归（数据集、Trace 回放、门禁）。

不负责的：平台侧的设备接入和时序存储是根云那边现成的，我只调接口；检索和切分是算法同学做的；产品需求是服务业务出身的产品经理定的；前端我只提需求。
追问：那诊断逻辑（哪个码对应哪些原因）是你写的吗？

不是。那部分来自手册和老师傅，我做的是「让它可被检索、可被引用、可被验证」。比如手册里一个码有 5 种成因，我不判断哪个对，我提供的是「怎么用数据把这 5 个排掉 4 个」的路径。

别说「全栈都是我」；也别说「我只写 Prompt」——后者等于告诉他自己没有工程含量。
Q04你去过工地吗？懂设备吗？
去过三次，但不算多，我先说实话：一次跟着服务车跑了一天，一次在服务站看工程师接单，一次是客户培训现场。

设备原理我不懂，液压系统我讲不了。我懂的是这个判断过程的结构：一个报警码背后有几种成因、每种成因要用哪个数据去证伪、哪些判断必须人到现场才能做。

我们团队里产品是服务业务出身，手册和判据是他帮我把关的；我负责把它变成流程和证据。如果我装作懂液压，你问三个问题我就露馅了，那对我们都没好处。
为什么这样答能过：

工业行业的面试官最怕两种人：一种是纯互联网背景、把工业当 demo 做的；一种是装懂的。你主动划出「我不懂原理，我懂结构」，反而把自己放到了「能被业务用」的位置上——因为业务方也不指望一个做 Agent 的人会修挖机。

如果他继续压：「那你凭什么判断哪个原因更可能？」

凭三样，都不需要我懂原理：手册里的成因清单（这是厂家写的）、历史工单的分布（这是数据）、以及现场可测的量（这是工程师给我的）。我的工作是排优先级和给验证路径，不是凭直觉选一个。

绝对不要说「我在三一待过」「我跟过很多现场」——这种可验证的谎最容易被戳穿（他们圈子很小）。
三次现场：跟车一天 / 服务站接单 / 客户培训
Q05从设备报警到工单关闭，中间到底发生什么？
我按七步说：

① 设备自诊断出码，通过网关回传，平台按等级推送到对应的人（一级直接推给值班工程师）；② 工程师先看报警文本和设备状态，判断要不要打电话；③ 电话确认现象，客户描述往往不专业（「大臂没力」）；④ 远程看数据——这一步很多人跳过，因为要开好几个系统；⑤ 判断出车还是远程指导，出车要定人、定件；⑥ 到场维修，可能推翻前面的判断；⑦ 关单，写故障现象、原因、处置、换件。

我的 Agent 插在 ②到⑤ 之间，主要是把 ④ 这一步自动化，并且把 ③ 的口语描述和 ⑦ 的历史结论连起来。
追问：那第 ④ 步以前为什么没人做？

不是没人做，是太麻烦：要看实时曲线得进一个系统，看历史报警进另一个，翻手册是 PDF，查历史工单又是另一个。一个工程师一天处理十几单，没时间开四个系统。Agent 的价值一半在「判断」，一半在「一次把四个系统查完」。

七步：报警推送 → 看文本 → 电话 → 远程看数 → 定出车与备件 → 到场 → 关单
Q06报警分等级，Agent 对不同的等级做法一样吗？
不一样，三档三套策略。

一级（停机/安全类）：追求「快和全」，30 秒内必须出东西，宁可多给假设也不能漏；同时强制要求「安全提示」打头（比如涉及制动、回转的，先停机再排查）。二级（降功率/限速）：追求「准」，允许跑更多轮、查更多证据，因为它通常不致命但容易误判。三级（提示/保养）：追求「省」，通常是批量处理，只做「是不是假报警 + 该不该安排保养」，不生成完整诊断。

这个分级不是我想的，是跟着服务侧的响应 SLA 走的。
追问：一级报警你 30 秒能出什么？

出不了完整诊断，但能出三件事：这台设备当前最关键的 3 个参数和它们的正常范围、这个码在手册里的成因清单、以及「现场先确认什么」。这三件事就够工程师决定「现在出车还是先打电话」。

Q07误报（假报警）这么多，你们怎么治的？
先说结论：假报警不能靠看报警本身判断，只能靠报警之外的三样东西。

第一是工况：怠速时的低负载、冷启动时的高油压，都是正常的，不看工况就会误判。第二是历史分布：这个码在这台设备上过去 30 天报过几次、每次持续多久、有没有伴随其他码——单次短时报警和持续报警是两回事。第三是传感器自身的漂移：某个值常年偏高 5 度，突然「正常」了，那才是传感器坏了。

所以我的做法是给每条报警算一个「可信度」，而不是直接判真伪：工况是否匹配、是否孤立、是否漂移、同机型同期误报率多少。可信度低的，输出里直接写「疑似假报警，建议先观察 24 小时」。
追问：那 71% 的假报警识别率是怎么测的？

拿 300 条人工标注过「确认是假报警」的样本跑，看 Agent 有没有把它标成「疑似假报警」。注意这是识别率不是准确率——它同时会漏掉一些，也会把真故障误标成假报警，后者的代价更大，所以阈值我设得偏保守。

三样东西：工况 / 历史分布 / 传感器漂移
Q08数据不准、缺失、延迟，怎么办？
我把「数据有问题」拆成四种状态，每种都有明确处置，而不是笼统说「数据质量差」。

没有数据：设备离线或者这个机型没接这个信号 → 直接说「该项无法确认」，并且降级成「按症状给排查清单」。数据过期：回传延迟 5–15 分钟是常态，所以每个数据点都带采集时间，超过阈值就标「数据已过期 X 分钟」，不让它参与强结论。数据可疑：值突然为 0（典型是 CAN 丢帧）、或者长期恒定不变（传感器卡死）→ 标「可疑」，不作为证据。数据矛盾：两个源说的不一样（比如平台显示在线、SCADA 显示停机）→ 显式列出冲突，让工程师判断。

核心原则是：宁可说「不知道」，也不要用坏数据推一个好结论。
追问：那工程师看到一堆「无法确认」不会烦吗？

会，所以我在输出里做了分层：最上面永远是「我现在能确定的三件事」，下面才是「无法确认的项」。全是「无法确认」的时候，说明这台设备的数据链路有问题——这本身就是一个有价值的结论，比瞎猜好。

四态：无数据 / 过期 / 可疑 / 矛盾——这个回答能同时展示工程严谨和现场理解
Q09维修手册是怎么变成 Agent 能用的知识的？
手册最大的问题不是长，是结构不统一：有 PDF、有扫描件、有跨页表格，还有大量图纸。所以不能整本丢进去做向量检索。

我们的切法是按「故障码 → 可能成因 → 检查步骤 → 判据」这个四段结构切，而不是按页切。一段知识的最小单位是「一条成因 + 它的判据」，因为诊断时真正要用的就是判据。

每条切片带三个元数据：适用机型、手册版本、章节号。机型必须带，因为同一个码在挖机和泵车上可能是两回事；版本也必须带，因为手册改版后判据可能变。图纸基本不解析，只在输出里指路「见手册第 X 页图 3」——让工程师自己去看，比让模型瞎描述强。
追问：那表格怎么办？

表格单独处理成「键值对 + 行列标题」，不当正文切。因为诊断里最常用的就是表：参数正常范围表、扭矩表、故障码对照表。把表格切碎了，等于把最有用的一部分丢了。

追问：扫描件呢？

OCR 之后人工抽检 + 补结构，量不大（我们 38 本里只有 6 本是扫描件）。这部分我没让它自动化，因为错一个字可能就导致判据错。

Q10历史工单那么脏（都是口语），怎么用？
工单的价值不在文本漂亮，在它是唯一带「最终结论」的数据——手册告诉你可能是什么，工单告诉你实际是什么。

脏有脏的用法：不追求结构化字段，只抽三样东西——故障现象（客户原话）、处置动作（换了什么、调了什么）、是否解决。这三样能覆盖 80% 的诊断价值，剩下的（工时、费用、责任判定）对诊断没用。

抽取用模型做初抽 + 规则校验（比如「换了XX」必须能匹配到备件主数据里的件号），抽不出来的不硬凑，标记为「未结构化」，只做全文检索的兜底。

还有一个用法比检索更有价值：统计每个报警码的成因分布。比如「E-0213 在我们这 8 万条工单里，62% 是散热问题、23% 是油品、15% 是传感器」——这个先验直接决定假设排序。
追问：工单结论就一定对吗？

不一定，而且这是个大坑。有的工单写「已修复」，其实只是复位消警了；有的写了原因，其实是猜的。所以我在用之前做了一次抽样校验（抽了 200 条打电话回访确认），发现大约 15% 的结论不可信——这批被降权，只作为弱证据，不作为 ground truth。

这句很值钱：工单是唯一带最终结论的数据，但 15% 的结论不可信——既懂价值又懂陷阱
Q11备件和派工怎么联动？Agent 要不要给「换什么件」的建议？
给「可能涉及的部件」，不给「换这个件」。这是刻意的边界。

原因很实际：换件是维修决策，涉及保内保外、库存、成本、责任。Agent 说「换主泵」，工程师照做了没修好，这个责任算谁的？所以我的输出是「三个假设 + 每个假设涉及哪些部件 + 哪些是车上常备件」，让工程师自己决定带什么。

但有个例外很有用：当某个假设对应的部件是「非常备件、调件要 1–2 天」时，输出会显式提示「若确认是这条，需提前调件」。这句话能帮工程师省一天，而且不越界。
追问：那你怎么知道哪些是常备件？

这是业务给的清单，按服务站的库存策略来，不是模型判断的。我只做一件事：把「假设」和「部件」的映射关系建立起来，映射来自手册的成因-部件对应表。

Q12保内保外、三包这些，Agent 要不要管？
不做判定，但要带出来。

因为这是工程师的第一反应——「这个在保吗」，它决定了后面所有动作（谁付钱、要不要走审批、能不能换总成）。所以我在上下文里带三个字段：是否保内、保修到期时间、是否属于三包范围，但输出里明确写「保修状态仅供参考，以服务系统判定为准」。

这条边界很重要：一旦 Agent 说了「这个保内」，工程师据此承诺客户免费，后面判定是保外，就是一次投诉。
追问：那你就不怕它答错吗？

怕，所以这类字段我做成「引用式」而不是「结论式」：不写「保内」，写「服务系统显示该设备保修至 2026-09，请以系统判定为准」。把判定权留给人，把信息送到位。

Q13现场工程师凭什么用你这个东西？他们连 APP 都不爱开。
这个问题我们踩过，说三个真实的发现。

第一，他们不反感 AI，反感「多一个系统」。所以我们没做新 APP，做成了现有工单系统里的一个按钮——点一下，结果直接进工单备注。第二，他们要的不是「答案」，是「能拿去交差的东西」。所以输出是可复制的：一段话 + 两条依据，能直接贴给客户或者主管。第三，第一次用如果不准，就没有第二次。所以我们上线时只开放了高频 120 个码，宁可覆盖窄，也要保证前几次体验是好的。
追问：采纳率多少？

试点期日均 300 次调用，覆盖大约六成的工单。但这个数不能吹——它是「试点客户 + 主动点开」的口径，不是全量推广后的数。真正的采纳率要看「看了之后有没有改变决定」，这个我们只做了小样本访谈（大约 20 个工程师），没有系统埋点。

三条发现：不加系统 / 给可交差的东西 / 窄覆盖保体验
Q14这个项目谁买单？ROI 怎么算？
买单的是服务侧——因为省的是他们的钱。算法我一般这么算，三层：

第一层，少出车。误派工率降 18%，试点客户一个月大约 400 单派工，就是 70 单左右不用跑，按一次 500 算，三万多。第二层，少停机。MTTR 从 6.5 到 4.2 小时，一台设备一天台班损失按 2000 算，省下来的时间折算成客户满意度——这层不好直接算钱，但对续约和口碑有用。第三层，经验复用。老师傅的电话少了，新人上手快，这层最难量化，但是服务总监最在意的一条。

成本这边：单次诊断不到 1 块钱，加平台和人力，试点期整体投入大概是一个人月级别。
追问：那为什么不直接说「一年省几百万」？

因为试点只有 3 家客户、1.2 万台设备，全量推广的系数我没法拍。我给的是「单店可复现的口径」，不是一个漂亮的总额——总额谁都会乘，口径才是可信的部分。

这一层是「你能不能接住根云的数据」。答得好，技术面会觉得你像是内部人；答不好，会暴露你只做过互联网。

Q15「统一设备查询 Tool」具体是怎么设计的？
核心是「一组工具，一套参数约定」，不是一个万能大工具。

七个工具：get_device_profile（机型、配置、保修）、query_telemetry（按指标和时间窗取时序）、get_active_alarms（当前激活的报警）、query_alarm_history（历史报警及持续时长）、query_scada_mes（产线侧记录）、search_manual（按码/机型/症状）、search_cases（相似工单）。

所有工具共用三个维度做定位：设备号 + 报警码 + 时间窗。时间窗是必填的，不允许「取最新」，因为「最新」在不同数据源上不是同一个时刻。

返回结构统一成信封：数据体 + 元信息（采集时间、数据点数量、是否截断、数据质量标记）+ 错误码。这样模型不用为每个工具学一套返回格式。
追问：为什么不做成一个万能工具，让模型自己传 SQL 或 DSL？

两个原因。一是安全：让模型拼查询等于把数据库交给它，租户边界和性能都不可控。二是可评测：七个工具的调用正确率可以分别统计，一个万能工具的失败你分不清是「没查到」还是「查错了」。

追问：那模型不知道某个工具有什么用怎么办？

工具描述里写「什么时候用它」，不写「它是什么」。比如 query_telemetry 的描述是「当需要判断某个参数是否偏离正常范围时使用；已知报警码但不清楚具体参数时，先调 search_manual 拿到判据再调本工具」——把调用顺序的暗示写进描述，比写十行参数说明有用。

Q16三个数据源的时间对不齐，你怎么对齐？
先说结论：不追求「同一时刻」，追求「同一事件窗」。

三套数据的时间基准本来就不一样：设备回传是设备本地时钟（有的还没对时）、SCADA 是产线服务器时间、MES 是业务单据时间。硬对齐到秒是自欺欺人。

我的做法是：以报警触发时刻为锚点，开一个前后各 15 分钟的事件窗；每个数据点在返回时都带自己的采集时间，而不是统一改成窗口时间；如果某个源的时间偏移超过阈值（我们按 2 分钟），标「时间不可信」，只做趋势参考不做因果判断。

输出里我会写「在 14:20–14:35 这个窗口内」，而不是「14:27 时油温 92 度」——因为后者的精度是假的。
追问：那因果判断怎么办？时间都不准，怎么说是 A 导致 B？

只做「顺序 + 持续性」的弱因果，不做强因果。比如「油温先升高并持续 12 分钟，之后才出现压力报警」——这是可观测的顺序；我不会说「因为油温高所以压力低」，那是机理，得让手册和工程师说。

这句话很专业：不追求同一时刻，追求同一事件窗；精度是假的，顺序是真的
Q17根云、SCADA、MES 三个数据有什么区别？为什么要都接？
三个视角，回答三个不同的问题。

根云（设备侧）：设备自己回传的，回答「这台机器现在什么状态」——转速、油温、油压、故障码、位置、工时。这是主数据。SCADA（产线侧）：工厂里的采集监控，回答「这条产线上发生了什么」——启停、联锁、工艺参数。设备在产线上，产线的异常会影响设备读数。MES（业务侧）：回答「这台设备当时在不在生产」——工单、产量、停机记录。

为什么要都接：因为很多「故障」其实是生产安排导致的。设备连续 12 小时没动，油温低、压力低，一堆报警——MES 一看，那天没排产。只看设备数据，你会把它当成故障。
追问：那这三个源冲突了听谁的？

不投票，显式列冲突。设备说在线、SCADA 说停机，很可能是设备心跳还在但产线停了。这种情况的正确输出是「数据源不一致，建议现场确认」，而不是选一个信。

Q18工具的参数和异常返回怎么定？
参数三条原则：必填项少、枚举代替自由文本、时间窗必填。比如查时序只要四个参数：设备号、指标名（枚举，不许模型自己编）、起止时间、聚合粒度。指标名用枚举是关键——模型很爱编「液压油温度」这种不存在的字段名。

异常返回我定了六个码，覆盖绝大多数情况：TIMEOUT（超时）、NO_DATA（该时段无数据）、STALE（数据过期）、SUSPECT（数据可疑，比如恒值/突变 0）、NOT_FOUND（设备/码不存在）、FORBIDDEN（越权）。

每个错误都带一句「建议下一步」，比如 STALE 建议「缩短时间窗或改为查历史报警」。这样模型不需要自己推理怎么补救，也不会无限重试同一件事。
追问：为什么不直接把异常抛成自然语言让模型自己理解？

因为模型会把「超时」理解成「没有异常」，这是最危险的一种误读。结构化错误码 + 固定建议，能让「失败」变成流程里的一个明确分支，而不是一段可被自由解释的文字。

六个错误码：TIMEOUT / NO_DATA / STALE / SUSPECT / NOT_FOUND / FORBIDDEN
Q19数据回传延迟 5–15 分钟，你怎么保证诊断不误判？
三条。

第一，所有时效性判断都基于「数据时刻」而不是「当前时刻」。输出里写的是「截至 14:32 的数据显示」，而不是「现在油温 92 度」。这一句话能避免 90% 的误判争议。第二，延迟超过阈值就切换诊断模式。低于 5 分钟按「在线诊断」做，5–15 分钟按「近实时诊断」做（只做趋势和假设，不做「当前是否仍异常」的判断），超过 15 分钟直接降级成「离线排查清单」。第三，把延迟本身当成一个信号。某台设备平时 3 分钟回传，突然 20 分钟没数据，这本身就是异常——可能断电、可能信号、也可能是设备已经停了。
追问：那工程师要「现在怎么样」，你怎么办？

我会明确告诉他我做不到，然后给他两个替代：一是最近的确定数据（带时刻），二是「建议现场确认的两个值」。这个行业里，诚实说「我只有 15 分钟前的数据」比假装实时更被接受。

Q20同一个报警码在不同机型上含义不同，你怎么处理？
这是这个项目最容易被忽略、也最容易出错的地方。

处理方式是把机型和配置版本做成检索的强制过滤条件，不是「参考信息」。查手册必须带机型 + 配置版本；查历史工单必须同机型（至少同系列）；参数正常范围必须按机型取值。

更进一步，我在输出里会显式写「本结论适用于 SY215C / 配置版本 3」，因为工程师可能同时在看好几台设备，串台是最常见的误用。

如果这个码在该机型的手册里查不到——不猜，直接说「该机型手册无此码，可能是变体配置或新版本」，并建议走技术支持。
追问：配置版本怎么知道？

设备档案里有出厂配置和变更记录。但现实是变更记录不全（现场改装很常见），所以我在输出里加了一句固定提示：「若设备存在非原厂改装，本判据可能不适用」。这句话是给工程师的，不是给模型的。

Q21知识检索为什么不用纯向量？手册检索的难点在哪？
因为工业检索的第一需求是精确命中，不是语义相似。

工程师输入的是「E-0213」「SY215C」「主泵压力」，这些是型号和编码，纯向量检索经常给出「语义相近但机型不对」的结果——那比没检索到更糟，因为模型会拿它当依据。

所以是混合检索：先按元数据硬过滤（机型、码、版本），再做 BM25 + 向量的混合排序，最后 rerank 取 top-k。硬过滤是第一步，不是可选项。

另外手册有个特点：答案往往在表格里。参数范围、扭矩值、码表，这些表格必须单独结构化，不能当正文切。
追问：那「症状描述」检索呢？客户说的是「大臂没力」，手册里没这个词。

这就是向量该发挥作用的地方：症状到成因的映射用语义检索，码和参数用精确检索。所以是两条路，不是一套。我们建了一个症状同义词表（业务给的），把「没力/抬不起/发软」归一到「动臂举升无力」，再走检索。

一句话：编码走精确，症状走语义，先过滤再排序
Q22上下文是怎么分的？预算怎么控？
四层，按变化频率分：

系统层（角色、五阶段流程、输出格式、禁止事项）——整个会话不变；设备层（机型、配置、手册版本、保修状态）——一次诊断内不变；会话层（当前假设列表、已排除的成因、已获取的证据摘要）——每轮变；证据层（本轮检索到的原文片段）——每轮换。

预算控制的顺序是：先裁证据层的重复片段（同一章节多次命中只留一次），再压会话层的旧证据（只留结论不留原文），最后才动设备层，系统层永远不裁——裁系统层等于换了个 Agent。

我们按模型窗口留 20% 给输出和工具结果，剩下的按 3:2:3:2 分给这四层。
追问：为什么系统层永远不裁？

因为它是流程约束。裁掉「必须先确认工况再判断异常」这种约束，模型就会跳步，而跳步在工业场景里等于瞎猜。宁可这一轮拒绝执行，也不能带着残缺的规则跑。

Q23「证据引用」做到什么粒度才算够？
我的标准是：工程师点开之后，能在 10 秒内判断「这条证据支持不支持这个结论」。

所以证据分三类，粒度不同：数据类——给曲线片段，标出时间窗和阈值线，不是给一个数；手册类——给到章节 + 段落，带机型版本，最好能定位到那一页；工单类——给工单号 + 现象 + 处置 + 是否解决，不给全文（全文太长且脏）。

每条证据还带两个字段：可靠性（数据源可信度、工单结论是否被校验过）和前提条件——这个字段是我踩坑后加的，后面会说。
追问：那如果一条结论有三条证据，但其中一条是工单（弱证据），怎么呈现？

分开列，不混在一起算「支持度」。输出里是「强证据：2 条（数据 + 手册）｜弱证据：1 条（相似工单，结论未校验）」。混在一起算分是最容易自欺的做法。

Q24工具怎么分「只读」和「控制」？
按有没有外部可见的副作用分，不按「危险不危险」分。

只读类：查档案、查时序、查报警、查手册、查工单——随便调，失败重试也无所谓。控制类：复位故障码、改参数阈值、远程锁机/解锁、下发升级——这些一旦发出去就改变了设备状态，且可能不可逆。

控制类走三道：PreToolUse 审批（人点确认）、参数二次校验（锁机必须带工单号或授权单号）、回执确认（发出去了要等设备回执，回执不明就停）。

分类写死在工具注册表里，模型不能自己声明「我这个是只读的」——那是把门禁交给被门禁管的人。
追问：复位不是最常用、最无害的吗？也要审批？

恰恰相反，复位是最容易掩盖问题的操作。现场「复位一下试试」很常见，但复位之后报警消失、真因还在，下次可能更严重。所以复位我也要求审批，并且在审批单上写清「复位仅清除报警，不解决根因」。

按副作用分，不按危险分——这句话能体现你想的是系统而不是功能
Q25控制指令发出去了，但没收到回执，怎么办？
停下来，转人工，绝不自动重试。

因为「没收到回执」有两种可能：指令没到，或者到了但设备已经执行了、回执丢了。重试的后果是重复执行——复位两次没事，锁机两次、参数改两次就可能出问题。

具体做法：指令带幂等键（工单号 + 设备号 + 动作 + 时间片），超时后状态置为「不确定」，不是失败；同时查设备当前状态（下一轮遥测）来反推是否生效；反推不出来就挂一条待人工核实的记录，并且在 UI 上显式告诉工程师「这条指令状态未知，请确认后再操作」。
追问：那工程师着急，非要你重发呢？

那就让他手动重发，并且记录是人工触发的。系统不能替他承担这个判断——这是责任边界，不是技术问题。

不确定态 > 失败态：这是工业系统的通用原则，和项目一的投递状态机是同一个思路
Q26工具超时和重试策略怎么定？
分工具定，因为它们的耗时差异很大。

查档案、查手册：3 秒超时，最多重试 1 次——这类是内存/索引查询，慢了就是真有问题。查时序：8 秒超时，不自动重试——因为时序查询慢通常意味着时间窗太大或数据量大，重试只会更慢，正确做法是让模型缩小窗口。控制类：超时不重试，进不确定态。

重试还有一个前提：只对幂等的只读调用重试。这条规则写在工具注册表里，不靠模型自觉。
追问：模型一直重试同一个查询怎么办？

Harness 层有重复调用检测：工具名 + 归一化参数的哈希，同一哈希出现 3 次就强制打断，并把「该查询反复失败」写进结论——这本身是个有价值的信号，说明数据链路有问题。

Q27设备离线了，Agent 还能干什么？
降级成「离线排查清单」，但仍然有用。

离线时拿不到实时数据，但还有三样东西能用：历史数据（离线前最后一段）、报警历史（这个码以前报过没有）、手册与工单。所以输出从「诊断结论」变成「排查路径」：按手册的判据顺序，列出「到现场先测什么、什么结果对应哪种成因」。

而且离线本身是个线索：设备突然离线，可能是断电、可能是通信模块、也可能是被人为关机（欠款锁机之后）。这个判断要交给工程师，但我要把它提示出来。
追问：那怎么区分「设备停了」和「通信断了」？

看两个信号：心跳有没有、最后一条数据是不是「正常关机」的收尾。这两个我区分不了的情况很多，所以输出里写「离线原因不明」，让现场确认。不猜。

Q28谁能发起控制类操作？权限怎么划？
三层：谁能发起、谁能审批、什么条件下允许。

发起：只有绑定该设备的服务工程师和值班主管，Agent 自己不能发起，只能「建议」并生成一个待审批项。审批：复位和改参数由主管批，锁机/解锁要走风控或商务授权（带授权单号）。条件：必须有未关闭的工单、设备在线、且不在保修争议状态。

所有控制类操作留全链路审计：谁发起、谁批的、什么参数、什么时候、回执是什么。这份审计比功能本身重要——出事的时候它是唯一能说清责任的东西。
追问：Agent 能不能自己决定「建议复位」？

能建议，但建议里必须写清「复位会清除报警、不解决根因」，并且不能把它放在第一位——除非证据显示这是瞬时干扰。这个区分很细，但它决定了工程师会不会盲从。

L3Harness 机制 · Q29–Q44

这一层是技术面的主战场。每道题都要能落到「状态、判据、字段、失败分支」四样里至少两样。答不出来的，去读 Craft Agents 的权限与会话实现，同构的。

Q29五阶段流程，是硬编码的，还是模型自己决定走到哪一步？
阶段是硬编码的状态机，阶段内的动作交给模型。

具体说：状态机只有五个节点和固定的迁移条件；模型在节点内部做两件事——选哪个工具、判断证据够不够。它不能自己说「我进入结论阶段」，那是 Harness 根据判据判的。

为什么这么切：如果让模型自由规划，出问题你只能看一整条 trace，没法归因。现在可以按阶段聚合指标——是「状态确认」环节漏了工况，还是「证据验证」环节只查了一个源。这个归因能力，是我后来能把命中率从 40 多提到 62 的直接原因。
追问：那阶段迁移的判据长什么样？

每条迁移都是「条件组合」，不是单个阈值。比如从「异常定位」到「假设生成」，要求三件事同时成立：已确认工况（不是未知）、已确认报警是否仍激活、至少拿到一个偏离基线的参数。少一条就留在原地继续查，超过轮次就转人工。

一句话：阶段是状态机，阶段内是模型；迁移靠判据，不靠模型自觉
Q30Harness 具体长什么样？每一轮它给模型什么、拿回什么？
一个 DiagnosisState 对象贯穿全程，每轮把它渲染成上下文，跑一轮模型，再把结果写回去。

状态里五个字段组：设备（型号、配置、工况、在线状态）、报警（码、等级、首次/最近触发、持续时长）、证据（Evidence[]，每条带来源、时间、片段、可靠性、前提）、假设（Hypothesis[]，带先验分、支持证据、反证、验证动作）、进度（当前阶段、已用轮次、已排除项）。

每轮给模型的是「状态的自然语言摘要 + 本阶段可用的工具清单 + 输出格式要求」；拿回来的是「工具调用」或「结构化结论」。拿回来的东西必须能写进状态，写不进去的（比如模型自由发挥的一段分析）直接丢弃——这是保证可回放的关键。
追问：为什么不直接把历史消息全给模型？

因为历史里 80% 是工具返回的原始数据，全给会挤爆上下文，而且模型会去读不该读的细节。状态摘要是「已经消化过的事实」，比原始消息更适合做决策依据。原始数据留在 trace 里，需要时才回查。

Q31最大轮次怎么定？重复调用怎么检测？
轮次按阶段分配，不是全局一个数。状态确认 2 轮、异常定位 3 轮、假设生成 2 轮、证据验证 4 轮、结论 1 轮，总上限 12。一级报警压缩到 6 轮以内，因为要快。

重复检测用「工具名 + 归一化参数」的哈希：参数里的时间窗先归一化（比如都对齐到分钟），避免「查了 14:20–14:35 又查 14:21–14:36」被当成两次不同调用。同一哈希出现 3 次判定为原地打转，强制跳到「证据不足」分支。

还有一层是无进展检测：连续两轮状态里没有新增证据、也没有排除任何假设，就判定没进展——这个比重复调用更早发现问题。
追问：为什么是 12 轮？

两个约束夹出来的：下界是「最复杂的多故障 case 跑完五个阶段大概要 9–10 轮」，上界是「12 轮以上的时延就超过 30 秒了，工程师已经在打电话了」。所以 12 是个工程折中，不是理论值。

Q32「证据不足自动补查」——你怎么判断不足？
不是让模型说「我觉得不够」，是三条可计算的判据：

① 假设没有差异化证据——两个假设的支持证据是同一批数据，说明这条证据区分不了它们，必须补查；② 关键前提未验证——证据带 precondition 字段，前提没验证就标黄，标黄的证据不能作为首选结论的唯一支撑；③ 证据源单一——只有数据没有手册、或只有手册没有数据，都要补另一个源。

满足任意一条就自动补查，补查的方向由「缺哪类证据」决定，不让模型自己想去查什么。
追问：补查几次为止？

最多两轮补查，第三轮还不足就转人工并说明「缺什么证据」。无限补查是最常见的坑——它不会让结论变好，只会让时延和成本失控。

三条判据：无差异化 / 前提未验证 / 源单一
Q33什么叫「无法收敛」？怎么判？
四种情况判为不收敛，全部是显式条件：

① 轮次用尽仍没排除到 2 个以内假设；② 证据互相矛盾且无法用数据判定（比如两个传感器一个说高温一个说正常）；③ 关键前提无法验证（比如油品型号现场没记录）；④ 数据质量太差（四态里「可疑/矛盾」占比过半）。

触发之后不是「给个最可能的」，而是输出一份转人工单：已经排除了什么、还差什么、建议现场测哪两个值、建议问客户什么。这份单子本身就是交付物——它让工程师到场之前就有方向。
追问：转人工率 22% 会不会太高？

我认为不高，甚至偏低才是危险的。这个行业里，「答错」的代价远大于「说不知道」。22% 里有一半是数据问题（离线、过期、可疑），这类本来就该转；另一半是真难 case，正是最该让人上的。

Q34故障假设是怎么生成的？排序靠什么？
三个来源，合成一个候选池：手册的成因清单（厂家写的，最权威）、历史工单的成因分布（数据，最贴近现场）、故障树的父子关系（FTA 给的因果结构）。

排序不用模型打分，用一个可解释的加权：先验 × 证据强度 × 可验证性。先验来自工单分布（比如这个码 62% 是散热）；证据强度看支持证据的条数和可靠性；可验证性看「这个假设能不能用现有数据证伪」——不能证伪的假设排后面，因为它会浪费轮次。

模型的作用是「把手册里的成因翻译成这个机型、这个工况下的具体表述」，不是「发明成因」。这条边界很硬：假设必须能追溯到手册或工单，凭空生成的直接丢弃。
追问：那新故障（手册里没有的）怎么办？

处理不了，也不该由它处理。手册没有、工单没有的，最多归到「未知成因」并转人工。我不让它「推理出新型故障」——那不是诊断，那是猜。

Q35两条证据互相矛盾，你怎么处理？
三步：先判是不是真矛盾，再判谁更可信，最后显式呈现。

真矛盾很少，多数是「时间不对齐」或「口径不同」造成的假矛盾——比如平台说在线、SCADA 说停机，其实是心跳还在但产线停了。所以第一步先对齐时间窗和定义。

真矛盾了，按可靠性排序：设备原始数据 > 平台聚合数据 > 工单描述 > 客户口述。但排序不等于丢弃，输出里会写「A 源显示 X，B 源显示 Y，两者不一致，建议现场确认」——把矛盾交给能解决它的人（现场），而不是让模型选一个。
追问：那模型会不会被矛盾搞晕，来回改结论？

会，所以状态机里有个规则：同一假设被「支持→推翻→再支持」两次以上，直接冻结该假设并记录「证据不稳定」。这比让它反复横跳好——反复横跳的结论最不可信。

Q36一台设备同时报 7 个码，你怎么排优先级？
不做「七个并行诊断」，做因果链归并。

先把 7 个码按时间排序，看是不是「首发码 + 伴随码」的结构。工业设备上这很常见：油温高 → 粘度下降 → 主泵效率下降 → 压力不足 → 报压力低。修主泵是白修，因为主泵是被拖下水的。

归并规则三条：① 时间上先出现的、且手册里是「上游成因」的，优先；② 有明确因果边的（FTA 里有父子关系）合并成一个根因候选；③ 判不出来的，按「影响安全 > 影响出勤 > 影响效率」排序，并且明确告诉工程师「这是并列假设，建议先测 X 再决定」。

输出不是「7 个问题」，是「1 个主因候选 + 2 个次因 + 1 条验证顺序」。
追问：那如果首发码是个假报警呢？

那整条链都不成立——所以假报警判定必须在归并之前做。顺序是：先逐条判可信度，再归并，再排优先级。顺序错了，会把一串假的伴随码归并成一个像模像样的假结论。

这句能加分：先判真假，再归并因果，最后排优先级——顺序错了会造出「很像真的」的假结论
Q37为什么强制结构化输出？长什么样？
因为输出要被三拨人消费：工程师看、系统存、评测跑。自然语言只满足第一种。

结构大概五块：结论区（1 个主因 + 2 个次因，每个带置信档位而不是百分比）、证据区（每条证据的来源、时间、片段、可靠性、前提）、排查步骤（按顺序、每步带「怎么判、判到 A 说明什么、判到 B 说明什么」）、风险提示（涉及安全/保内/高风险操作的显式提示）、不确定项（哪些没查到、为什么）。

置信度我给「高/中/低」三档，不给 82% 这种数——那个数字是假的精度，而且工程师会当成承诺。
追问：结构化会不会限制模型表达？

会，但这是我要的。工程师不需要一段漂亮的诊断散文，他需要能照着做的步骤。要解释的时候，我允许他在每个字段里写一句人话，但不允许自由格式的大段分析。

Q38手册版本、机型这些，怎么保证不被模型搞混？
三个动作：进上下文、进检索过滤、进输出标注。

进上下文：设备层上下文里固定写「机型 SY215C / 配置版本 3 / 适用手册 v2.4」，一次诊断内不变，且放在系统层之后、证据之前。进检索过滤：查手册必须带机型和版本做硬过滤，不带就不许查。进输出标注：结论区最后一行固定写「本结论适用于 __ 机型 __ 版本手册」。

为什么这么较真：同一个码在不同机型上含义不同，这是工业诊断里最常见的误用。工程师一天看十几台设备，串台是常态，不是意外。
追问：如果手册版本和设备实际不符呢？

会提示。设备档案里有出厂配置和变更记录，如果手册版本晚于设备生产日期，输出会加一句「该机型可能存在配置差异，判据仅供参考」。这句话不解决问题，但它让工程师知道该怀疑什么。

Q39「PreToolUse 审批」具体怎么落地的？
三层，缺一不可。

第一层是模式。会话有三个模式：只读（Explore，只允许查询类工具）、逐次确认（Ask，每个写操作弹审批）、自动（Auto，只给内部批处理用）。诊断默认是「只读 + 控制类强制确认」，也就是模式是只读，但控制类工具单独走确认——这两件事不冲突，因为审批挂在工具上，不挂在模式上。第二层是规则。用正则白名单放行查询类（get_*、query_*、search_*），控制类（control_*）一律不在白名单里，落进审批。规则文件按工作区分，客户 A 的白名单不会跑到客户 B。第三层是业务条件。审批不是「点一下就行」，要校验设备归属、工单状态、是否保内争议、授权单号——这些是通用规则给不了的，必须写在我们自己的门里。
追问：审批卡住（人不在）怎么办？

超时 10 分钟按拒绝处理，落一条 pending 记录，会话停在那里但状态可恢复；人回来之后可以继续，不用重跑整轮。审批人不在不是异常，是设计内的状态。

三层：模式（模式管默认）/ 规则（正则白名单）/ 业务条件（自己写）
Q40复位这种「点一下就好」的操作，为什么也要审批？
因为复位的本质是清除证据。

现场「复位一下试试」很常见，复位之后报警消失，看起来好了；但真因还在，而且下次可能更严重——最典型的是过热保护被反复复位，最后烧的是主泵。所以复位不是「无害的小操作」，它是「让系统忘掉刚才发生过什么」。

技术上还有一个理由：复位有副作用、可能不可逆、且影响后续诊断的数据完整性。按「有没有外部可见副作用」这条标准，它就该进审批，跟锁机是一类。
追问：那工程师不嫌烦吗？

嫌，所以审批单上写清楚「复位仅清除报警，不解决根因，且会导致后续 30 分钟数据不可用于诊断」。让他在知道代价的前提下点，而不是拦住他不让点。

Q41Trace 里存什么？怎么回放？
一次诊断一条 Trace，按「轮」组织。每轮存五样：输入的状态摘要哈希、模型输出的原始内容、工具调用（名 + 参数 + 返回摘要 + 耗时 + 错误码）、状态变更（新增/修改了哪些证据和假设）、阶段迁移（从哪到哪、触发判据）。

回放的用法有三个：排查（工程师说「它给错了」，我直接看那轮的工具返回是不是有问题）；评测（同一份 Trace 用新的判据重跑，看结论会不会变）；沉淀（把老师傅认可的 Trace 直接变成 few-shot 样例）。

关键是工具返回要存摘要+指针，不存全量——全量数据太大，而且会随时间失效（时序数据会过期）。
追问：回放能完全复现吗？

不能，模型有随机性。所以回放分两种：确定性回放（固定工具返回，只重跑决策，看判据是否稳定）和统计回放（跑 5 次看分布）。前者用来测判据，后者用来测稳定性。

Q42Contract Test 测什么？
测「工具契约没被改坏」，不测「诊断准不准」。

具体三类：参数契约——必填项、类型、枚举值、边界（时间窗不能超过 7 天）；返回契约——字段是否存在、错误码是否在枚举内、空结果是否走 NO_DATA 而不是空数组；行为契约——超时是否真的在 3 秒触发、越权是否返回 FORBIDDEN 而不是抛异常。

为什么要单独测：诊断准确率掉 5 个点很难定位，但工具契约一改，Agent 会以「看起来正常」的方式崩掉——比如返回从数组变成对象，模型照样能读，但字段全错。这种错最贵，因为它不报错。
追问：用真实数据测还是 mock？

参数和返回结构用 mock（快、稳定、能覆盖边界），行为契约用真实环境（超时、越权必须在真环境测）。混着用会两头不靠。

Q43「只读 Reviewer」是什么？用模型复核模型靠谱吗？
Reviewer 是一个独立会话，只做一件事：检查结论里的每条判断，有没有对应的证据支撑。它不改结论、不打分、不生成新假设——只做「引用核对」，所以叫只读。

用模型复核模型靠不靠谱，取决于你让它复核什么。让它判「这个诊断对不对」不靠谱（它没有现场信息）；让它判「这句话有没有引用、引用的是不是同一台设备同一时间窗」很靠谱，因为这是纯文本比对，不需要领域知识。

所以我把 Reviewer 限定在三个检查项：引用是否存在、引用与结论是否同源同时、结论里有没有出现证据里没有的数字。三项都是可判定的。
追问：那 Reviewer 自己错了呢？

它的错是「误报」——把对的标成没引用。所以它的输出只用来提醒人，不直接改结论，也不进自动门禁。它是质检员，不是法官。

这句很值钱：让模型判「对不对」不靠谱，判「有没有引用」很靠谱——把复核限定在可判定的范围
Q44Regression Gate 的规则怎么定？
三层门禁，按「挂了会不会死人」排：

硬门禁（任一失败即阻断）：安全类用例（涉及制动、回转、高压的必须给安全提示）、越权用例（控制类工具在只读模式下必须被拦）、契约用例（工具返回结构）。软门禁（超过阈值阻断）：根因 Top-3 命中率、证据覆盖率、转人工率。观察项（只记录不阻断）：时延、成本、冗余度。

规则的关键不是阈值，是用例的归属：每个历史 badcase 修完必须变成一条硬门禁用例。这样门禁是会长大的，而且长在真实事故上。
追问：门禁跑一次多久？会不会拖慢发布？

硬门禁 40 条，跑一次 6 分钟左右，挂在提交前；全量 240 条一晚上跑一次。拖慢发布是可接受的成本——比线上误诊便宜太多。

L4评测与回归 · Q45–Q56

工业 Agent 的评测和互联网不一样：你没有无限流量做 A/B，也没有干净的标注。所以面试官真正想听的是「在数据很脏、样本很少的情况下，你怎么知道自己没变差」。

黄区答题模板：①痛点（评测不可信会怎样）→ ②数据集怎么来（来源比例）→ ③指标怎么算（分母是谁）→ ④一次判断失误 → ⑤收口「我负责评测设计和口径，标注是业务同学做的」。
Q45Eval Dataset 是怎么建起来的？
四类场景，240 条，每类 60 条：传感器异常（数据对但读数异常）、机械故障（有明确换件结论）、假报警（人工确认无故障）、多故障并发（一码多因或一机多码）。

来源三条：历史工单抽样 60%（有最终结论的那种）、老师傅口述的场景 25%（他们脑子里那些「一看就知道」的 case）、线上 badcase 回流 15%。

每条用例固定四样：设备档案快照、报警与时间窗、当时可查到的数据（做成回放包）、期望结论（根因 + 必须覆盖的证据类型）。数据做成回放包是关键——不然半年后时序数据过期，用例就废了。
追问：为什么不多建一点？240 条够吗？

不够，但再多的边际收益很低。240 条能稳定区分「明显变差」，区分不了「好 2 个点」。而工业场景里，2 个点的差异根本不影响上线决策——影响决策的是「会不会给出危险建议」。所以我把力气花在硬门禁用例上，而不是堆数量。

Q46Ground truth 从哪来？工单结论就一定对吗？
不一定，这是最大的坑。我抽样 200 条电话回访校验过，大约 15% 的工单结论不可信——有的是「已修复」其实只是复位消警，有的是工程师写的猜测。

所以 ground truth 分三级：A 级（有换件记录 + 客户确认解决）、B 级（有明确处置描述但没回访）、C 级（只有「已修复」三个字）。只有 A 级进硬门禁，B 级进软指标，C 级只做参考。

另外还有一类是老师傅裁决：拿不准的 case，让两个资深工程师独立判，不一致的进仲裁。这批只有 40 条，但质量最高。
追问：那模型和 A 级不一致，就一定模型错吗？

不一定。有几次是工单写错了原因但恰好修好了（换件换对了、归因写错了）。这种我单独标一类「结论对但归因错」，不参与根因命中率计算——不然会把模型冤枉成错的。

Q47Top-1 62%、Top-3 81% 具体怎么算的？
分母是「有 A/B 级 ground truth 的用例」，不是全部 240 条——没有可信答案的 case 不计入，否则指标没有意义。

Top-1：Agent 给出的第一顺位假设，和 ground truth 的根因是同一个（按成因编码比，不按文字比）。Top-3：前三个里任意一个对上。

两个细节：一是「部分对」怎么算——比如 ground truth 是「液压油型号错」，Agent 说「油品问题」，我判为对，因为成因层级一致；这种判定规则必须提前写死，不能事后解释。二是多故障 case 单独统计，不和单故障混在一起，否则会被单故障的好成绩掩盖。
追问：62% 在工业场景够用吗？

作为「副驾」够用，作为「自动诊断」远远不够。这也是我一直强调的定位：它是给工程师的第二个意见，不是替代。真要到自动诊断，Top-1 得到 90% 以上，而且要有兜底——我认为短期内做不到。

Q48「证据覆盖率 94%」怎么评的？
机械可算的：输出里每一条「判断句」，是否挂了至少一条可点开的证据。94% 意味着 6% 的判断句没有引用——那 6% 我抽样看了，主要是「建议现场确认」这类非判断句被误算，真正无引用的结论大概 2%。

但覆盖率只说明「有引用」，不说明「引用对不对」。所以还有一层引用正确率：抽 100 条人工核，看引用内容是否真的支持该结论。这个是 88%——剩下 12% 里，一半是引用了同章节但不同机型，一半是引用了相关但不充分的条款。
追问：为什么不做到 100%？

因为有些判断本来就来自「排除法」——排除了 A、B、C 之后剩下的 D，它没有正面证据。这类我会标「推断，无直接证据」，算在覆盖率的分子里但不假装有引用。硬凑引用比没有引用更危险。

Q49「工具选择质量」怎么评？
三个指标，都能从 Trace 直接算：必要工具覆盖率（这条 case 至少该调的几个工具，调了几个）、无效调用率（返回 NO_DATA 或没改变任何状态的调用占比）、重复调用率（同一哈希出现两次以上）。

必要工具清单是我人工标的（每条用例标 2–4 个必须的工具），标的时候不看模型输出，避免「它调了什么就算什么必要」。

还有一个更有用的指标：关键工具是否在关键阶段被调用。比如「查工况」必须在状态确认阶段调，不能等到结论阶段才想起——这种顺序错误的代价比漏调更大。
Q50多故障并发怎么评？总不能只看 Top-3 吧。
单独一套标准，三个维度：主因是否找对（这是最重要的）、是否错误地把伴随码当独立故障（过度诊断）、排序是否合理（先修哪个）。

过度诊断在工业场景特别贵——你让工程师修三个地方，他可能只修一个就走了，剩下两个下次再报，客户会觉得「你们根本不会修」。所以我在评分里给「过度诊断」很重的惩罚，宁可少说一个，不要多说两个。

这类用例只有 60 条里的一部分（真正多故障的大概 18 条），样本很少，所以我不看小数，只看「有没有出现把伴随码当主因」这种定性错误。
Q51假报警识别 71%，是准确率还是召回率？
准确说是在人工标注的假报警样本上的召回率——300 条确认的假报警，Agent 标出 71%。这个数会让人误以为「很准」，所以我每次都会补一句另一个数：把真故障误判成假报警的比例是 4%。

这两个数的代价完全不对称：漏掉一个假报警，工程师多看一眼；把真故障说成假报警，工程师可能就不出车了——那是停机甚至安全事故。所以阈值我调得偏保守，宁可召回低一点。
追问：那为什么不干脆不判假报警？

因为不判的话，工程师被 4,000 条报警淹没，最后的结果是「全都不看」——那比误判更糟。假报警识别的价值不是省一次出车，是把工程师的注意力抢回来。

两个数一起说：召回 71% + 误判真故障 4%，并说明代价不对称
Q52离线评测挺好，上线就不好用，为什么？
三个典型原因，我都遇到过。

一是分布不一样：评测集是从「有结论的工单」抽的，而线上大量是「没结论」的琐碎报警，模型在后者上表现差很多。二是数据状态不一样：评测用的是回放包（干净、完整），线上是实时数据（缺、慢、脏）。三是人在环里：评测时模型是「一次给完」，线上一来一回，工程师会追问、会否定，多轮之后结论会漂。

所以上线前我加了一轮「影子跑」：拿真实线上请求复制一份给 Agent，不影响工程师，只看它和实际处置的差异。这轮跑了两周，暴露的问题比评测集多得多。
Q53MTTR 从 6.5 小时到 4.2 小时，这个归因可靠吗？
不完全可靠，我会主动说清楚。口径是「试点客户、同机型、报警到关单」，但同期还有两件事在发生：服务侧在推「备件前置」、客户那边进入旺季出车更频繁。

所以我的说法是：「指标变了是事实，归因我只敢给一半」。能相对干净归因的是「误派工率降 18%」——因为这个指标直接由「到场后发现与报警不符」定义，和 Agent 的判断强相关。

面试里我宁愿给一个打折的结论，也不给一个漂亮的假因果。工业客户最恨的就是「你们的数据很好看，但我不信」。
别说「提升了 35% 的效率」这种综合指标——一追问口径就崩，而且工业人一听就知道是包装出来的。
Q54怎么证明它不是「蒙对」的？
四个办法，按说服力排：

① 反事实测试：把关键证据删掉（比如拿掉油温曲线），看结论会不会变。会变，说明它是靠证据推的；不变，说明它在背答案。② 干扰测试：塞一条无关但显眼的假证据（比如一个不相关的报警码），看它会不会被带偏。③ 分布外测试：拿没见过的机型/码跑，看它是老实说「无此码」还是硬套。④ 一致性：同一 case 跑 5 次，结论是否稳定。

这四个里，反事实测试最能说明问题——一个靠证据的系统，删证据就该崩。
追问：那如果删了证据它还答对呢？

那可能是因为这个码的成因太集中（比如 90% 都是同一个原因），它靠先验就蒙对了。这种情况我会在报告里标「该码先验过强，指标虚高」，不拿它当能力证明。

四个测试：反事实 / 干扰 / 分布外 / 一致性
Q55为什么不做微调？买个开源模型微调一下不是更准？
三个理由，第三个是决定性的。

一是数据不够：真正高质量的标注（A 级 ground truth）只有几百条，微调一个工业模型远远不够。二是知识会变：手册改版、新机型上线、报警码增删，微调一次的成本跟不上变化。三是可解释性：这个场景必须能说「我为什么这么判」，微调后的模型给不出证据链，而证据链是这个产品的核心交付物。

所以我们走的是「检索 + 编排 + 证据」这条路，模型只负责「读懂和选择」，不负责「记住」。
追问：那以后数据够了会不会微调？

会，但只会用在「分类/抽取」这类子任务上（比如把工单口语抽成结构化），不会用在整个诊断链上——诊断链的可解释性是产品要求，不是技术偏好。

Q56上线之后怎么让它持续变好？
一个闭环，四个动作，每周跑一次：

收——工程师点了「没用/不对」的 case 自动进待审池；判——人工判是「数据问题、知识问题、还是推理问题」，三类走三条路；修——数据问题修链路，知识问题补手册切片，推理问题改判据或加 few-shot；锁——修完的 case 变成门禁用例，防止回退。

关键是第 判 这一步不能省。绝大多数团队直接跳到「修」，结果把数据问题当模型问题修，越修越糟。
追问：一周能处理多少条？

试点期一周 20–30 条，其中真正需要改代码的大概 3–5 条。剩下的都是知识或数据问题，产品同学就能处理。这个比例很重要——如果每周有 20 条要改代码，说明架构有问题。

L5压力追问与陷阱 · Q57–Q68

这一层考的不是技术，是「你会不会为了圆场而扩大陈述」。工业行业的人见过的 PPT 比你见过的报错多。

Q57说实话，你下过现场吗？你连挖机都没开过吧。
没有长期待过，去过三次：跟服务车跑了一天、在服务站看了一下午接单、还有一次客户培训。

挖机我不会开，液压我讲不了。但我做的不是设备，是判断过程——一个码背后有几种成因、每种成因拿什么数据去证伪、哪些必须人到现场。

我们团队里产品是服务出身，手册和判据他帮我把关；我负责把它变成流程、工具和证据。如果我装作懂设备，你问三个问题我就露馅，那对谁都不好。
如果他继续压：「那你怎么知道工程师真正需要什么？」

靠两件事：一是看他们实际怎么干活（跟车那天我记了他们开几个系统、打几个电话）；二是每周看「点了没用」的反馈。我不敢说懂他们，但我能说清他们哪一步最烦——就是「为了一个报警去开四个系统」。

不要说「我在三一干过」「我跟过很多现场」。这个圈子小，一问就穿，而且穿了之后你说的所有技术细节都会被重新怀疑。
Q584 个月做一个诊断 Agent，还是试点，能做出什么东西？
4 个月做不出「自动诊断」，我做出来的是「副驾 + 一套可验证的评测」——这两件事在 4 个月里是够的，因为工具层是现成的（平台有数据接口），我做的是编排、证据、门禁。

我很清楚它没到哪一步：只覆盖 6 个机型、只开放高频 120 个码、只有 3 家客户、还得靠工程师点一下才跑。这些边界我会主动说，因为一个说自己「已经全量上线」的 4 个月项目，你反而该怀疑。
追问：那这 4 个月的价值到底在哪？

在于证明了「证据链 + 评测」这条路能走通，而且找到了最贵的那类错误（前提未验证的证据）。后面谁接手，不用从零想这件事。试点项目的价值本来就不是规模，是把不确定性打掉。

Q59有代码或者 demo 可以看吗？
公司代码在内网，带不出来，这个我不糊弄你。

我能做两件事：一是白板画一遍完整的诊断链路，从报警进来、到状态机怎么走、到证据怎么挂、到审批怎么拦，可以画到字段；二是讲一个具体的误判，包括当时怎么定位、改了什么规则。这两件事编不出来。

另外我平时读也改过同类开源 Agent 工作台的权限层和会话层，机制是同一套（会话 / 技能 / 数据源 / 三档权限），如果你对某个机制感兴趣，我可以按那份实现讲。
不要现场打开一个 GitHub 仓库说「这是我写的」。除非你能回答里面每一个设计选择，否则这是最快翻车的方式。
Q60为什么只干了 4 个月就走了？
是试点项目的周期到了，不是我跑了。4 个月的目标是「验证这条路能不能走通」，验证完了，接下来是推广和产品化——那需要一个更大的团队和更长的周期，而我当时想继续往「Agent 基建」这个方向走。

另外说句实话：试点期的资源很少（5 个人、3 家客户），能验证的东西有限。我想去一个能把这件事做大的地方。
追问：那你怎么保证下一份不会又几个月就走？

看两件事：这个岗位是在做平台还是在做项目；团队里有没有人比我更懂这一层。第一个决定我有没有事做，第二个决定我能不能长。这两条我现在会先问清楚。

别说「公司不行 / 领导不懂技术 / 太累」——任何对前雇主的负面评价都会被记一笔。
Q61你才一年多经验，工业这边的事你能扛得住吗？
扛不住「设备专家」那部分，这个我认。但工业 Agent 这个岗位要的不是设备专家，是能把专家判断变成流程和证据的人——这部分我做过三遍（数字员工、诊断、CRM）。

而且我有个习惯：做任何东西都先想「怎么验证它对」。工业场景里这个习惯比经验更值钱，因为经验没法复用，判据可以。
追问：那你打算怎么补设备知识？

跟着真实的诊断 case 补，不是啃教材。每修一个 badcase 就是一次设备课——这比看手册快，而且记得住。

Q62说实话，现场工程师根本不用 AI，你这个是不是伪需求？
半真。他们不用「AI」，但他们每天都在打电话问人——这就是需求，只是没人把它叫 AI。

我们踩过的坑恰好证明这点：第一版做了个独立 APP，没人开；改成工单系统里的一个按钮，调用量才起来。不是需求不存在，是入口不对。

而且这类产品的正确指标不是「日活」，是「有没有改变决定」——他看了之后是决定出车还是不出车、带这个件还是那个件。这个我们只做了小样本访谈，没做系统埋点，所以我不敢给你一个漂亮的采纳率。
这句很值钱：不是需求不存在，是入口不对——它同时承认了问题和解法
Q63要是它判断错了，工程师拆错件、客户停机，谁负责？
责任在人，但设计上要让「人犯错之前有机会停一下」。三条：

① 它只给假设和排查步骤，不给「换这个件」的指令——维修决策永远是人做的；② 所有结论都带证据和不确定项，工程师能看见「这条是猜的」；③ 高风险动作（复位、改参数、锁机）走审批，而且审批单上写明后果。

这套设计的本质是：不把责任转移给模型，但把「判断依据」提前给到人。至于万一还是错了——留全链路 trace，能复盘是谁在哪一步做了什么决定。这在工业场景里比「准确率」更重要。
追问：那出了事故，trace 会不会变成追责工具？

会，这是必然的。所以我在设计时就默认「trace 会被拿去看」，这反而让每一步都必须留依据——这对系统本身是好事。

Q64根云平台自己就有故障诊断，你这不是重复造轮子？
不重复，是两层。平台那层是「码 → 知识」：告诉你这个码是什么意思、可能是什么原因，这是规则和知识库。我那层是「码 → 这台设备现在的证据 → 该先查什么」，是针对单台设备、单次报警的推理。

打个比方：平台是维修手册的电子化，我是拿着手册和这台机器的数据帮你做判断的那个人。手册不会看你的油温曲线，也不会知道你昨天刚换过油。
追问：那为什么不直接做进平台里？

最终应该做进去，但试点阶段放在外面更快——不用等平台排期，可以快速改判据和评测。这也是试点项目的常见做法：先证明价值，再谈合并。

Q65为什么不做预测性维护（RUL）？那个更值钱吧。
更值钱，但我们做不了，原因很硬：RUL 需要寿命标注——你得知道每个部件从装上到失效的全周期数据，还得有足够多的失效样本。我们手上只有报警和工单，没有部件级的寿命标签，做出来就是拍脑袋。

而且预测性维护的错误代价更高：说「还能用 200 小时」结果 50 小时就坏了，那是事故；说「马上要坏」结果没事，那是浪费。这类模型的上线门槛比诊断高一个量级。

诊断不一样：它有明确的触发点（报警）、有可验证的结论（修完对不对）、有天然的人在环（工程师）。先做能验证的，再做值钱的，这是我的判断。
这句能直接用：先做能验证的，再做值钱的
Q66它比干了二十年的老师傅强在哪？
不强，差得远。老师傅听声音就知道哪不对，这个我做不到，也不打算做。

它强在三个地方，都是老师傅的短板：一是不忘——1,800 个码、38 本手册，人记不住；二是不累——凌晨三点第一百次报警，它的判断质量和第一次一样；三是可复制——老师傅退休了，他的判断路径还在系统里。

所以定位从来不是替代，是让一个新手工程师在夜里也能有个「像老师傅在旁边」的东西。
Q67期望薪资？
我现在 __，期望 25–28，主要看岗位空间。如果这块能给到架构和落地权限，24 以上我可以定。

（被压时）我理解预算有区间。如果 base 到不了，我想聊两件事：这个岗位半年后能做到什么程度；有没有机会碰评测和基建这一层——这两件对我比多两千块重要。
不要在没 offer 的时候主动降；降一次，后面每次都会降。
Q68你有什么问题问我？
三个：

① 现在服务侧最疼的是哪一块——误派工、备件、还是响应时效？
② 诊断这块现在是平台在做还是业务在做？两边的边界怎么划？
③ 我进来前三个月，你最希望我交付的一个东西是什么？
为什么问这三个：

第一个让他暴露真实痛点（你可以顺势接「这块我做过」）；第二个探组织边界（也暗示你懂「平台 vs 业务」的矛盾）；第三个把面试变成入职规划。

不要问「加不加班」「团队氛围」——留到 HR 面。

L6失败与反思 · Q69–Q74

技巧只有一个：失败要具体到能复述现场，反思要落到规则上。「我以后会更谨慎」是废话，「我加了一个 precondition 字段」是能力。

Q69这个项目里，你最大的一次误判是什么？
一台泵车报液压油温高，Agent 给了「散热器堵塞」，证据是手册 4.2 节，置信度高。工程师洗了散热器，没好。真因是液压油加错型号。

代价：一次出车、客户停机 5 小时、工程师对它的信任崩了，之后两周调用量腰斩。

根因不在模型，在我的证据设计：手册 4.2 节的前提是「油品符合规格」，而这个前提从来没被验证。我把一段正确的知识，当成了一个成立的证据。

改了三件事：证据对象加 precondition，前提未验证必须标黄且不能单独支撑首选结论；同一症状必须给至少两条不同链路的假设（散热/油品/负载）；这次 case 进评测集，作为「单证据高置信」的反例。
追问：这件事之后，工程师还信它吗？

花了一个月才缓过来。具体做法是请那位工程师参与评审——他每指出一个错，我们就改一条规则，并且在输出里标「本条经 XX 工程师复核」。信任不是靠准确率回来的，是靠「他知道你会改」回来的。

Q70有没有一个技术决策，你后来发现错了？
有，我一开始想让模型自由规划诊断路径——觉得 Agent 嘛，就该自己决定查什么。

结果三个问题：时延不可控（有时 5 轮有时 20 轮）、归因不可做（错在哪一步说不清）、回归不可测（每次路径都不一样，没法比）。

后来改成五阶段状态机 + 阶段内自由。改完之后时延方差小了一半，而且能按阶段出指标——「状态确认错」和「证据验证不足」是两种完全不同的病，得分开治。自由度应该给在「怎么查」，不是「查什么阶段」。
Q71和业务方/现场冲突过吗？
冲突过，最典型的一次是「要不要给结论」。业务希望它直接说「换主泵」，因为工程师要的是干脆；我坚持只给假设和步骤。

最后我用一个数字说服了他：试点期有 3 次「Agent 说换件、工程师换了没好」，每次都是二次出车加客户投诉。而「给假设 + 步骤」的情况，工程师自己判断错的只有 1 次。

我的收获是：跟业务争，不要争「谁对」，要争「错了谁承担」。责任一清楚，方案就定了。
Q72有没有做了但最后没用的功能？
有，语音输入。当时想的是工程师在现场手脏、不方便打字，做语音报故障应该很自然。

结果没人用。原因很土：现场噪音大，识别不准；而且他们宁可打三个字「大臂没力」，也不想说一段话再改错别字。

这件事让我明白：现场的效率不是「少动手」，是「少等待」。他们愿意打字，但不愿意等一个转圈。后来我们把力气花在「3 秒出第一屏」上，效果比语音好得多。
Q73给你三个月和两个人，你会做什么？
按这个顺序：

第一个月：不写新功能，先把「看得见」做出来——把诊断链路的 trace 和三个指标（根因命中、证据覆盖、转人工率）接到看板上。不知道现在什么样，后面全是猜。
第二个月：挑一个最高频、最有结论的码族做深（通常是液压温度这一类），把命中率和证据质量做到能拿给客户看。
第三个月：把这套东西抽成可复用的部分——工具契约、证据对象、评测集——让第二个码族能直接接。

我不会一上来做平台，平台是结果不是起点。
Q74这个项目教会你最重要的一件事？
「知识正确」不等于「证据成立」。

手册里写的每一句都是对的，但它有前提。模型很容易把「一条正确的知识」当成「一个成立的证据」，然后给你一个置信度很高、但对这台设备完全不成立的结论。

所以工业 Agent 的核心不是「知道得多」，是知道自己什么时候不该下结论。这条后来一直跟着我：做任何 Agent，我都会问一句——它凭什么这么说，这个「凭什么」经得起现场验证吗。
收尾金句：知识正确 ≠ 证据成立；核心不是知道得多，是知道什么时候不该下结论

10白板题 W1–W5

白板不是画得好看，是边画边说话。每道题的第一句话决定他信不信你真的搭过。

W1 画一次完整诊断

第一句：「我画主干，然后补两个分支——转人工和转降级。」
画：报警 → 建会话（带设备档案）→ 状态确认（在线/工况/报警是否仍激活）→ 异常定位（参数偏离 + 时间窗）→ 假设生成（手册×工单×FTA）→ 证据验证（补查循环）→ 结论（假设 + 证据 + 步骤 + 风险）→ 落地（工单备注 / 转人工单）。
补分支：①证据不足两轮 → 转人工；②数据过期/离线 → 离线清单。
坑：别从「用户提问」开始画——这个场景没有用户提问，触发源是设备报警。

W2 画工具契约与权限门

第一句：「工具按副作用分两类，门在执行前，不在提示词里。」
画：模型 → 工具调用 → 【权限门】→ 只读类直接过 → 控制类走审批（人）→ 执行 → 回执 → 不确定态。
标注：门里三层——模式（只读/确认/自动）、规则（正则白名单）、业务条件（设备归属/工单状态/是否保内）。
坑：别把审批画成「模型自己判断要不要问」。

W3 画证据对象与引用

第一句：「证据不是一段文字，是一个带前提和可靠性的对象。」
画：Evidence{ 来源类型 / 来源 ID / 版本 / 采集时刻 / 片段 / 可靠性 / 前提条件 } → 支撑 → Hypothesis{ 成因 / 先验 / 支持证据 / 反证 / 验证动作 } → 结论。
加一句：「前提未验证的证据要标黄，且不能单独支撑首选结论——这是踩过坑之后加的字段。」
坑：别只画「检索 → 回答」，那说明你没有证据链的概念。

W4 画评测与回归

第一句：「评测要能回答三件事：它准不准、它稳不稳、它会不会做危险的事。」
画：回放包（设备快照 + 报警 + 数据 + 期望结论）→ 三档门禁（硬/软/观察）→ Trace 回放 → badcase 回流 → 回放包更新。
加一句：「硬门禁里最重要的是安全类和越权类，不是准确率。」
坑：别说「我们做了 240 条用例」就完了——数字不配口径等于没做。

W5 画数据流与时间对齐

第一句：「三套数据的时间基准不一样，所以我不追求同一时刻，只追求同一事件窗。」
画：设备（设备时钟）/ SCADA（产线时间）/ MES（单据时间）→ 以报警时刻为锚开 ±15 分钟窗 → 每点带自己的采集时刻 → 偏移超阈值标「时间不可信」。
坑：别画成「统一时间戳对齐到秒」——工业人一眼知道那是假的。
