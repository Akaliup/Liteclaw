# 导学：数字员工平台（LiteClaw）

> 目标：看懂一个能长期运行、多入口、多租户的自托管 Agent 工作台是怎么被工程化的，掌握其中可迁移的 Agent 应用开发机制，并支撑目标简历与面试。
> 水平假设：会写 CRUD、懂 TypeScript 与常见后端概念；方向：Agent 应用开发（`guide-agent`）；实际覆盖：主服务 `src/`、Runner `container/agent-runner/src/`、共享契约 `shared/`、Web `web/src/` 的关键机制；未覆盖 Electron 桌面壳、计费细则与七渠道逐个实现细节（见「选读与进阶目标」）。
> 源码基线：2026-10-17 对本地仓库 `liteclaw-main` 的静态分析；包版本取自 `package.json`（`@earendil-works/pi-coding-agent` 0.84.2、`better-sqlite3` 12.x、Hono、React 19）。仓库未记录 commit 号时以文件与符号为准，行号仅作辅助定位。

## 学习目标与项目地图

**服务对象与目标**：LiteClaw 面向希望"AI 员工在自己服务器上干活"的团队——它不是聊天壳，而是把 LLM 包成一个有身份、有技能、有记忆、有工位、有考勤（定时任务）、有权限边界的员工。产品层级是 `Agent Profile（身份/四段 Prompt/能力策略）→ Workspace（文件目录、执行模式、渠道绑定）→ Session（Main / Runtime / Native Context / Scheduled Run）`。

**它要跨过的四类障碍**（以下为从当前机制逆推的设计目的，仓库未记录当时的立项材料）：

| 障碍 | 具体表现 | 项目里的承担者 |
| --- | --- | --- |
| 执行体不可控 | 模型调用会卡死、被打断、被改配置，进程要能收新消息又不能重来 | Runner 进程协议 + IPC 目录 + 会话串行队列 |
| 上下文不可控 | 系统提示、Agent 人格、技能/MCP/插件清单、渠道格式会互相污染，token 会失控 | PromptPlan 分层 + 能力解析清单 + 上下文预算 |
| 入口不一致 | Web 和七个 IM 渠道的流式、附件、卡片、重试语义各不相同 | StreamEvent 单一契约 + 渠道可靠投递状态机 |
| 长期运行失真 | 重启丢任务、重复发消息、记忆被并发写坏、跨用户越权 | 调度器重启恢复 + inbox/turn/outbox 状态机 + 结构化记忆表 + 无旁路 ACL |

**模块职责**（只列与 Agent 能力直接相关的部分）：

| 模块 | 职责 | 关键入口 |
| --- | --- | --- |
| 宿主主服务 | 消息消费、渠道路由、IPC 分发、调度、Runner 编排、HTTP/WS | `src/index.ts`、`src/web.ts` |
| Runner | 在容器或宿主机里跑一轮 Agent，输出结构化事件 | `container/agent-runner/src/pi-index.ts` |
| Runtime 适配层 | 把 Pi Agent Runtime 的生命周期翻译成产品事件 | `container/agent-runner/src/runtime/pi/` |
| 队列与容量 | 同 Session 串行、跨 Session 并发、退避重试、暖 Runner 生命周期 | `src/group-queue.ts` |
| 能力与上下文 | 四段 Prompt、PromptPlan、Skills/MCP/Plugins 精确清单与挂载 | `container/agent-runner/src/prompt-plan.ts`、`src/effective-skill-resolver.ts`、`src/claude-context-resolver.ts` |
| 可靠性 | 入站/轮次/出站/卡片的持久状态机 | `src/channel-reliability-store.ts` |
| 长期状态 | 定时任务、长期记忆、用量与计费 | `src/task-scheduler.ts`、`src/memory-store.ts` |

**四条代表性端到端链路**（课程按它们展开，不按文件目录展开）：

1. **IM 入站链路**：渠道长连接收到消息 → 准入与租户校验 → `channel_inbox` 落库 → GroupQueue 按序列化键排队 → 拉起容器/宿主机 Runner → Runner 从 stdin 拿 `ContainerInput`、从 IPC 目录持续接收后续消息 → Pi session 流式产出 → `StreamEvent` 回宿主 → 落库 + 更新渠道卡片或 WebSocket。
2. **Web 入站链路**：Web 只是控制面之一，走同一个队列、同一份 StreamEvent 契约；它不改变已由原生 IM 首次占有的 Session 渠道身份（`setSessionChannelOwnerOnce`）。
3. **定时运行链路**：调度器到点 → 以隔离 IPC 目录拉起一次 `isolated` 运行 → Runner 用 `output.task.md` 那套输出契约 → 结果投递回绑定的渠道会话；重启时错过的周期任务记 `missed` 并推进计划，一次性任务补跑。
4. **能力变更链路**：编辑 Agent Profile 或选择技能 → 生成带 hash 的有效清单与上下文预览 → 暂停相关 Runner（mutation pause）→ 提交成功后丢弃旧输入/失效暖 Runner，提交失败则恢复队列。

## 学习重点与记忆提纲

**先理解这些因果（不理解就会背错结论）**：

1. 串行边界是"序列化键"而不是群：同一逻辑 Session 的多个 JID 必须共享一个 Runner，否则同一上下文会被两个进程同时推进；而不同 Session 必须能并发，否则暖 Runner 会互相堵住。
2. 进程边界是一次运行的隔离单位：Runner 只负责"跑一轮 + 接后续消息"，所有租户、权限、计费、落库判断都在宿主，因此 Runner 里的工具副作用必须回宿主执行。
3. 上下文是"计划"而不是"字符串"：每个 prompt block 带 id/owner/condition/hash，才能回答"这轮模型到底看到了什么"，也才能在能力变更时判定暖 Runner 是否失效。
4. 投递可靠性来自状态机而不是重试次数：入站先落库再 claim、出站分 uploading/sending、不确定态单独表达，才避免"重发导致用户看到两条"。
5. 记忆是知识表 + 全文索引而不是向量库：换来可审计、可版本、可软删与确定性排序，代价是语义召回弱，需要靠 kind 与加权列弥补。

**再记住这些主链（能复述即可）**：

- `IM/Web 消息 → 落库/准入 → GroupQueue(序列化键) → Runner(stdin ContainerInput) → Pi session → StreamEvent → 宿主落库+投递`
- `Agent Profile/技能变更 → 有效清单(hash) + 上下文预览 → mutation pause → 失效暖 Runner 或回滚`
- `调度器到点 → 隔离 IPC 运行 → 任务输出契约 → 投递回原会话；重启时 missed 推进计划、once 补跑`
- `记忆写入 → 签名鉴权 + 幂等键 → 版本表 + FTS 行 → 检索 bm25 加权 + snippet`

**必须记住的边界**：Host 模式没有应用层全局并发上限（这是设计选择，不是遗漏）；容器模式受 `maxConcurrentContainers` 与用户计费并发双重限制；Prompt 估算阈值是 SDK 初始化前的保守兜底，权威值来自运行时上下文用量；ACL 没有 admin 全局旁路，越权返回 404 隐藏存在性。
