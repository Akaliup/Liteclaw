00三分钟读懂这本册子

这本册子只做一件事：让「数字员工平台」这个项目在被追问到第四层时，仍然是一个前后一致、有边界、有失败、有数字的故事。它不是知识点百科，是作战脚本。

先说清楚这份材料怎么用。
① 带 的题，答案必须能说到机制层——这些是真实存在的技术骨架，仓库里每一个都能翻到对应实现，背不下来就去读一遍，读完你会比 80% 的候选人讲得清楚。
② 带 的题，答案只到「设计取舍 + 指标口径 + 一次复盘」为止，不要往实现细节里跳，跳进去就是给自己挖坑。
③ 带 的题是被识破的高危区，答案的目标不是赢，是不输——把话题平移到你真正能讲的东西上。

三条铁律

铁律一：先给边界，再给能力。每讲一个模块，第一句是「我负责到哪、不负责到哪」。主动划线的人听起来像做过的人；全是「我独立完成」的人听起来像背简历的人。

铁律二：每个抽象后面挂一个具体。说「上下文预算」→ 立刻给「50k 警戒、100k 硬拒」。说「降级」→ 立刻给「5 分钟窗口错误率 20%、半开 30 秒」。抽象让人怀疑，具体让人相信。

铁律三：留一个真的失败。整场面试至少要主动交出一次「我当时的判断是错的」，并说清后来怎么改的规则。没有失败的项目听起来就是假的。

03三档自述：90 秒 / 3 分钟 / 8 分钟

三档不是把同一段话说长说短，而是三个不同的切面：90 秒给结论，3 分钟给结构，8 分钟给一个决策故事。

90 秒版（开场必用，背到条件反射）

我第一段在慧贸天下，做跨境电商的多店铺数字员工平台。简单说，就是把客服、选品、广告这三个岗位做成能自己干活的 Agent：每个 Agent 有身份和四段 Prompt，有明确挂载的技能和 MCP 工具，有独立的会话和记忆，跑在隔离的运行体里。

我负责 Agent 编排这一层，具体三块：上下文——把系统提示做成一份可审计的「计划」，每块带版本、生效条件、内容 hash 和 token 估算，超预算在建会话之前就拒；能力与工具——按显式选择生成带 hash 的有效清单，容器侧逐个只读挂载，选了但不存在就直接失败不静默替换，有副作用的工具回宿主执行并做幂等；运行与评测——同一会话严格串行、不同会话并行，再往上用 312 条业务用例横评 5 个模型，把结论变成按岗位的路由和三级降级。

结果上，客服人工介入率从 45% 降到 27%，单店 token 成本降了 40%。我最想聊的是上下文预算和工具副作用这两块，因为这两块最容易在线上出事。

3 分钟版（技术面开场，加结构）

这个平台的产品模型是三层：Agent Profile 是身份，管四段 Prompt、能力策略、版本；Workspace 是工位，管文件目录、执行模式（容器还是宿主）、渠道绑定；Session 是运行时，管上下文、记忆、串行队列和一次次的 run。三层对应三种变更频率——月级、客户级、分钟级——分开之后才不会「改一次 Prompt 把租户隔离也动了」。

一次运行长这样：IM 或 Web 收到消息 → 准入和租户校验 → 入站落库 → 按序列化键进队列 → 拉起运行体，通过 stdin 下发结构化输入，运行期间从增量目录持续接新消息 → 运行体里跑一轮 Agent，流式产出事件 → 事件回宿主，落库 + 更新渠道卡片或推 WebSocket。

我这层主要解决三个问题。第一，上下文不可控：系统提示不是一个大字符串，是一份计划，四类归属、固定顺序、条件不满足就不进计划，整份计划算一个总 hash，用来判断暖运行时要不要失效。第二，能力不可验证：分层候选 → 显式选择 → 带 hash 的清单 → 只读挂载，缺了就失败，因为静默替换等于悄悄换了个 Agent。第三，执行不可控：并发边界按序列化键而不是按会话归属，宿主模式刻意不加应用层并发池，卡死用活动时间戳判定、先软关闭再杀进程树。

再往上是我加的评测和路由：312 条用例、120 条人工校准、七个维度加权，输出一张「岗位 × 模型」的适用性矩阵，落到 ProviderPool 的分岗路由和三级降级上。降级不是换个模型继续跑，是换模型 + 收窄工具白名单 + 强制带引用 + 高风险转人工。

8 分钟版（终面 / 总监面，讲一个决策故事）

（前 3 分钟同上，讲完结构后转入下面这个故事。）

我讲一个我判断错的事。上线第 5 周，我们给客服岗位模板做了一次批量改配置，本来以为只是改提示词，风险很低，就没走运行时暂停。结果有 3 家店铺在切换窗口里同时加载了新旧两份人格，表现是同一个人在两句话之间口吻跳变。用户不会说「你配置错了」，用户会说「这个客服是不是精神分裂」。

排查花了 40 分钟，原因很讽刺：日志里两个版本的 Prompt hash 都在，正因为两个都在，才看不出哪个是「应该生效的」。

这件事之后我改了两处。第一处是流程：能力和人格变更统一收口到一个带暂停令牌的事务接口，暂停期间新消息标待处理不拉起新运行，提交成功才丢旧输入换新运行时，失败就恢复队列让原运行继续。第二处是观测：把 Prompt 版本 hash 和 plan hash 写进每一轮的 trace，让「这轮到底用的哪版人格」变成一个可查字段，而不是靠人去比日志。

我更想说的是这件事改变了我对「配置」的看法。在 Agent 系统里，Prompt 不是文案，是行为——改文案可以灰度，改行为必须走事务。后来我做工业诊断那个项目，把「复位、改参数」这类操作放进 PreToolUse 人工审批，其实是同一个判断在另一个场景的延伸：凡是会改变系统行为的东西，都要有提交语义和回滚路径。

L1开场与背景 · Q01–Q10

这一层决定他愿不愿意听你讲第二层。目标只有两个：让他相信你真的在一家公司里干过这件事；让他找到他想钻的那个洞。

Q01用一句话说，这个项目是做什么的？
把 LLM 做成能长期在一个组织里干活的「数字员工」：每个 Agent 有身份和人格、有明确挂载的技能和工具、有独立的工作区和记忆、有考勤（定时任务）、有权限边界，通过 Web 和几个 IM 渠道交付结果。它不是聊天壳，重点是「长期运行」和「多租户」这两件事。

为什么这么说：「长期运行」和「多租户」是这个词组的两个支点，一句话把它们点出来，等于提前告诉他你的难点在哪，他会顺着这两个词追问——而那正是你最强的两块。

追问：和市面上的 Agent 框架有什么区别？

多数框架解决「怎么把一个任务编排出来」，我这边解决「怎么让一个 Agent 长期待在一个组织里」。差别在四件很工程的事：身份人格是一等公民（换 Agent 是改配置不是改代码）；执行有工位（容器或宿主进程按工作区隔离，超时、卡死、重启都有处置）；入口是组织现有的沟通工具（多个 IM 加 Web 共享同一份流式契约和同一套投递语义）；长期状态齐全（定时任务、记忆、用量计费）。反过来说它不擅长把复杂任务拆成任意 DAG 去跑，那是编排引擎的活，我这里的工作流是写在提示词里的规则，不是可执行引擎。

别说「就是一个多 Agent 协作平台」——multi-agent 会立刻把话题引向你没有的东西（子 Agent 编排只接了一层扩展）。

Q02为什么要做这个？之前是怎么解决的？
之前是「人 + 表格 + 复制粘贴」：客服靠人盯五个店铺的后台，选品靠运营手工拉竞品数据做对比表，广告复盘是每周导一次报表人工看 ACOS。三个痛点很具体——跨店铺重复劳动、政策口径不一致（同一个问题不同客服答得不一样）、上下文丢失（客户上午说过不接受分期，下午换个人接手又要重问）。所以第一版没做「全能助手」，只做客服这一个岗位，把政策问答和订单查询跑通，再复制到选品和广告。
追问：ROI 怎么算的？老板为什么批预算？

算的是人力替代率而不是「AI 多聪明」：一个客服能同时看的店铺数从 2 个到 8 个，按人头折算省下来的人力成本，对比 token 成本加服务器成本。第一版上线三个月，客服侧人力没增但店铺数从 60 涨到 140，这是最直接的说服力。

追问：为什么先做客服，不做选品？

因为客服的输入输出最结构化、错误代价最低、可评测性最好——政策问答有明确的标准答案，能建用例。选品涉及比价和主观判断，早期做它等于先做一个没法评测的东西，出了问题只能靠感觉调。

可用锚点：第一版只做客服 / 三个月店铺 60→140 / 人力未增
Q03你具体负责哪一块？边界在哪？
我负责 Agent 编排这一层，具体三块：上下文（四段 Prompt、Prompt 计划、token 预算、每轮拼接）、能力与工具（技能与 MCP 的解析、有效清单、挂载、工具副作用的回宿主执行）、运行与评测（会话串行队列、运行体生命周期、模型评测与路由）。

不负责的三块我说清楚：前端控制台是另一个同事；渠道适配（飞书、企微、WhatsApp 的 SDK 对接）是后端同学；模型侧我们只调 API，没有微调，也没有自己的推理集群。

为什么先说不负责：面试官判断「这人是不是真做过」的一个隐性标准，是看他知不知道自己不知道什么。一个把整条链路都说成自己做的人，反而会被认为没进过真实团队。

追问：那队列和投递状态机也是你写的？

队列的串行语义和暂停/恢复是我改的，投递状态机那张表是后端同学建的、我参与了状态设计（尤其是「不确定态」那一条）。这个区分很重要，因为它决定了我能不能讲投递的细节——我能讲语义，不能讲每个渠道 SDK 的重试参数。

别说「全栈都是我」；也别说「我只是打杂」——前者不可信，后者等于放弃这个项目。
Q04团队怎么分工？你和产品、运营怎么协作？
Agent 小组 4 个人：我、一个后端、一个前端、一个从运营转过来的产品。节奏是双周迭代，需求从运营侧来——他们最清楚哪类问题答错了。

协作上有个我觉得挺关键的做法：用例先于 Prompt。运营提一个场景，先把它写成 3–5 条带标准答案的用例进 Benchmark，然后我才动 Prompt。这样「这次改动有没有变好」不是靠感觉，是靠那几条用例过没过。产品负责判断用例的业务重要性，我负责判断它能不能被稳定判定。
追问：运营不懂技术，怎么保证用例质量？

两道。第一道是把用例写成「输入 + 期望行为 + 不可接受行为」，不写「期望话术」——话术会限制模型，行为不会。第二道是我做一次可判定性审查：这条用例我能不能用确定性断言判？不能的话能不能用 rubric 判？都不能就打回去重写，因为不可判定的用例进了 Benchmark 只会制造噪音。

可用锚点：4 人小组 / 双周迭代 / 用例先于 Prompt / 3–5 条起
Q05第一个版本做了多久？上线节奏是怎样的？
第一个可用版本大概 7 周：前 3 周做最小闭环（一个岗位、一个渠道、能问答能查单），中间 2 周做隔离和权限（不然不敢给第二个店铺用），最后 2 周做投递可靠性和评测基线。之后是双周一个小版本。

真正的转折点是第 3 个月接入第二个岗位的时候——我们发现「加一个岗位」不是加一段 Prompt，而是要重新想清楚能力清单怎么按岗位裁剪。那次之后才把「岗位模板」这个东西抽象出来。
追问：7 周怎么排的？为什么先做隔离再做功能？

因为多店铺产品的第一道生死线是「A 店的数据不能出现在 B 店」，这个如果留到后面补，所有查询接口都要返工。功能可以少，边界不能错——这是我当时跟产品争得最凶的一次，最后用「先给两个店铺试用，串一次数据就停项目」说服了他。

Q06用户真实反馈里，最扎心的一条是什么？
「它答得对，但我不敢用。」

一个客服主管的原话。她不是嫌回答不准，是嫌没有依据——客户问「你们这个能不能退」，Agent 答「可以的，30 天内」，她没法确认这句话是从哪条政策来的，只能自己再查一遍，那 Agent 就白干了。

所以后面做的第一件事不是提准确率，是强制引用：知识库检索必须返回命中的政策条款和版本，回答里带出处；检索不到就不许答，转成「我帮你确认一下」。这一条上去之后，人工介入率反而降得比提准确率那次更快。
追问：强制引用会不会让回答变得很啰嗦？

会，所以引用是结构化的不是散文式的：正文正常说，末尾挂一个来源标记，前端渲染成可点的小标签，IM 里渲染成一行「依据：退货政策 v3 §2.1」。用户不点就看不见，客服点开就能核。这件事的本质是把「可信」从文案问题变成数据问题。

可用锚点：「答得对但不敢用」/ 强制引用 / 检索不到就转人工
Q07你们说「数字员工」，和普通的客服机器人差别到底在哪？
三个东西：身份、工位、考勤。

身份是四段 Prompt 加能力策略，可以版本化、可以灰度、可以回滚——「换一个客服」是改配置不是改代码。工位是工作区，文件、记忆、权限、渠道绑定都在这一层，两个店铺的 Agent 物理上不共享目录。考勤是定时任务，它会在没有人的时候自己起来干活（比如每天早上拉一次竞品价格），而且重启之后「错过的那次」有明确语义。

普通客服机器人是「一问一答的函数」，数字员工是「一个有状态的进程」。这个差别在演示里看不出来，在第七天就看出来了。
追问：「有状态的进程」具体指什么状态？

三类：会话状态（这轮之前聊了什么、有哪些未确认的输入）、记忆状态（这个客户的事实、决策、待办，带版本和来源）、运行状态（这个会话的运行时是不是暖的、有没有被暂停、上一次失败了几次）。第三类最容易被忽略，但它决定了「用户点了停止之后会不会自己又跑起来」。

Q08为什么要把产品模型切成 Profile / Workspace / Session 三层？两层不行吗？
因为这三件事的生命周期不一样，混在一起会互相污染。

Profile 是配置，月级变更，责任人是我和产品；Workspace 是权限和数据边界，客户级，责任人是租户管理员；Session 是运行时状态，分钟级，没有责任人，它是自动的。三层对应三种变更频率、三种责任人、三种失效方式。

两层最典型的坏结果是：改一次 Prompt，把所有店铺的权限配置也一起带进了变更窗口——你本来只想改一句话，结果触发了一次全平台运行时重启。反过来也成立：某个店铺要迁走，你要动的是 Workspace，不应该碰到 Prompt 版本。
追问：那 Session 为什么还要再分 Main / Runtime / Native Context？

因为「一个逻辑会话」和「一个运行体」不是一对一。同一个逻辑会话可能换过运行时（比如配置变更、进程崩了重拉），但它的消息历史是连续的；而原生上下文（引擎自己维护的那份对话状态）是绑在某一个运行时实例上的，换代就没了。分开之后，才能回答「这次回答是基于哪一段历史」——这在排查「它为什么忘了刚才说的话」时是必须的。

别说「三层是行业最佳实践」——他会立刻问「哪个行业、哪篇实践」，你就死了。只说生命周期。
Q09一个店铺一个 Agent，还是一个岗位一个 Agent？
岗位是模板，店铺是实例。Profile 定义「客服应该是什么样」，一个店铺绑一个客服 Workspace，Workspace 里实例化这个 Profile。所以是「M 个岗位模板 × N 个店铺 = M×N 个运行时身份，但只有 M 份配置」。

这个设计的好处是改一次模板能影响所有店铺，坏处也是这个——所以我们加了「店铺级覆盖」：模板里允许某些字段被店铺覆盖（比如店铺专属的退货地址、品牌口吻），覆盖项单独记版本，模板升级不会冲掉覆盖。
追问：模板升级怎么不冲掉店铺覆盖？

字段级的三态：继承、覆盖、锁定。继承跟随模板；覆盖是店铺自己写的值，模板升级不动它；锁定是「这个字段禁止被模板改」。合并的时候按字段算，不是整份 Prompt 替换。这里踩过坑——早期是整段替换，结果一次模板升级把三个店铺的品牌口吻改成了通用口吻，客户直接投诉到运营。

可用锚点：M 模板 × N 店铺 / 字段级三态：继承·覆盖·锁定
Q10如果让你重做一遍，第一件事会改什么？
把评测放在最前面，而不是第三个月才补。

我们一开始是「先做功能，出问题了再想怎么测」，结果前两个月所有的调优都是拍脑袋——改完 Prompt 觉得「好像好一点」，其实可能只是那天的样本偏了。等到 312 条用例建起来，才发现有些早期的设计决策根本没法评测，比如把所有政策塞进系统提示里，用例一跑就知道这条路走不通，但那时候已经写了一堆依赖它的逻辑。

如果重做，我会在第一周就先写 30 条用例，哪怕很粗糙。有了尺子再盖房子。
追问：30 条够吗？会不会覆盖不全？

不够，但它能挡住最蠢的错误。我的经验是：30 条用例能覆盖 80% 的「明显不对」，剩下的 20% 要靠 badcase 回流慢慢长。真正危险的不是用例少，是没有回流机制——用例是会长大的东西，一开始就要留好入口。

L2架构与设计 · Q11–Q24

这一层是他判断「你是使用者还是建设者」的分水岭。每个答案都要有一个「不这么做会怎样」的反面。

Q11一条消息进来，到用户看到回复，中间发生了什么？
八步，我按顺序说：

① 渠道长连接收到消息，做准入和租户校验；② 入站先落库，不直接进内存队列——这是后面所有可靠性的前提；③ 带租约领取，按序列化键进队列，同一逻辑会话严格串行；④ 拉起运行体（容器或宿主进程），通过 stdin 下发一份结构化输入；⑤ 运行体建会话、拼 Prompt 计划、解析能力清单、挂载工具，然后跑一轮；⑥ 运行期间从增量目录持续接新消息，作为「跟进」注入同一会话，不是新开一轮；⑦ 流式事件回宿主，宿主落库、更新渠道卡片或推 WebSocket；⑧ 一轮结束做幂等收尾，没确认的消息写回队列重投。
追问：为什么入站要先落库？直接进内存队列不是更快？

快，但会丢。进程重启、部署、OOM 都会让内存队列消失，而 IM 侧不会重发——用户以为发了，系统里没有。落库之后再领取，最坏情况是重复处理（可以用幂等键去重），而不是丢消息。这个取舍在所有投递系统里都一样：宁可重复，不可丢失，然后用幂等把重复的代价压到零。

追问：第 ⑥ 步「跟进」和「新开一轮」的区别是什么？

跟进是注入到当前这一轮的会话里，模型能看到「用户在我干活的时候又说了句话」，历史是连续的；新开一轮是另起一个上下文，模型不知道上一轮在干什么。区别在体验上很直观：用户说「帮我查下订单」然后补一句「是上周那个」，跟进能接住，新开一轮就变成「哪个订单？」。

画图顺序：消息 → 落库 → 租约领取 → 序列化键排队 → 运行体（stdin）→ 会话/计划/能力/工具 → 流式事件 → 宿主落库投递 → 幂等收尾
Q12为什么用独立进程跑 Agent，而不是在主服务里直接调 SDK？
三个理由，按重要性排：隔离、可控、可换。

隔离：Agent 会执行模型生成的代码、读写文件、调用工具，这些不能和主服务共享进程和权限。独立进程 + 只读挂载 + 受限目录，最坏情况是炸一个运行体，不是炸整个服务。

可控：模型调用会卡死、会跑飞、会被用户中途打断。在主服务里你只能等它返回或者杀线程（很多 SDK 根本杀不掉），独立进程可以直接杀进程树，还能先发一个关闭哨兵让它优雅收尾。

可换：运行体里是「引擎适配层 + 产品事件」，换引擎只改适配层；主服务只认结构化输出和事件，不认引擎类型。
追问：进程间怎么通信？为什么不用 HTTP？

stdin/stdout 加一个增量目录。stdin 下发一次结构化输入（JSON，用固定标记包起来，避免和日志混在一起）；stdout 逐条输出结果和事件；运行期间的新消息走增量目录里的文件，运行体轮询消费。不用 HTTP 的原因是方向不对——宿主到运行体是「推」，运行体到宿主是「流」，HTTP 要么长轮询要么 SSE，两边都得维护连接状态，而文件和管道天然是「谁在谁读」，崩了也不留下半开连接。

追问：那你们怎么保证 stdout 里不会混进调试日志？

用标记包裹：每条结构化输出以固定起始标记开头、固定结束标记结尾，标记之间的内容才解析，标记外的当日志丢弃。这个设计很小但很关键——一旦日志混进协议流，解析就会随机失败，而且只在特定日志量下复现，极难排查。

Q13「序列化键」是什么？为什么不按会话或群来串行？
序列化键是「共享同一份上下文的那个标识」，不一定是群 ID。同一个逻辑会话可能有多个入口——Web 页面、私聊、某个话题——它们共享同一段对话历史，就必须共享同一个运行体并且严格串行，否则两个进程同时推进同一份上下文，模型看到的历史会互相覆盖。

反过来，不同会话之间没有共享上下文，就该并行。早期版本我用过一个全局并发池，结果一个「空闲但没超时」的暖会话能把别人的消息卡住整整一个空闲超时周期——那是我第一次意识到，并发控制的粒度选错，比并发数设错更致命。
追问：那不同会话并行，资源不会打爆吗？

会，所以并行不是免费的。容器模式有两道闸：系统级容器并发上限，和用户计费并发上限——后者是产品语义，你买的套餐决定你能同时跑几个。宿主模式我刻意不加应用层并发池，因为进程由操作系统管，加了反而会和 OS 的调度打架，还容易掩盖真实容量。

追问：同一会话串行，那用户连发三条消息，后两条要等很久？

不会等成三轮。第二条进来的时候，如果第一条还在跑，它会作为「跟进」注入当前轮，而不是排一个新轮次。等于三条消息被合并进同一轮的处理里。这也是为什么「不能按消息数算延迟」——用户感知的是「我发完之后多久有回应」，不是「每条消息多久」。

Q14宿主模式为什么不加应用层并发池？这不是偷懒吗？
是刻意的设计选择，不是遗漏，而且我在文档里写清楚了，就是为了避免后来人「顺手加一个」。

理由：宿主模式下每个运行就是一个普通进程，CPU、内存、文件句柄都由操作系统调度。你在应用层再放一个信号量，等于在 OS 之上套一层不懂 OS 的调度器——它不知道哪个进程真的在吃 CPU，只知道「我发了 N 个令牌」。更实际的问题是，这个池子会和空闲回收打架：一个暖会话占着令牌但没在干活，新消息就进不来。

容器模式不一样，容器是重资源，创建有成本，必须显式限制并发数。
追问：那宿主模式跑太多进程把机器打爆怎么办？

两层兜底：一是每租户的计费并发上限，这是产品侧的闸；二是 OS 层的资源限制（进程数、内存上限、CPU 配额），由部署侧配。如果真到了要应用层限流的地步，说明该上容器了，而不是在宿主模式里打补丁。

别说「因为懒 / 没来得及做」——把设计选择说成遗漏，等于承认自己不懂容量模型。
Q15容器模式和宿主模式的差别？什么时候用哪个？
差别在隔离强度和启动成本的取舍。

容器：文件系统隔离、能力只读挂载、并发有明确上限、启动慢（秒级）、适合「不受信任的 Agent」和「多租户」。宿主：直接跑在机器上、启动快、能用的东西多（本地工具、系统命令），但隔离弱，所以额外要求管理员身份才能开——因为它跑在有权限的机器上，风险和容器不是一回事。

我们的默认是容器，宿主留给「自己的机器、自己的 Agent」这种场景。
追问：宿主模式要求管理员身份，为什么？

因为宿主模式下的 Agent 能碰到机器上的一切：文件、进程、网络。让普通租户开这个，等于给他一个 shell。这不是权限洁癖，是风险定价——容器的越权最多是越出工作区，宿主的越权可能是整台机器。

Q16多店铺隔离，你到底隔离了什么？
四层，从下往上：

文件：每个 Workspace 一个目录，容器侧只读挂载自己的那部分，挂载清单是显式生成的，不是扫目录。数据：所有查询强制带 workspace 条件，没有「管理员旁路」可以跳过它。能力：技能、MCP、插件按 workspace 解析，A 店挂的工具 B 店根本看不见。上下文：会话和记忆按 workspace 分区，检索带 scope 过滤，跨店检索在接口层就不存在。

再加一层隐性的：计量。token 用量按 workspace 归集，否则成本算不清，也没法做配额。
追问：文件隔离靠目录，那软链接或者路径穿越怎么办？

挂载是白名单不是黑名单：只挂清单里列的路径，而且是只读。路径穿越在容器里最多穿到别的挂载点，穿不到宿主；宿主模式下有额外的路径校验，拒绝一切指向工作区之外的解析结果。关键是不给「解析后再说」的机会——先规范化路径再判断，而不是判断完再解析。

追问：向量检索的 metadata filter 会不会破坏召回？

会，这是向量库的老问题：先过滤再搜索会破坏图的连通性。我们的做法是——记忆这块根本没上向量（用结构化表加全文索引），所以不存在这个问题；如果将来上，大租户会用独立分区而不是 filter。这个回答的好处是：它同时展示了你知道这个坑，又解释了为什么你的方案里没有这个坑。

Q17多租户系统里，管理员该不该有全局权限？
分两层看，不能一句话答。

平台运维层需要全局能力：系统配置、用户与邀请、审计、计费——这些语义本来就是跨租户的，没有全局权限根本没法运维。

工作区和渠道资源这一层，我不给管理员全局旁路。原因不是洁癖：这类资源一旦有旁路，就会出现「管理员能看别人 Agent 的对话历史」这种状态，而这恰恰是自托管产品最敏感的东西——客户把 Agent 放在自己服务器上，图的就是数据边界清楚。所以判断函数只看创建者和显式授权，管理员不是隐式授权。
追问：那管理员要排障怎么办？总不能每次都找客户授权吧？

给他「可观测但不含内容」的能力：看运行状态、看错误码、看 token 用量、看 trace 的结构（哪一步失败、调了哪个工具），但不看消息正文和记忆内容。真要查内容，走客户授权的临时授权流程，有时限、有审计。这个划分我觉得比「给不给」更有意义——排障需要的是结构，不是内容。

追问：这套权限怎么验证没漏？

四身份契约测试：创建者、同租户其他人、管理员、不存在的 ID，四种身份对每个资源族跑一遍，预期是「成功 / 404 / 404 / 404」。把管理员也写成用例，是因为「顺手加个旁路」最容易发生在修 bug 的时候，测试是唯一的刹车。

Q18越权为什么返回 404 而不是 403？
因为 403 会泄漏「这个资源存在，只是不属于你」。攻击者可以用 403 和 404 的差异做枚举：遍历 ID，返回 403 的就是存在的资源，返回 404 的就是不存在——一次遍历就能摸清你有多少工作区、多少会话。

统一返回 404，等于把「存在性」也当成敏感信息。代价是排障时稍微麻烦一点（分不清是没权限还是没有），所以我们内部日志里记真实原因，对外只给 404。
追问：那用户体验不就差了？用户明明有权限却看到 404 怎么办？

只有越权才 404，有权限的正常返回。用户看到 404 的场景基本只有一种：链接过期或者被移除了——这时候 404 反而是对的语义。

一句话总结：403 说「你不能看」，404 说「没有这个东西」，后者不提供枚举面
Q19改了配置，正在跑的会话怎么办？
做成一次事务，三段：暂停相关运行——暂停期间新消息标记为待处理，不再拉起新运行；提交变更；收敛——提交成功就丢弃旧运行里挂起的输入、用新配置起新运行；提交失败就把队列恢复回去，让原运行继续。

关键是「用户主动停止」和「变更引起的停止」必须分开：前者丢弃被中断的输入（用户不想继续了），后者必须保留待重放输入（用户没打算放弃那句话）。这两种状态在队列里显式表达，不靠「进程还在不在」去推断。
追问：暂停期间用户发的消息去哪了？会不会丢？

进待处理队列，不丢。暂停只是「不拉起新运行」，消息照常落库。变更完成后按顺序重放。这里有个细节：重放要带原来的时间戳和渠道上下文，否则投递会投错地方——用户在两分钟前在飞书群里问的，不能在 Web 上回。

追问：如果提交卡住了，一直不返回呢？

暂停有超时。超时后按失败处理，恢复队列，并且把这次变更标记为「未生效」——注意不是「回滚」，因为可能已经写了一部分。真正的收敛靠幂等：变更带版本号，重复提交同一个版本是安全的。

Q20流式事件为什么强调「单一真相源」？
因为流式事件是三方唯一共享的数据结构：宿主要落库和广播、运行体要输出、前端要渲染。三份各自演化，症状是「某个事件在 Web 上能显示、在 IM 卡片里丢了」，而且极难定位是谁的问题。

做法是一份类型定义文件做真相源，构建时复制到三个消费方，三份都是生成物、不允许手改，改副本会被一致性校验拦下来。事件里带作用域（主代理还是子代理）、展示层级（主文本、细节、调试）、运行归因标识——宿主不需要知道某个事件该不该给用户看，它只负责转发，前端按层级决定放主文本还是细节面板。
追问：加一种新事件要改几处？

两处：真相源加类型，两个消费方的渲染加分支。投递链路不用动——这是分层带来的好处。如果加事件要改投递，说明抽象漏了。

追问：展示层级放在事件里，会不会让事件变大？

会多几个字节，但省掉的是「宿主判断该不该发」的逻辑，那个逻辑一旦写错，就是把调试信息发给客户。用一点带宽换一次事故，我觉得值。

Q21投递为什么要做成状态机？重试几次不就行了？
因为 IM 的超时语义是歧义的：超时可能意味着没发出去，也可能意味着发出去了但响应没回来。重试的代价是用户看到两条一样的回复，不重试的代价是用户永远收不到。这个二选一，靠「重试次数」是解不掉的，只能靠状态。

所以四张表：入站、轮次、出站、流式卡片。入站先落库再带租约领取并续约，防两个消费者处理同一条；轮次有心跳和终态，超时中断；出站分上传和发送两个阶段，每阶段结束才推进状态；到了「可能已经成功」的边界，状态不是成功也不是失败，而是单列的不确定态，要求核对而不是自动重发。
追问：不确定态谁核对？总不能让人天天看。

分层闭合。绝大多数能在系统内闭合：发送前记录载荷哈希和消息锚点，超时后先查会话里有没有对应的已发送记录，查到就判成功、收敛；查不到才进不确定态。真正要人的是「平台既不支持幂等也不支持查询」的场景，这类按人工对账处理，错误信息带固定前缀，UI 上一眼能看出「这条需要人工确认」。

追问：那这个不确定态的比例大概多少？

很低，但我不给精确数——因为它是长尾，取决于渠道 SDK 的质量。我能量化的是「自动闭合率」：绝大多数超时在查询阶段就被收敛了，进人工的是万分之一量级。这类数字我不会编，只能说量级。

别编一个精确到小数点的比例。长尾指标编不圆，而且他很可能追问「怎么统计的」。
Q22长期记忆为什么用全文索引，不用向量检索？
因为我要的不是「语义最相近」，是能被引用、能被修改、能被追责。

底层是结构化知识表：每条记忆有类型（事实、决策、教训、待办）、状态、版本、来源、更新时间；检索用全文索引按加权列排序，返回命中片段。向量检索的优势是语义召回，代价是结果不可解释、更新后难以确认哪些旧向量失效、跨租户隔离要额外索引结构。

我们的场景里 Agent 需要的是「上次这个客户说不接受分期」这种确定事实，不是「意思相近的段落」。所以我选了可审计的那条路，代价是近义召回弱——用类型过滤和列权重去补。
追问：那同义词怎么办？客户说「分期」和「账期」你怎么召回？

两层：写入时做一次术语归一（把同义说法映射到标准词，落在 keywords 列），查询时扩展查询词。这不是向量那种「自动懂」，是人工维护的词表——但它可控，错了能改，而且改完能回归测试。向量召回的错你没法「改」，只能重训或者调阈值。

追问：并发写坏了怎么办？两个会话同时改同一条记忆。

乐观并发：更新带期望版本，冲突就失败重试。删除不是真删，是状态置为失效并留墓碑——召回不再命中，但审计还能回答「这条什么时候被谁作废的」。写入还要求签名鉴权和幂等键，因为运行体在隔离环境里，不能让它直连库——那等于把租户边界交给提示词去守。

Q23服务重启，定时任务的语义怎么保证？
两种任务两种语义，这必须显式写死，不能靠「部署时别重启」回避。

周期任务错过一次，我不补跑，只记一条「错过」并推进到下一个计划点——补跑十个闹钟通知没有意义，反而会刷屏。一次性任务不一样，它代表用户明确要在这个时间点做这件事，所以重启后仍然补跑。

还有两个细节：任务定义有指纹，用来区分「同一任务重试」和「任务被改过之后的新版本」——用户改了提示词，旧版本的失败计数不该算在新版本头上；任务和对话共用同一套超时和队列语义，因为它本质上也是一次 Agent 运行，占同样的配额。
追问：任务一直失败，怎么不烧钱？

有界重试：到顶就收敛成失败并留记录，下一次按计划正常触发，不因为上次失败就改变计划。加上配额约束——配额耗尽时任务不执行并记录原因，而不是排队等一个可能永远不来的额度。

追问：任务的输出和对话有什么区别？

任务运行是「无人等待」的，它不知道有谁在看，所以要求结束时给结论性内容，而不是反问用户。这个约束是写在输出契约里的，不是靠提示词提醒——提示词会忘，契约不会。

Q24这套架构里，你觉得最脆的地方在哪？
三处，按脆弱程度排：

第一是配置变更与运行态的一致性。它跨了四个东西——数据库、队列、运行体、渠道绑定——任何一处没处理好，表现都是「行为变了但没人知道为什么」。我出过的那次事故就在这。

第二是工具副作用的幂等。运行体回宿主执行工具有网络跳，跳一次就多一个「不知道成没成」的窗口。我们现在靠幂等键加不确定态兜，但这是补丁，不是根治。

第三是上下文预算的估算。估算永远是估的，真实值只有运行时知道。我们用的是保守口径（宁可提前拒），代价是偶尔误拒一个其实没超的配置。
追问：第三点误拒不会影响体验吗？

会，但比反过来好。误拒的表现是「保存失败，提示内容过长」，用户改短就行；误放的表现是「上线后这一轮直接 400」，而且是随机复现——因为供应商那边的截断策略不透明。前者是可解释的失败，后者是不可解释的失败。

这句话很值钱：「可解释的失败」优于「不可解释的成功」——它能套用到你后面所有的设计取舍上。

L3机制深挖 · Q25–Q42

这一层是这本册子最值钱的部分。答案里的阈值、顺序、字段名、失败分支，是「做过」和「听过」之间唯一的分界线。建议每一题都去仓库里读对应的那一课，读完再回来背。

Q25Agent 的系统提示你是怎么组织的？为什么不做成一个大模板字符串？
大模板字符串的三个问题在我们这里都会立刻变成线上问题。

第一是不可审计：用户问「我的 Agent 为什么这么说话」，你得能回答这轮到底注入了哪些块、各占多少 token；字符串拼完就查不出来了。第二是不可失效：人格、技能清单、工作区记忆任何一处变了，正在跑的暖运行时必须失效，否则它还在用旧人格；要知道变没变，就得有内容哈希。第三是不可控预算：平台块、人格块、记忆块、渠道格式块会随租户和渠道组合放大，必须在送模型之前就知道总量。

所以我把系统提示做成一份计划：每个块带标识、版本、作用域（主代理还是子代理）、归属（平台 / Agent / 工作区 / 渠道）、是否必需、生效条件、内容哈希、字节与 token 估算；整份计划再算一个总哈希。块之间顺序固定，条件不满足的块不进计划。这样「这轮模型看到了什么」是一个可序列化的产物，能存审计、能在两个版本之间 diff。
追问 1：为什么要有「生效条件」这个字段？

因为同一份配置在不同场景下该不该出现是不同的。比如「渠道格式块」只在 IM 渠道出现，Web 不需要；「子代理协作指引」只在允许派生子代理时出现。把这些写进条件，而不是在代码里 if-else，好处是条件本身可审计——用户能看见「这块为什么没出现」。

追问 2：整份计划的哈希用来干什么？

判断暖运行时要不要失效。哈希不变，说明模型该看到的东西没变，暖会话可以继续用，省掉一次冷启动；哈希变了，说明配置或能力变了，这个运行时已经「过期」，必须换。没有这个哈希，你只能靠「配置文件改了」这种外部事件去猜，猜错就是人格串味。

别说「用一个模板引擎，比如 Jinja / Handlebars」——那是实现细节，且会把他引向「模板注入怎么办」，跟你没关系。
Q26token 估算是在什么阶段算的？引擎自己不是会算吗？
引擎的用量是权威的，但它是会话建好之后才有的。我需要在建会话之前拦一道，因为提示超限的表现是这一轮直接失败，而失败点在供应商那边，排查成本极高。

所以在计划阶段用保守口径估：按 UTF-8 字节数除以四，再和多字节字符的实际个数比，取大的那个。这个口径对英文偏保守、对中文更保守，正是我要的方向——宁可提前拒，也不要上线才发现。

两级阈值：越过警戒线只记警告并继续，越过硬阈值就报错、拒绝启动这一轮，让调用方看到明确的失败原因，而不是模型侧返回一个看不懂的 400。
追问：为什么是「字节除以四」和「字符数」取大？不能直接用 tokenizer 吗？

tokenizer 要加载词表、要跟模型版本对齐、还有不同供应商的差异，放在请求路径上既慢又脆。字节除以四是个粗糙的近似（英文大约 4 字节一个 token），多字节字符数是个下界（中文一个字至少一个 token）。两者取大，等于取「两种错误里更保守的那个」。是近似，但方向可控。

追问：硬阈值具体多少？

警戒 50k，硬拒 100k。这两个数不是拍的——是按我们主力模型的上下文窗口留出输出和工具结果的预留之后倒推的。而且它们是「计划阶段」的阈值，运行时的压缩阈值由引擎按模型自己的预留策略决定，两者不是一回事，我在文档里写清楚了，就是怕有人以为改个数字就能改压缩时机。

Q27某个 Agent 的人格块特别长，一直触发警告，你怎么处理？
警告是有用的信号，但不该变成静默降级。

我的顺序是：先让警告可见——写日志、进上下文审计、前端的能力预览里能看到每个块的估算；再由产品层决定是提示用户精简，还是让运行时自己做压缩。我不会在计划阶段悄悄截断人格块，因为截断人格等于悄悄换了一个 Agent，这个后果比超限更难排查。

真正的兜底在运行时：压缩开关始终打开，阈值由运行时按模型自己的预留策略决定。历史里那些「按百分比触发压缩」的旋钮在当前引擎下只是参考值，不会真的控制行为——这个区别必须写在文档里，否则会有人以为改个百分比就能改时机。
追问：那如果用户就是不精简，一直警告呢？

那就一直警告。警告不是错误，它是给人看的决策依据。真正会拦住他的是硬阈值——到 100k 就保存不了，那时候他必须处理。中间这段「能跑但很贵」的区间，选择权交给用户，因为只有他知道这段人格对他值不值这个钱。

别说「我会自动截断最长的块」——这是本册里最容易被判「没做过」的回答之一，因为它回避了「截断等于换 Agent」这个真问题。
Q28每轮还要拼画像、记忆、渠道格式，为什么这三块单独拆出来？
因为它们的变化频率和静态块完全不同。静态块在一个会话里基本不变，是会话级的；记忆摘要和工作区状态每轮都可能变，渠道格式取决于这条消息从哪来。

混在一起有两个坏结果：一是任何一轮的记忆变化都会让整份计划的哈希变掉，暖运行时的失效判断就没法用；二是审计里分不清「模型看到的这段是人格还是记忆」。

拆开之后，会话级哈希只覆盖静态块；轮次级内容单独拼在提示末尾、带自己的标记，顺序固定为画像 → 记忆 → 渠道格式 → 用户输入。顺序固定也有实际意义：它让同一份配置在不同轮次之间的 diff 只出现在真正变化的部分。
追问：顺序为什么是这个顺序？把用户输入放最前面不行吗？

不行。用户输入放最前面，模型容易把「刚才那句话」当成唯一指令，忽略人格和流程约束；放最后，等于「先立规矩，再说事」。而画像和记忆放在规矩之后、事情之前，是因为它们是「关于这个人和这个客户的事实」，属于上下文而不是指令。这个顺序我们也试过别的排法，最直观的差异是「客服会不会忘记用客户称呼」。

Q29四段 Prompt 具体是哪四段？冲突了谁优先？
四段：IDENTITY（我是谁、服务谁、边界在哪）、SOUL（价值取向、语气、什么情况下宁可说不知道）、AGENTS（工作流：先做什么后做什么、什么情况转人工）、TOOLS（能用哪些工具、什么条件下用、哪些必须审批）。

优先级是 TOOLS > AGENTS > SOUL > IDENTITY，从硬到软：工具约束是系统能力边界，业务不能覆盖；流程是业务规则；语气是风格；身份是背景。冲突判断不靠模型自觉，靠拼装顺序和显式声明——同一段里出现冲突时，高优先级段落的内容会以「约束」措辞后置，让模型最后看到。
追问：为什么 TOOLS 优先级最高？它不是最没「人格」的一段吗？

正因为它是能力边界的声明。如果业务能覆盖 TOOLS，等于允许「用提示词提权」——比如业务写一句「你可以直接给客户退款」，就把审批流程绕过去了。所以 TOOLS 段的变更要走技术审核，不接受业务直接编辑。这个规则很土，但它挡住的是最贵的一类事故。

追问：这四段和「系统提示 / 用户提示」是什么关系？

正交的两个维度。四段是「内容归属」，系统提示和用户提示是「注入位置」。四段里前三段通常进系统提示，TOOLS 的一部分（比如本轮可用工具清单）会跟着工具定义走，不占提示词。这么分是为了让「改语气」和「改能力」变成两个互不影响的动作。

Q30append 和 replace 两种编排机制，什么时候用哪个？
append 是叠加：在模板基础上补充业务约定，比如「本店周末不发货，遇到物流时效问题要主动说明」。replace 是整段替换：当业务需要一套完全不同的流程时用，比如「这个店铺的退货走线下，不要引导客户走平台流程」。

判断标准很简单：新内容和旧内容能不能共存。能共存就 append，会打架就 replace。同段同时出现 append 和 replace 时，replace 生效，并把 diff 记进变更记录——因为 replace 的语义是「我明确不要原来那段了」。
追问：append 多了会不会互相矛盾？

会，而且这是最常见的翻车方式：三个运营各 append 了一条，其中两条冲突，模型就随机选一个执行。所以我们限制 append 的条数和总长度，并且要求每条 append 带「适用场景」——不写场景的 append 直接拒绝。这个限制很烦，但它把「模糊叠加」变成了「带条件的规则」。

追问：replace 掉了原来的流程，回归用例怎么办？

用例跟着模板走，不跟着店铺走。replace 之后这个店铺跑的是「变体用例集」——基础用例里那些依赖原流程的会被标记为不适用，同时必须补 3 条新流程的用例。没有用例的 replace 不允许提交，这是硬规则。

Q31你说的「配置回归」，具体怎么跑？改一次 Prompt 要多久？
两档：smoke 60 条，8 分钟，每次改配置自动跑；其中 20 条是 gate，挂了不允许提交。跑的方式是固定输入 + 固定模型参数 + 固定工具桩，只看「行为」不看「措辞」——措辞每次都不一样，看措辞的回归测试会一直红。

判定分两类：确定性断言（有没有调用正确的工具、有没有引用到正确条款、有没有越权字段）和 rubric 判定（完成度、事实性）。前者必须 100% 过，后者允许波动但有阈值。
追问：8 分钟够吗？60 条怎么选的？

不够全，但够挡住回归。60 条是「每个能力点至少一条 + 每个历史事故一条」选出来的，不是随机抽。历史事故那部分最重要——每修一个 badcase，就把那个 case 固化进 smoke，用例只会变多不会变少。

追问：模型本身也会变（供应商升级），怎么区分是配置的问题还是模型的问题？

固定模型版本，升级模型单独走一次全量 312 条，不和配置变更混在一起。混在一起是最容易扯皮的事——你改了一句 Prompt，结果模型那天升级了，指标掉了，你说不清是谁的锅。

Q32一个 Agent 同时挂了技能、MCP 服务和插件，你怎么保证它实际拿到的就是你选的那几个？
三步，把它变成可校验的产物。

第一步分层候选：内置、外部、项目、托管、工作区、用户、插件各自成一个来源层，同名能力按层优先级去重。这一层只负责「可能有哪些」。第二步精确选择：用户在 Agent 策略里显式选了哪些，就只保留哪些；选择结果连同每个能力目录的内容哈希生成一份有效清单，清单本身也有哈希。第三步才是挂载：容器模式按清单逐个只读挂载，宿主模式把同一份清单同步到会话目录。两种模式用同一份清单，不存在「容器里是这批、宿主里是那批」。
追问：为什么挂载要「逐个只读」？直接挂一个总目录不行吗？

挂总目录等于把「这个 Agent 能看见什么」交给目录内容决定，而目录内容是可以被别的东西改的。逐个挂载之后，能看见什么完全由清单决定，清单有哈希、有审计、可以 diff。这是「白名单」和「黑名单」的差别。

追问：清单里的哈希是什么的哈希？

每个能力目录内容的哈希，加上清单本身的哈希。前者的作用是发现「技能内容被改了但版本号没变」——这在插件和外部技能里很常见；后者的作用是让暖运行时判断失效，跟 Prompt 计划的哈希是一个道理。

Q33选了但不存在、被禁用、被删了，怎么办？
直接失败，不静默替换。

静默替换的诱惑很大：用户删了个技能，你悄悄给他换成同名的另一个版本，界面上一切正常。但 Agent 的行为会变，而且没人知道为什么变——这种 bug 的排查成本是最高的，因为你连「变了」都不知道。

所以我的策略是：选择指向的能力被禁用、删除、或者在镜像里根本不存在，这次配置就直接保存失败，让用户看到「这个技能不可用」。宁可让保存失败，也不要让运行时猜。
追问：那用户会觉得很难用吧？删个技能就保存不了。

所以我们把「引用检查」提前到编辑时：用户一删技能，界面上先把所有引用它的 Agent 列出来，让他先解绑再删。真正到保存时才失败的，是并发场景（他删的时候别人正在保存）。失败提示里带上是哪个 Agent 引用了它，一句话就能解决。

追问：「缺失即失败」会不会导致一个坏技能拖垮所有 Agent？

不会，因为失败的是那一个 Agent 的这一次配置提交，不是整个平台。而且它失败得很早——在写入之前，不是在运行的时候。运行时失败才是灾难，配置时失败只是麻烦。

Q34能力清单变了，正在跑的会话怎么办？
不能让旧运行时继续用旧清单，也不能粗暴杀掉正在跑的一轮。所以把变更当成一次事务：先暂停相关运行（暂停期间新消息标记待处理，不再拉起新运行）→ 提交变更 → 提交成功就丢弃旧运行里挂起的输入、用新清单起新运行；提交失败就恢复队列，让原运行继续。

用户主动停止和变更引起的停止要区分开：前者丢弃被中断的输入，后者必须保留待重放输入，因为用户没打算放弃那句话。这些状态都放在队列里显式表达，而不是靠「进程还在不在」来推断。
追问：那正在跑的那一轮，它的输出还算数吗？

算，但要标注。它用的是旧清单，输出会带旧清单的哈希；新运行起来之后，同一个会话的历史里会有「这段是旧能力下产生的」。这个标注不是洁癖——排查「为什么它昨天会用那个工具、今天不会了」的时候，这是唯一线索。

Q35有副作用的工具为什么必须回宿主执行？直接在运行体里发消息不行吗？
因为运行体里没有做产品决策所需的信息，也没有权限。

运行体知道的是「模型想干什么」；宿主知道的是「这个租户有没有配额、这个会话该投到哪个渠道的哪个话题、这条消息是不是重复的」。这些判断放在运行体里，等于把租户边界交给提示词去守。

所以工具分两类：纯计算的（读文件、搜代码、算东西）直接在运行体里执行；有外部副作用的（给用户发消息、排定时任务、写长期记忆、请求人工确认）走增量通道回宿主，宿主执行完把结果写回来。为了不重复执行，每个请求带一个由运行时实例和轮次派生的幂等键，宿主按这个键去重。
追问：一来一回不是慢吗？

慢几十毫秒，换来的是「不会发错地方、不会重复发、不会越过配额」。这类操作本来就是低频的（一轮最多几次），慢一点无所谓。真正高频的是读文件、搜代码，那些在运行体里做。

追问：工具的返回值模型能看懂吗？

能，因为我们把工具结果统一包装成文本或图片内容块，而不是让模型去猜一段 JSON 是什么意思。这个细节很小但影响很大——模型对「裸露的 JSON」经常理解错字段含义，包一层自然语言描述之后，工具调用的成功率会明显不同。

Q36宿主在执行工具副作用的时候挂了，运行体在等结果，怎么收场？
两边各有兜底。

运行体这侧：工具执行有超时和取消，收到中止信号就把失败返回给模型，模型下一轮自己决定重试还是换个做法，这一轮不会永久挂住。

宿主这侧：副作用请求和它的结果都落库，进程重启后能看到「这个请求发出去了但没有结果」。这时候不重放副作用，而是把状态标成不确定并要求核对——尤其是发消息这类外部可见的操作，重放的代价是用户收到两条。

这条规则在整个系统里是一致的：凡是外部可见的副作用，不确定态要显式表达。宁可让人看一眼，也不要自动重试两次。
追问：核对的人看到什么？

看到「哪个会话、什么操作、什么时候发起的、载荷哈希是什么」。他不需要看完整内容，只需要判断「这条消息对方收到没有」——去渠道后台看一眼就知道。所以核对界面设计的目标是「30 秒能判完」，不是「信息齐全」。

追问：能不能设计成幂等，就不用核对了？

能设计的都设计了（发消息带客户端消息 ID、写记忆带幂等键）。但外部系统不一定支持——很多 IM 平台的发送接口既不幂等也不支持按 ID 查询。这时候「不重放」是唯一安全的选择。

Q37MCP 工具怎么接进来的？参数校验做几次？
MCP 工具的 schema 和引擎要的 schema 不是一套，所以中间要做一次转换，而且校验做两次：入口按 schema 校验一次（挡住模型生成的畸形参数），实现层再校验一次（挡住调用方绕过入口直接调）。

命名空间也要处理：不同 MCP 服务可能有同名工具，注册时按「服务名 + 工具名」做命名空间，模型看到的是一个扁平的工具列表，但路由到具体服务时能唯一定位。

还有个坑：MCP 的 schema 允许一些引擎不支持的写法（比如联合类型、复杂 oneOf），转换时要降级成「宽松的 object + 运行时校验」，不能让模型因为 schema 太复杂而不敢调用。
追问：为什么校验两次？入口校验不够吗？

不够。入口校验挡的是模型，实现层校验挡的是「别的调用方」——比如内部脚本、定时任务、子代理。只有实现层的校验是真正的边界，入口的校验是「早点给出好错误」。

Q38你怎么知道某个运行是真卡住了，而不是在跑一个很长的工具？
用活动信号，不用「开始时间」。运行体每次有实际进展——收到模型增量、工具开始或结束、写出一条输出——都会更新活动时间戳；判定卡死看的是「距上次活动过了多久」，而不是「这轮跑了多久」。跑一个 5 分钟的长工具是正常的，5 分钟没有任何事件是不正常的。

还有一个我踩过的点：先挑候选，再重新校验一次才动手。因为在挑出候选到真正处理之间，运行可能刚好自己活过来了，这时候杀掉是纯粹的误伤。这个「候选 + 重校验」的模式在任何并发场景里都必要，单靠一次快照做决策迟早出错。
追问：活动时间戳怎么更新？运行体主动上报吗？

宿主侧根据收到的事件更新，不依赖运行体自报——自报的话，运行体卡死的时候恰恰不会上报。宿主收到任何一条流式事件就刷一次时间戳，这比心跳更真实。

追问：阈值多少？

按场景分：对话轮次比任务运行短，长工具的超时比普通工具长。但我不背具体秒数，因为它是配置项——重要的是判定逻辑（距上次活动），不是那个数字。

Q39「优雅收尾」具体怎么实现？为什么不直接杀？
直接杀会丢两样东西：正在流式输出的内容，以及运行体里那些还没确认的投递。

所以先走软路径：往增量目录写一个关闭哨兵，运行体在循环里会检查它，命中就中止当前回合、把未确认的消息写回、然后输出一个「已关闭」的终态退出。宿主看到这个终态就知道是正常关闭，不需要重试。

只有软路径超时、或者进程已经不响应了，才杀进程树。而且杀之前要把这一轮标成「运行体退出」而不是「用户停止」——这两种情况对后续输入的处理完全不同：用户停止要丢弃被中断的输入，异常退出要重新从库里读消息。
追问：哨兵文件为什么放在增量目录，不放别的地方？

因为增量目录本来就是运行体和宿主之间的通信通道，运行体每轮都会读它。放在这里不需要新增机制，也不会出现「哨兵被删了但进程没收到」的窗口。这是把新需求挂到已有通道上，比新开一个通道更可靠。

追问：软关闭要等多久？

几秒量级，够它把当前这一段输出完、把未确认消息写回。等太久等于没杀，等太短等于直接杀。这个值跟「一次工具调用最长多久」有关，我们按 P99 工具耗时定的。

Q40失败重试是有界退避，那一直失败呢？有哪些例外？
退避有上限、重试次数也有上限，到顶之后不再自动重试，把错误交回会话，让用户或上层看到明确原因。

但有四个例外必须单独处理：①上下文溢出不退避——等一会儿不会让上下文变小，直接重排并让运行时压缩；②用户刚点过停止的会话短时间内不重排，否则运行体会把自己重新拉起来，表现是「点了停止又自己开始干活」；③配置变更期间的失败不退避，因为原因是正在换运行时，等变更完成再重放才有意义；④新用户消息到来时取消旧的退避计时器，但保留重试计数——不然每次新消息成功一次就把连续异常洗白了，永远触发不了上限。
追问：为什么上下文溢出要跳过退避？

因为退避的前提是「等一等可能会好」，而这个错误等一等一定不会好。它的正确处置是「立刻重排 + 压缩」，让模型在一个更小的上下文里重跑。把它和网络错误走同一条重试路径，是最常见的错误设计。

追问：新消息保留重试计数，这个细节很多人想不到。怎么发现的？

线上发现的：有个会话一直失败，但每次失败之后用户又发了句「在吗」，新消息处理成功一次就把计数清零，于是它永远在「失败-清零-失败」的循环里，一次都没触发上限，也没报警。修完之后我们加了一条规则：只有一轮真正成功才清零，用户发新消息不算成功。

这个故事很值钱：它证明你不是照着文档实现，而是在线上被咬过
Q41流式卡片，进程崩了之后怎么接管？
先读卡片记录的当前状态，再决定是续写还是收尾，绝对不能直接新建——新建的后果是用户看到两张卡片，而且两张内容还不一样。

接管的顺序也有要求：先确定这一轮不会再产出新的出站消息，再把轮次标终态，否则会出现「轮次已失败但出站队列还在往里塞」。

卡片本身有节流：IM 的流式不是推流，是反复编辑同一条消息，编辑太频繁会被平台限流，所以要有最小编辑间隔，并且终态那次必须发（不能因为节流把最终内容吞掉）。
追问：怎么确定「不会再产出新的出站消息」？

看两个信号：运行体进程已经不在，且它的最后一条事件是终态（不是「正在输出」）。如果进程没了但最后一条事件不是终态，说明是异常退出，这时候要先把「可能还在路上的出站」按超时收敛，再标终态。

Q42记忆写入为什么要签名鉴权？运行体不就在你自己的进程里吗？
运行体是隔离环境里的进程，它拿到的是任务输入，不是数据库权限。如果让它直连库写记忆，等于把租户边界交给提示词去守——模型被诱导一下就能写别人的记忆。

所以写入走请求：宿主给这一轮下发一个实例标识和签名密钥，运行体提交变更请求时带签名和幂等键；宿主校验签名、校验租户归属，再按版本做乐观并发控制。

版本这块不能省：两个会话同时改同一条记忆，后写的如果直接覆盖，前一个 Agent 刚确认的事实就悄悄没了。删除也不是真删，是状态置为失效并留墓碑——召回不再命中，但审计还能回答「这条什么时候被谁作废的」。
追问：签名密钥怎么下发？不怕被模型读到吗？

密钥在运行体启动时通过输入通道下发，存在进程内存里，不写文件、不进提示词。模型能看到的只有工具描述，看不到密钥。这个边界要说清楚：运行体里的代码是可信的，运行体里的模型输出是不可信的。

L4评测与路由（黄区） · Q43–Q56

这 14 题是你和普通候选人的差距所在，也是最容易被追穿的地方。三条自保原则：只讲设计取舍、只讲指标口径、只讲一次复盘。被问到实现细节，就平移回这三样。

黄区答题模板（所有题都用这个骨架）：
① 为什么做：一个具体的痛点（模型选型靠感觉 / 降级靠拍脑袋）。
② 怎么做：三段话，不超过三个组件名（用例集、评测口径、路由策略）。
③ 指标口径：这个数怎么算的、分母是什么、取哪个时间窗。
④ 一次复盘：一个具体故障或一次判断错误 + 改了什么规则。
⑤ 收口：「这部分我负责设计和落地，代码是小组一起写的；模型侧我们只调 API，没有微调。」
Q43312 条用例是怎么来的？拍脑袋想的吗？
三个来源：真实会话抽样 60%——从线上抽高频问题，按意图聚类后每类抽若干条；运营专家出题 30%——他们知道哪些问题最容易答错，比如政策边界、跨平台规则差异；线上 badcase 回流 10%——每个投诉或纠错都固化成一条。

六类场景：政策问答 120、商品对比选品 60、广告复盘 48、多轮改单 36、工具调用 30、拒答边界 18。最后那 18 条是「不该答」的用例，很多人会漏掉这一类，但它恰恰是最容易出事故的——Agent 在该拒答的时候硬答，比答错更危险。
追问：为什么政策问答占这么多？

因为它占线上会话量的七成以上，而且它有标准答案，可判定性最好。用例集的分布应该跟着「流量 × 可判定性」走，不是跟着「哪个场景高级」走。

追问：用例会不会过时？

会，所以我们每季度做一次「用例审计」：连续三个月全过的用例降权（它已经不能区分模型了），连续失败的用例拆细（说明它太笼统）。用例集不是资产，是会腐烂的东西。

Q44用例是你写的，Prompt 也是你调的，这不就是自己出题自己考？
这个问题问得对，我们一开始就是这个毛病，所以后来做了三件事。

第一，作者分离：用例主要由运营和产品写，我负责「可判定性审查」——我只判断这条用例能不能被稳定判定，不改它的期望。改期望必须走他们。第二，冻结集：有一份 120 条的 golden 集，任何人不得因为「模型没过」去改它，只能新增；改它要三个人签字。第三，留出集：调 Prompt 的时候只用 192 条，最后 120 条 golden 只在发布前跑一次。相当于给自己留了个不参与调参的考卷。
追问：120 条够做留出集吗？

统计上不够严谨，我不装。它的作用不是给出置信区间，是防止「我把答案背下来了」这种自欺。真要严谨的做法是每次抽样轮换，我们做不到那么高的标注成本，所以选择了「冻结 + 不参与调参」这个折中。

别说「我们用了 K-fold 交叉验证」——那是有监督学习的说法，套在 Prompt 调优上会被追问细节，一问就穿。
Q45七个维度具体怎么打分？谁来打？
分两类，不混着打。

确定性维度（工具调用、指令遵循、稳定性）：代码判。比如「有没有调用订单查询工具」「返回里有没有出现不该出现的字段」「同一输入跑五次结果是否一致」，这些是断言，不打分。

语义维度（任务完成度、事实与证据准确性）：先人工标 120 条建 rubric，再让 judge 批量跑。rubric 是三级——不合格、合格、优秀，每一级都带「什么样的回答算这一级」的具体描述，不给描述的打分一律作废。

时延和 token 成本是采集出来的，不是打出来的，直接从 trace 里取。
追问：为什么语义维度不让人工全标？

312 条 × 5 个模型 = 1560 次判断，人工标不完，而且人会疲劳、标准会漂。人工的价值在「定标准」，不在「执行标准」。所以我用人工标 120 条来校准 judge，剩下的交给 judge 批量跑，并且定期抽查 judge 和人工的一致率。

Q46LLM-as-judge 的偏差你怎么控？
三个已知偏差，各有对策。

位置偏差（偏向先出现的那个）：对比两个回答时交换 A/B 顺序各跑一次，结论不一致就记为「平」。长度/啰嗦偏差（偏爱长回答）：rubric 里明确写「冗余不构成加分，关键事实缺失构成扣分」，并在 judge 的提示里要求先列证据再打分。自我偏好（偏爱自己家的模型）：judge 不用被测的五个模型，用一个不在候选池里的模型，并且允许它输出「无法判断」。
追问：「无法判断」会不会被滥用？

会，所以我们监控它的比例。超过一定比例说明 rubric 写得不清楚，或者用例本身不可判定——这两种都是要修用例，不是修 judge。

追问：judge 自己也会错，你怎么知道它错在哪？

靠那 120 条人工校准集：算一致率，并且看混淆矩阵——是「把不合格判成合格」多，还是反过来。前者危险（会放过坏模型），后者只是保守（会误杀好模型）。方向不一样，处理方式也不一样。

Q47κ=0.71 这个一致率，算可用吗？
在「三级 rubric + 语义判断」这个任务上，0.71 属于「substantial agreement」，可用但不完美，我的用法是只看相对排序，不看绝对分。

具体说：模型 A 比模型 B 高 3 分，这个结论可信；模型 A 得了 78 分，这个数字不可信。因为 judge 的系统性偏差在两个模型之间是抵消的，绝对分不是。

所以我们的报告里，矩阵给的是排序和「分档」（比如第一档、第二档），不给小数点后两位。给小数会让人误以为有精度。
追问：那怎么知道 0.71 不是算错了？

用混淆矩阵看分歧集中在哪。我们的分歧主要在「合格 vs 优秀」这一档——也就是「答对了但答得好不好」这种主观判断上；「不合格 vs 合格」这一档一致率明显更高，而这一档才是决定能不能上线的。所以这个 κ 对我们的决策影响没那么大。

可直接背：看相对排序，不看绝对分；分档不给小数；分歧集中在「好」而不是「对不对」
Q48五个模型横向比，怎么保证公平？
四件事固定住才算公平：同一份 Prompt（不做模型特调，特调就没法比）、同一组工具（同样的 schema 和返回格式）、同一批用例和同一套 rubric、同一时间窗（避免供应商当天限流或降级影响）。

温度这类参数我会说明：主要用低温度跑（追求可复现），但每个模型跑三次取中位数，不取最优——取最优等于给方差大的模型加分。
追问：不同模型的上下文窗口不一样，长用例怎么办？

长用例单独一组，只比能装下的模型，短用例那组全员参与。硬把长用例塞进小窗口的模型，等于用截断惩罚它，结论会失真。报告里两组分开列。

追问：那价格差异怎么算进去？

价格不混进能力分，单独一列「单次任务成本」——因为「贵 3 倍但好 3 分」这种结论，不同岗位的答案是不一样的，让看报告的人自己判断，而不是我替他加权。这也是后来把成本权重从 10 降到 5 的原因。

Q49「岗位 × 模型适用性矩阵」，给我一个具体结论。
举两个，都是当时真实影响过配置的。

客服岗位：以政策问答为主，GLM 在「事实与证据」上只比 GPT 低 3 分左右，但单次成本大约是四分之一，时延也更低 → 定为主模型，GPT 做 fallback。这个决定直接把单店成本从 ¥200 压到 ¥120 附近。

选品岗位：要跨站比价 + 长上下文读详情页，Kimi 的长文稳定性明显更好，DeepSeek 在中文商品描述上更强但长文截断多 → 主 Kimi，关键比对走两条并行再交叉验证。

广告复盘：这一块所有模型都不够好，因为要算数。结论是「不靠模型算，让它调工具算」——这条结论比选哪个模型有价值得多。
追问：为什么广告复盘要工具算？模型不是能做算术吗？

能做，但不可靠，而且错得很隐蔽——它会把 3.2% 和 3.5% 说反。我们的做法是把 ACOS、ROAS 这类计算全部下沉成工具，模型只负责「决定查哪个时间段、怎么解释结果」。这个改动之后，广告复盘的事实性错误基本清零。

这个结论很加分：它说明你懂「模型能力边界」，而不是把什么都交给模型
Q50你说成本权重从 10 降到 5，为什么？
因为发现它把结论带偏了。原来成本占 10 分，结果一个模型只要便宜，总分就能排前面，哪怕它在「事实准确性」上明显差——而客服岗位答错政策的代价，远大于省下来的那点钱。

降到 5 之后，成本从「决定排名的因素」变成「同档位之间的决胜因素」。这个调整是运营提的，我一开始不同意，后来用两组数据说服了自己：一次政策答错带来的客诉处理成本，是 token 成本的上百倍。
追问：那为什么不干脆去掉成本维度？

因为它是真实约束。完全不看成本，结论会变成「全都用最贵的」，那这个评测就没有落地价值了。评测的目的是选型，不是排名。

Q51ProviderPool 怎么判断一个供应商「挂了」？
两个信号，任一满足就打开熔断：滚动 5 分钟错误率超过 20%，或者 P95 时延超过阈值（按岗位不同，客服 25 秒）。然后进入半开：30 秒后放少量真实流量试探，成功就恢复，失败就继续熔断。

不只看 5xx——限流 429 和「返回了但内容是空的」也算失败。后者最坑，因为它不报错，只在评测和用户投诉里体现。
追问：为什么是 20% 不是 5%？

5% 太敏感，正常波动就会误切——切换本身有成本（时延上升、风格变化），切来切去比不切更糟。20% 是我们观察到「用户能明显感知到变差」的量级。这个数不是理论值，是调出来的。

追问：滚动窗口为什么是 5 分钟？

1 分钟样本太少，容易误判；15 分钟反应太慢，用户已经难受完了。5 分钟大约几百次调用，够判。这三个数字（20%、5 分钟、30 秒）建议一起背，它们是成套的。

Q52三级降级链具体是什么？降到最后一档是什么？
第一档主模型（按岗位配）；第二档备用模型（能力接近、不同供应商，避免同一家全挂）；第三档是小模型 + 收窄能力 + 转人工——注意第三档不是「更便宜的模型」，是「更保守的行为模式」。

降到第三档时同时做四件事：收窄工具白名单（禁写操作）、强制输出带引用、命中高风险意图直接转人工、把所有回答标记「降级模式」。

核心判断是：降级不是换个模型继续跑，是换个模型 + 降权限 + 加复核。
追问：为什么不设第四档「直接报错」？

因为报错也是一种服务，而且是最差的那种。用户宁可拿到一个保守但正确的回答，也不想看到「系统繁忙」。但如果第三档也挂了，那就只能报错——这时候错的是整个系统，不是某个供应商。

追问：切到备用模型，历史对话风格会跳变，用户不觉得奇怪吗？

会觉得，所以我们不在会话中途切——只在「新一轮开始」时切，并且如果这个会话之前是主模型，会补一句轻量的衔接（比如「我换个方式帮你确认」）。中途切是最糟的：同一段对话里两种语气，用户会以为换人了。

这句是全场最值钱的一句：降级 = 换模型 + 降权限 + 加复核，不是换模型继续跑
Q53降级之后质量下降了，谁负责？
分三层，责任是明确的。

系统层负责「不要更糟」：降级时收窄权限、强制引用，把「可能出错」的操作挡掉。业务层负责「可接受」：降级模式下高风险意图直接转人工，这个人力的成本是产品提前认过的。监控层负责「看得见」：降级期间的成功率、转人工率、投诉率单独看板，不和正常时段混在一起算平均值——混在一起就永远发现不了降级的影响。
追问：那降级期间的用户体验，你们有指标吗？

有，主要看「转人工率」和「同一会话的追问次数」。降级期间这两个都会涨，涨多少是可以接受的，是产品定的阈值。超过阈值就说明这次降级不该继续，应该考虑直接暂停服务并告警。

Q54路由策略是规则还是学习出来的？
规则，而且我坚持用规则。

路由的输入是三个东西：岗位（客服/选品/广告）、意图类别（前置分类器给的，比如「政策问答」「比价」「算数」）、实时状态（这个供应商现在熔断没有、这个租户的配额还剩多少）。输出是模型 + 参数。这是一张可读的表，不是模型。

为什么不做学习：路由错了的代价不对称——把简单问题路由到贵模型只是浪费钱，把复杂问题路由到弱模型是答错。而且规则可解释，出问题能改；学出来的策略出问题，你只能重训。
追问：那前置分类器自己错了呢？

会错，所以设了兜底：分类置信度低于阈值就走主模型（贵的那条），不走便宜的那条。宁可多花钱，不要错答。这个兜底逻辑本身也是规则。

Q55讲一次真实的降级，从触发到恢复。
有一次主力供应商区域抖动，不是完全挂，是成功率掉到 60% 左右、时延翻倍。5 分钟窗口的错误率摸到 30%，熔断打开，流量切到备用。

切过去之后发生两件事：一是时延从 1.8 秒涨到 2.4 秒左右（备用模型首字慢），二是备用模型在「多轮改单」这类场景上明显不如主模型，改单成功率掉了。所以我们中途做了一次收窄：把改单相关的意图直接转人工，而不是继续用备用模型硬扛。

恢复是半小时后，半开试探成功、逐步放量回来的。事后的结论是：降级链要按「能力维度」设计，不能按「供应商」设计——备用模型不是主模型的等价替代，它在某些能力上是断崖式的。
追问：这半小时里，用户知道自己在被降级服务吗？

不知道，我们没做「系统繁忙」的提示，因为那会造成更大的恐慌。但内部看板上有标记，客服侧能看到「这个时段是降级模式」，遇到投诉知道怎么解释。对外不透明度，对内全透明。

复盘结论可以直接背：降级链按能力维度设计，不按供应商设计
Q56Benchmark 分数涨了，怎么证明线上真的变好了？
两件事分开看：Benchmark 证明「没变差」，线上指标证明「变好了」。

Benchmark 的作用是门禁——它防的是回归，不是证明提升。真正的提升要看线上：转人工率、追问次数、投诉率、处理时长。我们做过的对照是「同一批店铺、前后两周」的对比，不是严格的 A/B（多店铺场景做 A/B 很难，因为店铺之间差异太大）。

所以我给结论时会很小心：「转人工率从 45% 到 27%」这个数，我能保证口径是对的（分母是会话数、取稳态周），但我不声称它 100% 归因于 Agent 的改动——同期还有运营侧的流程调整。
追问：那你怎么区分两者的贡献？

区分不了，我不装。我能做的是把「同期还发生了什么」列出来，让听的人自己判断。面试里我也这么说——过度归因比不归因更容易被识破。

绝对不要说「我们做了严格的 A/B 测试，p<0.05」——多店铺场景做不了干净 A/B，这句话会引来一串方法学追问。

追问：那你怎么解释简历上写「设计」？

简历上写的是我负责的模块，模块内的设计确实是我做的。但一个模块能上线，靠的是团队——这句话我在任何场合都会说。

别说「你可以去背调」「你可以问我前同事」——这听起来像威胁，而且他真去问你更麻烦。
Q58有代码吗？能看一下吗？/ 有 demo 吗？
公司代码在内网，离职时没有带走，这个我确实拿不出来——如果我说能给你看，你反而该怀疑。

我能做的是两件事：一是白板画链路，从消息进来怎么落库、怎么排队、怎么拉起运行体、事件怎么回传，我可以画到字段级；二是讲一个具体的 bug，包括当时怎么定位、改了什么。这两件事编不出来，你听完自己判断。
如果他坚持要看：

「那我给你看一个我自己在业余时间按同样思路写的最小实现，它只有几百行，但把「计划 → 能力清单 → 工具回宿主」这条链跑通了。它不是公司代码，功能差很远，但机制是同构的。」——只有在你真的有这个东西、并且能讲清每一行的时候才说这句；否则不要说。

绝对不要现场打开一个 GitHub 仓库说「这是我写的」，除非你能回答里面每一个设计选择的追问。这是最容易当场翻车的一步。
Q59你说的这些，听着像看了文档背下来的。
那我说一个不像文档的东西。

我们有个会话一直失败，但永远触发不了重试上限。查了两天才发现：每次失败之后用户会发一句「在吗」，新消息处理成功一次就把连续失败计数清零了，于是它永远在「失败 → 清零 → 失败」的循环里。

修法是：只有一轮真正成功才清零，用户发新消息不算成功。这个 bug 文档里不会写，因为它不优雅，甚至有点蠢——但它是我在凌晨两点坐在工位上想明白的。
这就是「反文档细节」的作用：所有靠谱的项目都有一个蠢 bug，讲它比讲架构更能证明你在场
Q60为什么只干了 8 个月就走了？
不是被动离开。慧贸让我把「交易侧」的 Agent 跑通了——多店铺、多岗位、模型选型和降级。但做到后面我发现，团队的重心在往「重运营轻平台」走：需求越来越多是运营工具，平台侧的投入在收缩。

而我想继续做的是 Agent 基建——上下文、评测、可靠性这些。所以我主动换到了工业侧，去做设备诊断，那边的难点在异构数据和人机协同审批，是同一个问题的另一面。

我给自己定的路径是：两年内把 To B Agent 的交易侧和生产侧各跑通一遍。
追问：那你怎么保证下一份不会又干 8 个月？

看两件事：这个岗位是不是在做平台而不是在做需求；团队里有没有人比我更懂这一层。第一个决定我有没有事做，第二个决定我能不能长。这两条我现在会先问清楚再决定去不去——这也是我为什么想问你（转向反问）。

别说「公司不行 / 领导不行 / 加班太多」——任何对前雇主的负面评价都会被记一笔，哪怕你说得对。
Q61你才一年多的经验，JD 写两年以上，我凭什么信你能独立扛？
年限我确实差几个月，这个我不辩解。我用交付密度换：14 个月里 3 个生产级 Agent 系统，每个都带评测、降级和回归门禁——这三样东西很多做了三年的人也没完整做过一遍。

「独立扛」如果指「从需求到上线」，数字员工平台的 Agent 编排层是我从 0 设计的；如果指「带人」，我只带过一个实习生，这块我不夸大。

另外我有个习惯可能比年限有用：我做的每个东西都会留一个「怎么验证它对」的方案。这个东西不太好教，但它决定了我能不能独立。
追问：那如果让你带两个人做新项目，你第一周干什么？

先定三件事：验收标准（什么算做完）、观测口径（上线后看哪三个数）、边界（哪些不做）。这三件事定不下来，人就越多越乱。第一周我不会写代码，我会写一页纸把这三件事说清楚，然后找人吵一架。

Q62这套东西，用 Dify / Coze / LangGraph 不就行了吗？为什么要自己写？
如果只是搭个 demo 或者内部工具，用 Dify 更快，这个我承认。

我们自己做，是因为三个需求那些平台给不了：一是自托管 + 多租户，客户要求 Agent 跑在自己服务器上、数据不出域；二是工位，Agent 要能读写工作区文件、按工作区隔离能力；三是交付到组织现有的 IM，而且要处理投递可靠性——超时了到底发出去没有，这个问题没有现成答案。

另外还有一个隐性原因：我们需要能改。评测、路由、降级这些东西，用别人的平台只能调参数，改不了机制。
追问：那 LangGraph 呢？它就是做编排的。

LangGraph 解决的是「把任务编排成图」，我们解决的是「Agent 长期待在一个组织里」。我们的工作流是写在提示词里的规则，不是可执行的图——这是刻意的，因为业务要改流程时不该发版。真要跑复杂 DAG，我会用它，而不是自己写。

诚实感来自这句：「如果只是搭 demo，用 Dify 更快」——承认工具适用边界的人，才像真的选过型
Q63你做的这些，业务真的需要吗？还是技术自嗨？
有一部分确实是自嗨，我说实话。

比如插件体系——做了 manifest、依赖检查、物化，其实到我们离开也没几个真插件，因为客户不会写。这部分投入产出比很差。

但另外三块业务是真的需要：强制引用（客服主管那句「答得对但我不敢用」）、降级（供应商抖动时业务不能停）、成本（单店从 ¥200 到 ¥120，这个是财务看得见的）。判断标准很简单：这块东西如果拿掉，业务会不会立刻疼。会疼的就是需要，不会疼的就是自嗨。
追问：那你怎么避免下次再做自嗨的东西？

先找一个「疼的人」。如果找不到具体的人为这件事疼，就先别做。插件体系那次就是没有疼的人，是我觉得「平台应该有插件」。

主动承认一块自嗨，比全程完美可信十倍——而且他接下来会放松对你的追问
Q64如果现在让你重做，技术栈会怎么选？
保留三个决定，换掉两个。

保留：SQLite 起步（单机自托管场景够用，运维成本几乎为零，后面要换再说）；TypeScript 全栈（前后端共享类型，流式事件那份真相源能直接复用）；进程隔离跑 Agent（这个决定我至今觉得是对的）。

换掉：一是把「配置变更」从散落在各处的写接口收口成一个带事务语义的统一入口，这个当初就没设计好；二是记忆那块我会一开始就留一个向量检索的插槽，哪怕先不用——现在想加要动表结构。
追问：SQLite 能撑住多租户吗？

自托管场景能，因为每个客户一台机器、几百个会话。但如果是 SaaS 多租户集中部署，就要换 Postgres——不是因为性能，是因为并发写和行级权限。选型要看部署形态，不能一概而论。

Q65你觉得自己最大的短板是什么？
两个，一个技术一个非技术。

技术上：我没做过高并发下的分布式系统。我们那个平台单机跑几百个会话，压力主要来自模型时延不是来自 QPS，所以我对「真正的分布式一致性」只有书本知识——像 Raft、分片、跨机房，我能讲原理，没在生产上处理过。

非技术上：我容易过早进入实现。有一次产品还在讨论需求，我已经把表结构画完了，结果方向变了，白干两天。现在我会强迫自己先写一页纸的验收标准再动手。
追问：那高并发这块你打算怎么补？

先在这个岗位的真实场景里补，而不是先去啃论文。如果团队有高并发的问题，我想参与排查而不是旁观——分布式这东西，看十篇文章不如跟着排一次故障。

别说「我的缺点是太追求完美 / 太拼」——这是最老套的假答案，会被当场识破并降低整体可信度。
Q66另一个候选人做过更大规模的系统，我为什么选你？
规模上我比不了，这个我不争。

我的差异在两点：一是我是从 0 到 1 做的，所有坑都是我自己踩的，所以我知道每个设计为什么长这样，而不只是知道它长这样；二是我做的每个东西都带评测——我习惯先想「怎么知道它对」，这个习惯在大团队里容易被流程替代掉，在小团队里是刚需。

如果这个岗位需要的是「把已有系统维护好、扛住规模」，他比我合适；如果需要「把一个新的 Agent 场景从 0 跑通、并且能说清它到底行不行」，我更合适。
为什么这样答有效：

你把选择权交回给他，同时精确地定义了自己的适用场景。这比「我学习能力强」有说服力得多。

不要说任何贬低另一个候选人的话，哪怕暗示也不行。
Q67期望薪资多少？
我现在是 __，期望 25–28，主要看岗位空间。如果架构和落地权限给得足，24 以上我可以马上定。

（如果被压）我理解预算有区间。如果 base 到不了，我想聊聊另外两件事：一是这个岗位半年后大概能做到什么程度，二是有没有机会参与到评测/基建这一层——这两件对我来说比多两千块重要。
三条纪律：

① 先给区间再给条件，不要先报死数；② 不要用「我值这个价」这种自我评价，用「我现在的数 + 市场区间」；③ 不要在没有 offer 的时候主动降，降一次后面每次都会降。

Q68你还有什么问题问我？
三个，按重要性：

① 这个岗位现在最让你不满意的是哪一块——是效果、稳定性还是成本？
② 团队现在有没有评测和回归机制？如果没有，是优先级问题还是没人做？
③ 我进来后前三个月，你最希望我交付的一个东西是什么？
为什么问这三个：

第一个让他暴露真实痛点（你后面可以顺势说「这块我做过类似的」）；第二个探团队成熟度（也暗示你重视评测）；第三个把对话从「面试」变成「入职规划」。

不要问「团队氛围怎么样」「加不加班」「有没有年终奖」——这些留到 HR 面，技术面问会显得你关心的是别的东西。

L6失败与反思 · Q69–Q74

这一层决定你是「能用的人」还是「可信的人」。技巧只有一个：失败要具体，反思要落到规则上——「我以后会更仔细」是废话，「我加了一条硬规则」是能力。

Q69最大的一次线上事故是什么？
上线第 5 周，一次客服岗位模板的批量改配置，没走运行时暂停。结果 3 家店铺在切换窗口里同时加载了新旧两份人格，表现是同一个客服在两句话之间口吻跳变。

排查花了 40 分钟，原因很讽刺：日志里两个版本的 Prompt hash 都在，正因为两个都在，才看不出哪个该生效。

根因是配置提交和运行时替换不是一个事务，我漏了暂停这一环。改了两处：流程上，能力和人格变更统一收口到一个带暂停令牌的事务接口，暂停期间新消息标待处理，提交成功才丢旧输入换新运行时，失败恢复队列；观测上，把 Prompt 版本 hash 和计划 hash 写进每轮 trace，让「这轮用的哪版人格」变成可查字段。
追问：影响面多大？怎么善后的？

3 家店铺、大约 40 分钟的会话受影响，没有造成资损，但有 2 个客诉。善后是逐个会话回看、给受影响的对话补了人工说明。真正让我难受的不是这 40 分钟，是「我们居然没有能力在 5 分钟内定位」。

这个故事的三段结构：现象（用户视角）→ 根因（一句技术话）→ 规则（改了什么硬约束）
Q70有没有一个技术决策，你后来发现自己判断错了？
有，全局并发池。

早期我给所有会话加了一个全局并发上限，觉得「资源有限就该限流」，很合理。结果一个空闲但没超时的暖会话能把别人的消息卡住整整一个空闲超时周期——用户感知是「系统卡了」，其实是「有人在占着位置不干活」。

后来改成按序列化键串行、跨会话不设应用层池，容量交给容器上限和计费上限。这件事教会我的是：并发控制的粒度选错，比并发数设错更致命。设错数字只是慢一点，粒度选错会造出一类你根本想不到的故障。
追问：那怎么避免再犯这类错？

现在我会问自己一句：「这个限制的持有者，和真正消耗资源的，是不是同一个东西？」如果不是，这个限制就会变成阻塞而不是保护。

Q71和产品/运营吵过架吗？怎么解决的？
吵过，最凶的一次是「先做隔离还是先做功能」。

产品要先把三个岗位都铺上去，因为客户在等；我坚持先把多店铺隔离做完，理由是多店铺产品的第一条生死线是「A 店的数据不能出现在 B 店」，这个留到后面补，所有查询接口都要返工。

最后我们各让一步：先给两个店铺试用，同时我给出一个明确的判断标准——「串一次数据就停项目」。这句话把争论从「谁对」变成了「什么条件下谁对」，讨论就结束了。

我的收获是：跟产品争论，不要争「重要性」，要争「失效条件」。重要性是主观的，失效条件是客观的。
这句可以直接背：不要争重要性，要争失效条件
Q72有没有做过但最后被砍掉的东西？
有，插件体系。

我做了 manifest、依赖检查、物化、展开，做的时候觉得这是平台化的必经之路。结果到离开也没几个真插件——客户不会写，内部也没人有动力写。

现在回头看，问题不在技术，在我把「平台应该有插件」当成了需求。真正的需求是「客户想要一个我们没做的能力」，那这件事的正确解法是「我们自己做，或者开放一个最小的接口」，而不是先建一套插件生态。

这件事之后我有个习惯：做任何平台化的东西之前，先问「谁会在上面写东西，他现在在哪」。
Q73给你三个月和两个人，你会做什么？
在你们这个业务里，我会按这个顺序：

第一个月：不写新功能，先把「看得见」做出来——把现有的关键链路加 trace 和三个核心指标（成功率、转人工率、单次成本），因为不知道现在什么样，后面所有改动都是猜。
第二个月：挑一个最高频、最可判定的场景做深（通常是客服政策问答这一类），把它做到「敢上线、能量化」，同时把那套评测沉淀下来。
第三个月：把第一个场景里可复用的部分抽出来——能力清单、工具接入、评测集——变成第二个场景能直接用的东西。

我不会一上来做平台，因为平台是结果不是起点。
追问：为什么不先做架构升级？

因为架构问题一般是「跑不动了」才成为问题。没跑起来之前升级架构，等于在猜未来。而且架构升级最难的部分不是技术，是说服别人接受一次没有新功能的三个月。

Q74这个项目教会你最重要的一件事是什么？
配置即行为。

在传统系统里，改配置是改参数；在 Agent 系统里，改一句 Prompt 就是改行为——它会改变 Agent 怎么说话、怎么选择工具、什么时候转人工。所以配置必须有提交语义：有版本、有暂停、有回滚、有回归用例。我那次人格串味的事故，本质是我把它当成了「改文案」。

这个判断后来一直跟着我。做工业诊断的时候，把「复位、改参数」放进人工审批，其实是同一句话在另一个场景的延伸：凡是会改变系统行为的东西，都要有提交语义和回滚路径。
收尾金句：配置即行为；会改变行为的东西，都要有提交语义和回滚路径

05五份 JD 的差异化追问

同一个项目，对着五个岗位要讲成五个不同的故事。下面只写「差异部分」——共性内容回去用 L1–L6。

① 智能体工程师（对接 MES / AMS / ERP / OA，Hadoop / 爬虫 / Django）

项做法
讲什么把重点放在「Skills 沉淀」和「工具面治理」：四段 Prompt、能力清单、MCP 工具接入、副作用回宿主、权限与日志审计。这家 JD 几乎逐字对应你的项目，不要跑偏去讲 Benchmark。
钩子句「你们要把 MES/ERP 的能力沉淀成可复用的 Skill，这件事我在数字员工平台里做过一遍：难点不在接工具，在接完之后怎么保证 Agent 只拿到该拿的那几个。」
必被问「Hadoop 生态熟吗？」→ 诚实：没在生产用过，数据侧我只到 SQL 和全文检索；「爬虫呢？」→ 写过，但不是主力，反爬和调度没深做。
别说别说「ERP 我懂」——你没做过 ERP 实施，一追问业务流程就穿。说「我做过把企业系统能力封装成工具，业务域可以学」。

② 跨境电商 AI 应用（亚马逊 / 沃尔玛 / Wayfair / HomeDepot）

项做法
讲什么重点换成业务视角：三个岗位怎么抽象、政策口径怎么统一、Listing 怎么保证参数准确、成本怎么算。少讲队列和投递，多讲「哪个环节省了多少钱/多少人」。
钩子句「我做过三个岗位的数字员工：客服、选品、广告。最难的其实不是模型，是政策口径统一——同一个退货问题，五个店铺五个说法，Agent 只是把这个混乱放大了。」
必被问「ACOS 和 ROAS 什么关系？」「FBA 和 FBM 的区别？」「Listing 生成怎么保证参数不编？」→ 前两个背术语表，第三个答：参数来自 ERP 商品表做断言校验，不靠模型自觉。
别说别说「我不懂业务，我是做技术的」——这个岗位一半的分在业务理解上。

③ AI Agent 工程师（Java / ERP / 分布式 / MES / LangChain）

项做法
讲什么重点放在架构与框架对照：三层模型、上下文管理、记忆机制、任务分解。主动做映射：「我们的 Prompt 计划 ≈ LangChain 的 prompt template + 预算控制，但我们把每块做成可审计的对象」。
钩子句「LangChain 解决的是『怎么拼起来』，我们解决的是『拼起来之后怎么知道它是对的』——所以我把上下文做成了计划、把能力做成了清单。」
必被问「LangChain / LlamaIndex 用过吗？」→ 诚实分层：LCEL 和 Retriever 用过，生产上我们没套框架是因为要控预算和审计；「Java 呢？」→ 能读能改，没主导过 Spring 微服务（见 L5-Q61 话术）。
别说别说「框架都是玩具，我们自己写」——会被认为不懂协作。

④ ai应用开发工程师（游戏后端 / Nodejs / PyTorch / WebSocket）

项做法
讲什么重点放在进程与实时性：运行体进程、IPC、流式事件、并发控制、幂等投递。这些和游戏后端的「房间/帧同步/断线重连」是同一类问题，主动建立类比。
钩子句「我们那个运行体其实很像一个游戏房间：一个逻辑会话一个进程，串行推进，中途能接新指令，断线了要能恢复，超时要能优雅收掉。」
必被问「WebSocket 熟吗？」→ 熟，我们前端推流就是 WS，处理过重连和消息乱序；「PyTorch 呢？」→ 只到能读能改推理脚本，没训过模型。
别说别说「游戏后端我没做过」就停了——补一句「但状态同步和幂等这类问题我处理过」。

⑤ AI应用开发 00268（Java 基础 / 数据结构 / OS / 网络 / 数据库）

06白板题 W1–W5

白板不是画得好看，是边画边说话。每道题的第一句话决定他信不信你。

W1 画一次运行的完整链路

第一句：「我先画主干，再补两个分支——失败和中断。」
画：渠道 / Web → 准入与租户校验 → 入站落库 → 租约领取 → 序列化键队列 → 运行体（stdin 输入 / 增量目录 / stdout 事件）→ 会话 + 计划 + 能力清单 + 工具 → 事件回宿主 → 落库 + 投递 → 幂等收尾。
补两个分支：①失败（有界退避，四个例外）；②中断（软关闭哨兵 → 杀进程树，标记「运行体退出」而非「用户停止」）。
坑：别一上来画数据库表。先画流向，他要细节会问。

W2 画三层模型与隔离边界

第一句：「三层不是分层架构，是三种生命周期。」
画：Profile（配置，月级）× Workspace（边界，客户级）→ Session（运行时，分钟级）；右边竖着画四条隔离线：文件、数据、能力、上下文。
加一句：「这四条线里，能力那条最容易漏——因为工具是运行体去调的，很多人忘了在解析阶段就按 workspace 裁剪。」
坑：别把 Profile 画成「提示词模板」，它是身份 + 能力策略 + 版本。

W3 设计「配置变更」的事务

第一句：「这个问题的本质是：外部只能看到旧配置的完整行为，或者新配置的完整行为。」
画：暂停（暂停令牌 + 新消息待处理）→ 提交（写库 + 版本号）→ 收敛（成功：丢旧输入、起新运行；失败：恢复队列）。旁边画一个状态机：运行中 / 暂停中 / 收敛中 / 已恢复。
补一句：「用户主动停止和变更引起的停止必须分开，输入的去留不一样。」
坑：别说「重启一下就好了」——那是最容易被否的一句。

W4 设计「投递状态机」

第一句：「先承认一件事：IM 的超时是有歧义的，所以状态里必须有一个『不确定』。」
画：入站（落库 → 领取 → 续约）→ 轮次（心跳 → 终态）→ 出站（上传 → 发送 → 确认 / 不确定 / 人工对账）→ 卡片（创建 → 编辑节流 → 终态）。
加一句：「不确定态不是失败，它要求核对；自动重发的代价是用户收到两条。」
坑：别画成「重试三次」——那说明你没理解问题。

W5 设计「模型路由与降级」

第一句：「降级不是换模型继续跑，是换模型 + 降权限 + 加复核。」
画：输入（岗位 / 意图 / 实时状态）→ 路由表（规则）→ 主模型 → 熔断（5 分钟 20%）→ 半开（30 秒）→ 备用 → 第三档（小模型 + 收窄白名单 + 转人工）。
加一句：「切换只在新一轮开始时做，不在会话中途做，否则同一段对话两种语气。」
坑：别画成「按价格排序选模型」。

07不会答时的止损三段式

被问到你真的不会的东西，唯一的正确动作是承认 + 推理 + 平移。三句话，90 秒，脸不红。

场景三段式
问到你没做过的技术（如 K8s、Kafka、Flink）「这块我没在生产上用过（承认）。我理解它解决的是 __，如果我要用，我会先看 __（推理）。我在项目里处理过类似的问题是 __，思路可能可以迁移（平移）。」
问到你项目里的空白（如「你们怎么做灰度」）「灰度我们做得比较糙，是按店铺分批的，没有流量比例灰度（承认）。真要做的话得先解决会话粘性问题——同一个会话不能一半新一半旧（推理）。我们当时用暂停 + 全量切换绕过了这个，代价是有个几十秒的窗口（平移）。」
问到数字，你没有「精确数我没有，因为 __（口径原因）。我能给的是量级 / 口径 / 趋势（给替代）。如果这个数对这个判断很关键，我回去可以查一下（收口）。」
问到一个你完全没听过的名词「这个我没听过（承认）。听起来像是 __ 这一类的东西？（推理）你可以说一下它主要解决什么，我看看和我做过的哪块像（平移）。」
三个绝对不能做的动作：①硬编一个答案（追问两层就崩，而且崩了之后你前面说的全部打折）；②沉默超过 5 秒（他会以为你在搜答案）；③把问题反问回去（「你们是怎么做的？」在没有给出自己判断之前，是逃避）。

10与项目二 / 三的衔接

三个项目必须是一条线，不是三件事。串线的那根绳是：Agent 从「能答」到「能干活」再到「干错有代价」。

主线叙事（一句话版）

项目一（交易侧）：让 Agent 能在一个组织里长期干活——身份、工位、能力、投递。
项目二（生产侧）：让 Agent 干错之前停下来——证据、审批、收敛、可回放。
项目三（自研）：把这两件事的公共部分抽出来——工具契约、执行内核、队列与对账。
所以跳槽不是换方向，是把同一件事做深一层。

一致性检查（三个项目之间不能打架）

检查点必须一致的说法
你的角色三个项目都是「Agent 应用开发 / 编排层」，不是「算法」，不是「架构师」
技术栈Python + TypeScript 为主，Java 只到能读能改；三个项目都别出现你没写过的语言
方法论的连续性项目一「配置即行为」，项目二「行为要有审批和回放」，项目三「行为要有幂等和对账」——同一句话的三次展开
失败叙事的递进项目一漏了暂停 → 项目二把高风险操作前置审批 → 项目三把副作用做成对账状态
