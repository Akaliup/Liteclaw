# C07 流式事件契约与三段同步

> 课程性质：核心
> 返回：[导学](../导学.md)；前置：[C06 会话串行队列与 Runner 生命周期](./C06-会话串行队列与-runner-生命周期.md)；下一课：[C08 渠道可靠投递状态机](./C08-渠道可靠投递状态机.md)
> 对应：B5；见 [面经](../面经.md)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

场景：一个 Agent 正在回答，Web 页面上主文本在逐字出现，思考过程折叠在细节面板，工具调用一条条冒出又完结；同一时刻飞书里那张卡片也在更新。如果这两边看到的内容不一样，或者重连之后历史里多出一条重复的回复，用户对「这个 Agent 到底说了什么」的信任就没了。

四个结论：

1. 流式事件只有一份真相源，构建期复制到宿主、Runner、前端三处；**改副本不会生效**，改动必须回真相源。
2. 事件带三类元信息解决三件事：`agentScope` 解决「谁在说话」，`displayLevel` 解决「给不给用户看」，`queryRunId`/`turnId` 解决「这段属于哪一次运行、哪一轮输入」。
3. Runner 侧不是把原生事件原样转发，而是有一层处理器做聚合：按 100ms / 200 字符刷帧、按父工具 ID 分桶、把高频心跳降频、并在结束时用累加器补齐「最后一段」。
4. 宿主侧广播前要做两件过滤：**归属围栏**（丢弃已被取代的 query attempt 的事件）和**可见性过滤**（按用户与群的授权范围决定谁收得到），并且上下文审计只留在服务端。

## 主链与职责

```
Pi 原生事件
└─ RuntimeEvent（C02 映射）
   └─ toStreamEvent → StreamEvent（产品契约）
      └─ writeOutput → stdout 标记帧
宿主解析帧
  ├─ 落库（消息、用量）
  └─ broadcastStreamEvent(chatJid, event, agentId)
       ├─ context_audit → 只 recordRunContextSnapshot，不广播
       ├─ streamRunFence.observeExact(snapshotJid, queryRunId, turnId) → 被取代则丢弃
       └─ 按 getGroupAllowedUserIds 过滤后推给 WebSocket
前端 chat store
  ├─ 主文本（primary）→ 气泡 / 卡片正文
  ├─ 细节（detail）→ trace 面板、工具轨迹
  └─ 调试（debug）→ 开发者视图
```

状态所有者：真相源在 `shared/stream-event.ts`；聚合状态（文本缓冲、工具生命周期、待完成任务集合）在 Runner 的事件处理器里；归属判定（哪个 `turnId` 属于当前有效的运行）在宿主；渲染分层在前端。

## 源码阅读

1. 契约本体：[shared/stream-event.ts](../../../shared/stream-event.ts)。三个枚举决定了整个体系：`StreamEventType`（文本、思考、工具三段、hook、task、权限拒绝、记忆召回、压缩边界、用量、状态、初始化…）、`StreamAgentScope`（`main`/`task`/`subagent`/`system`）、`StreamDisplayLevel`（`primary`/`detail`/`debug`）。文件头写明它是单一真相源，构建时复制到 `container/agent-runner/src/`、`src/`、`web/src/`，**不要直接编辑副本**。

2. 同步机制：[Makefile](../../../Makefile) 的 `sync-types` 调 `scripts/sync-stream-event.sh`，`typecheck` 依赖它，之后还有 `scripts/check-stream-event-sync.sh` 校验三份副本一致性。所以「手改副本」会在流水线里被拦下。

3. 归因字段：`StreamEvent` 上的 `queryRunId`（具体一次队列查询）、`turnId`（一轮用户输入）、`sessionId`、`messageUuid`、`isSynthetic`（本地合成事件标记）。这几个字段看着琐碎，实际上是所有「这段流属于谁」判断的唯一依据。

4. 三重适配的中间层：C02 讲的 `toStreamEvent`（[pi-runner.ts](../../../container/agent-runner/src/runtime/pi/pi-runner.ts)）把运行时事件翻译成产品事件，并顺手定好 `displayLevel`：`text_delta` → `primary`，`thinking_delta` → `detail`，工具事件 → `detail`，状态 → `detail`，会话事件 → `debug`。

5. Runner 侧聚合：[stream-processor.ts](../../../container/agent-runner/src/stream-processor.ts) 的 `StreamEventProcessor`。关键常量：`FLUSH_MS = 100`、`FLUSH_CHARS = 200`（两个条件任一满足就刷一帧）；文本按 `parentToolUseId` 分桶（`BUF_MAIN` 表示顶层），这样嵌套工具里的文本不会串到主回复里；`fullTextAccumulator` 单独累加全部 `text_delta`，因为运行时的最终结果只带最后一个文本块；思考 token 的心跳被压到 2 秒一次（源码注释说明原始帧一轮里能来几千次，1:1 广播曾把 Web 与卡片投影拖死）。

6. 工具生命周期配对：同一份处理器维护 `activeTopLevelToolUseId`、`activeSkillToolUseId`、以及 `pendingSkillInput`/`pendingTaskInput`/`pendingAskUserInput`/`pendingTodoInput` 四张按 content block index 累积 input JSON 的表，用来在工具参数还没解析完时就先拿到技能名、任务描述、待确认问题、todo 列表。`SDK_TERMINAL_TASK_STATUSES`（`completed`/`failed`/`killed`）是「不会再有后续信号」的判定集合，漏判的代价是待完成任务集合泄漏、关流被永久推迟。

7. 宿主广播：[web.ts](../../../src/web.ts) 的 `broadcastStreamEvent`。第一件事是 `context_audit` 的分流——上下文审计只写 `recordRunContextSnapshot` 并打日志，不发给客户端，注释写明原因是会把路径、提示词接线和框架术语暴露给用户。然后是 `streamRunFence.observeExact(snapshotJid, queryRunId, turnId)`：被取代的 query attempt 的事件直接丢弃并 `debug` 日志。最后按 `getGroupAllowedUserIds(chatJid)` 过滤接收者。

8. WebSocket 建连：[web.ts](../../../src/web.ts) 的 `setupWebSocket` 做 Origin 校验：同源（Origin 的 host 等于 Host 头）放行；`CORS_ALLOWED_ORIGINS=*` 全放行；否则比对白名单，不在白名单则 403 且每个 origin 只 warn 一次。注释解释了为什么必须做：CORS 中间件不覆盖 WebSocket，浏览器也不对 WebSocket 发 preflight，缺这层就是 CSWSH。

9. 前端消费：[chat.ts](../../../web/src/stores/chat.ts) 直接 import 同一份类型副本，把事件映射成 `StreamingTraceEvent`（带 `kind`、`scope`、`displayLevel`），主文本进正文、细节进 trace。

## 机制与边界

**为什么必须单一真相源。** 流式事件是宿主、Runner、前端三方唯一共享的数据结构。三份各自演化时，症状是「某个事件在 Web 上能看到、在 IM 卡片里丢了」，而三方都「觉得自己没错」。复制 + 一致性校验不是优雅，是把这类问题从运行时前移到构建时。

**为什么用 `displayLevel` 而不是让宿主决定可见性。** 宿主不知道前端现在有没有展开细节面板，也不知道某个渠道卡片能不能渲染 markdown。它只知道「这个事件是什么」。把呈现策略做成事件自带的属性，宿主就退化成转发器，新增一种事件不需要改投递链路。

**为什么要有围栏。** 一轮对话可能因为失败重试、能力变更、用户停止而产生多次运行尝试。旧尝试的回调可能在新运行已经开始了才到——如果不做围栏，就会出现「旧运行的文本被贴到新一轮的回复里」。`observeExact` 用 `queryRunId` 精确匹配，避免只靠 `turnId` 判断时把 A 的迟到回调误标成 B。虚拟 JID 里带 agentId 也是为了这个：A→B 的替换过程中，turnId 归属要能存活下来。

**为什么聚合放在 Runner 而不是宿主。** 聚合需要看到原生事件的全部细节（父工具 ID、content block index、input JSON 增量），这些信息在翻译成产品事件时就丢了。放在 Runner 侧，宿主拿到的是已经成形的帧，落库和转发都是简单动作。

**已知边界**：`FLUSH_MS`/`FLUSH_CHARS` 是经验值，极端长文本下仍可能一帧过大；`context_audit` 不上云意味着前端的能力预览要靠另外的接口；思考心跳降频会牺牲「思考过程逐字可见」的观感，换来投影不卡；围栏只解决同一逻辑会话内的取代关系，跨会话串台要靠 JID 自己正确。

## 需要懂什么

**流式不是「边收边发」，是「边收边规整」。** 模型输出的是细碎增量，UI 需要的是可渲染的帧，中间必须有聚合层，否则帧率会跟着 token 速率抖动。聚合层的三个参数（时间、字符数、父工具分桶）决定了观感和正确性。

**事件契约里最贵的字段是归因字段。** `queryRunId`、`turnId`、`agentScope` 加起来只占几十字节，但它们决定了「这段内容属于哪次运行」可不可判。删掉它们的收益是消息更小，代价是所有并发、重试、重连场景都变成猜。

**可见性是事件属性，权限是投递属性。** 事件说「这是细节」，投递说「这个用户能看这个会话」。两者混在一起会导致要么前端知道太多权限信息，要么宿主被迫理解渲染语义。

**副本一致性要用工具保证。** 靠 code review 记住「别改副本」不可持续，靠构建期的 diff 校验才可持续。

## 需要记住什么

主链：原生事件 → RuntimeEvent → StreamEvent（带 scope/level/归因）→ 标记帧 → 宿主落库 + 围栏 + 权限过滤 → WebSocket → 前端按 level 分层渲染。

必记不变量：

- 真相源只有 `shared/stream-event.ts`；三份副本由 `sync-types` 生成，`typecheck` 校验。
- `text_delta` 是 `primary`，思考与工具是 `detail`，会话内部事件是 `debug`。
- 聚合阈值 100ms / 200 字符；文本按父工具 ID 分桶；最终结论文本来自累加器，不是运行时结果的最后一块。
- 终态任务集合 `completed`/`failed`/`killed`，漏判会泄漏待完成任务集合并推迟关流。
- 被取代的 query attempt 事件必须丢弃；`context_audit` 不上客户端。
- WebSocket 必须校验 Origin（同源或白名单），否则暴露 CSWSH 面。

当前限制与演进方向：围栏依赖 `queryRunId` 被正确透传，任何一环丢字段都会退化成弱判定；聚合参数是全局常量，不区分渠道；没有对「帧过大」做硬限制（见 [C08](./C08-渠道可靠投递状态机.md) 的卡片渲染约束）。
