# C09 定时任务调度与重启恢复

> 课程性质：核心
> 返回：[导学](../导学.md)；前置：[C08 渠道可靠投递状态机](./C08-渠道可靠投递状态机.md)；下一课：[C10 长期记忆：FTS5 检索与写入治理](./C10-长期记忆-fts5-检索与写入治理.md)
> 对应：B6；见 [面经](../面经.md)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

场景：用户说「每天早上九点给我出一份昨天的项目进展」。这条任务要在服务重启、模型失败、渠道抖动、用户改计划之后依然语义正确。

四个结论：

1. 调度是「定义 + 发生」两段式：`scheduled_tasks` 存定义与下一次计划时间，每次到点生成一条**发生记录**（`task_runs`），执行、通知、日志都挂在发生记录上。
2. 重启语义显式分叉：周期任务错过就记 `missed` 并推进到下一次；一次性任务错过仍然补跑。这个区别来自「用户想要的是节奏还是那个时间点的动作」。
3. 计划推进有两个锚点：调度循环用 `task.next_run` 作锚点推进（不追当前时间，避免漂移累积），新建或修改任务则从当前时刻起算第一次触发。
4. 失败与损坏都要收敛到可解释状态：坏 cron 会把任务暂停而不是让它跑成毫秒循环；周期任务算出 `null` 的 `next_run` 是暂停而不是完成。

## 主链与职责

```
每 tick：materializeDueOccurrences()
  getDueTaskDefinitionsV2(100)          ← 取出到点的任务定义
  ├─ computeNextRun(task) 抛错 → 生成一条 missed 发生记录 + 任务置 paused
  ├─ shouldSkipBackfill(scheduledFor, schedulerStartedAtMs)
  │    true（周期任务错过）→ triggerType='backfill'，missedReason='Missed while scheduler was offline by Ns'
  └─ 否则 → triggerType='scheduled'（once 任务逾期也走 backfill）
      └─ materializeTaskOccurrence({taskId, scheduledFor, nextRun, triggerType, missedReason})

发生记录执行
  claim durable run（带心跳、带围栏）
  └─ runTask(task, deps, {durableRun, manualRun?})
     ├─ 拉起隔离运行（独立 IPC 目录）
     ├─ 结果写 run 记录 + task_run_logs
     ├─ 通知：按渠道逐个投递，失败按渠道重试
     └─ finalizeRecurringRun(task, nextRun, summary, durable)
        └─ nextRun 为 null 且非 once → 暂停（不完成）
```

状态所有者：任务定义在 `scheduled_tasks`；每次发生在 `task_runs`；通知投递状态在通知收据里；「调度器是否在线」用 `schedulerStartedAtMs` 表达。

## 源码阅读

1. 解析与校验：[task-scheduler.ts](../../../src/task-scheduler.ts) 顶部用 `cron-parser` 的 `CronExpressionParser`。五字段 cron 是分钟粒度；六字段 cron 只有在秒位解析成单值时才允许（否则等于允许秒级高频循环）。`interval` 有 `MIN_INTERVAL_MS` 下限，低于下限直接拒绝。

2. 两个推进函数，语义不同：`computeNextRun(task)` 以 `task.next_run` 为锚点推进——用于调度循环，好处是长时间运行不会因为 tick 抖动而漂移；`computeNextRunForSchedule(type, value)` 从当前时刻起算，用于新建/修改任务时算第一次触发。源码注释专门强调两者不能混用。

3. 时间语义：`once` 的 `schedule_value` 是不带 `Z` 的本地时间串，按进程本地时区解释再以 UTC 存储；修改任务时如果算出的下一次已经过期，会拒绝（避免「一保存就立刻触发」的意外）。

4. 到点物化：`materializeDueOccurrences`（2926 行起）。取 `getDueTaskDefinitionsV2(100)` 批量处理，`computeNextRun` 抛错时把这次发生记录成 `missed` 并把任务暂停（`status: 'paused', next_run: null`），因为一个解析不了的计划继续跑只会不断产生垃圾发生记录。

5. 错过判定：`shouldSkipBackfill(scheduledFor, schedulerStartedAtMs)`。判据是「计划时间早于调度器本次启动时间」，也就是「它到点的时候我不在线」。周期任务命中这个条件就**不补跑**，只记 `missed` 与原因 `Missed while scheduler was offline by Ns`；一次性任务即使逾期也走 `backfill` 真跑一次。

6. 执行与收尾：`runTask` 里带 `durableRun: claim`，发生记录有独立的主键、心跳与终态；`options.manualRun` 为真时**不推进** `next_run`（手动触发不该打乱原计划）；`finalizeRecurringRun` 遇到 `nextRun === null` 且不是 once 任务时把状态置为 `paused` 而不是 `completed`——注释说明这是为了防止「cron 表达式被改坏后任务静默消失」。

7. 去重屏障：源码里有一条注释（#363）说明必须等 `updateTaskAfterRun()` 写完 `next_run` 才能释放防重复屏障。顺序反了会导致同一时间点被重复物化两次。这类顺序约束在调度器里比在请求链路里更容易写错，因为没人会盯着它。

8. 通知与日志：一次发生的结果摘要与逐渠道投递状态分开记录，渠道失败按渠道重试（`retryPayloadForReceipt` 那类路径），`task_run_logs` 保存过程日志。一次性任务的临时工作目录在执行完后会被清理，启动时还会扫一遍孤儿目录。

9. 任务状态集合：运行终态包含 `success`、`failed`、`cancelled`、`missed`。`missed` 是一种**正常终态**，不是错误——它表达「这次没有执行，原因已知」。

## 机制与边界

**为什么周期任务错过不补跑。** 「每天早上九点」表达的是节奏，补跑会得到「下午三点收到一条本该早上九点发的日报」，信息价值下降而打扰上升。相反，「明天上午十点提醒我提交材料」是一次性动作，错过就补，晚到的提醒仍然有用。这条规则如果不显式写，团队里每个人都会有不同的直觉。

**为什么需要 `missed` 这个状态。** 把错过的发生记为失败会污染失败率，记为成功会掩盖漏跑。独立状态让「系统当时不在线」和「任务跑挂了」在排障时能分开看，也让用户看到的时间线是诚实的。

**为什么锚点要用 `next_run` 而不是 `now`。** 用 `now` 推进的话，每次 tick 的延迟都会累积成漂移：跑了三个月，「每天九点」可能变成「每天九点零二分」。用上一次计划时间作锚点，误差不累积。

**为什么手动触发不改计划。** 手动运行是「我现在就想看一次」，不是「以后都提前到这个时候」。混同会导致用户点几次「立即运行」，任务的计划时间被推得乱七八糟。

**为什么坏计划要暂停而不是删除。** 删除是破坏性的，用户改坏一个表达式不该丢任务；暂停 + 保留定义，用户改回来就能恢复（`PATCH /api/tasks/:id` 会重算 `next_run`）。

**已知边界**：调度器是单进程内存循环，多实例部署时没有分布式锁（同一任务可能被两个实例同时物化，靠 durable claim 兜底但不能完全避免重复通知）；错过判定用「本次启动时间」，如果重启很频繁，可能反复落入 missed；批量取 100 条，极端堆积时会分多轮处理。

## 需要懂什么

**定时任务的核心不是 cron 解析，是「发生（occurrence）」这个概念。** 定义只有一个，发生有无限多个；把状态挂在定义上，就无法回答「上周三那次到底跑没跑、发了什么」。所有可靠性能力（重试、通知、日志、幂等）都必须挂在发生记录上。

**恢复语义必须显式且可解释。** 「错过怎么办」不是实现细节，是产品语义。选择规则时问的是「用户当时想要什么」，而不是「哪种实现简单」。

**时间锚点的选择决定了长期正确性。** 锚在计划时间上误差不累积；锚在现在上，每次延迟都会变成永久偏移。这个区别在跑三天时看不出来，跑三个月就是 bug。

**损坏输入要收敛到可恢复状态。** 坏 cron、坏 `next_run`（手工改库或旧版宽松校验留下的 `NaN` 锚点）都要有明确处理路径：暂停、记录原因、允许用户修好再恢复。

## 需要记住什么

主链：`tick → 取到期定义 → 算下一次 → 判定 missed/backfill → 物化发生记录 → claim durable run → 执行 → 写 run + 日志 → 逐渠道通知 → finalize(next_run)`。

必记不变量：

- 周期任务错过：记 `missed` + 推进计划，不补跑；一次性任务逾期：补跑。
- 推进锚点是 `task.next_run`；新建/修改时从当前时刻起算。
- 周期任务 `next_run` 算出 `null` → 暂停，不完成。
- 手动运行不推进 `next_run`。
- `once` 的本地时间先按进程时区解释再转 UTC 存储。
- 先写完 `next_run` 再释放防重复屏障。
- 运行终态包含 `missed`，它是正常终态。

当前限制与演进：单进程调度、无分布式锁；错过判定只看启动时间；任务运行与普通运行共用同一套执行超时（见 [C06](./C06-会话串行队列与-runner-生命周期.md)），长任务会受与对话相同的上限约束（见 [面经 Q6](../面经.md)）。
