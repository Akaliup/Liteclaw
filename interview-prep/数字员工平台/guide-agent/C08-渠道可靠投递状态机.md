# C08 渠道可靠投递状态机

> 课程性质：核心
> 返回：[导学](../导学.md)；前置：[C07 流式事件契约与三段同步](./C07-流式事件契约与三段同步.md)；下一课：[C09 定时任务调度与重启恢复](./C09-定时任务调度与重启恢复.md)
> 对应：B5；见 [面经](../面经.md)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

IM 侧对用户承诺三件事：消息不丢、不重、可恢复。这三件事在代码里不是靠"多试几次"实现的，而是一套只有持久化与围栏职责的状态机：[channel-reliability-store.ts](../../../src/channel-reliability-store.ts) 开头的模块注释就把边界写死了——它只拥有 persistence 与 fencing，Provider I/O、路由决策和重试策略全部留在渠道层与运行时层。这个切分让同一套 inbox/run/outbox 模型能同时服务飞书、QQ、微信和未来的传输。

本课要拿走四样东西。第一，四张业务表加一张游标表的字段与状态枚举，状态名必须照源码记。第二，`lease_token` 的围栏语义——它授予的是"接管权"，不是"锁"。第三，"不确定态"（`uncertain`）为什么必须是状态机里的一等状态，而不是异常分支。第四，阻塞式流式卡片的三阶段与 finalize 的幂等基础（revision CAS）。

## 主链与职责

入站链路以飞书为样本最完整。[feishu.ts](../../../src/feishu.ts#L1761) 的 `handleIncomingMessage` 做四步：`recordChannelInbox({ status: 'queued' })` 先落库，`claimChannelInboxById` 拿租约，`processClaimedIncomingMessage` 执行，最后按结果走 `completeChannelInbox` / `ignoreChannelInbox` / `failChannelInbox`。落库失败时它不降级继续跑，注释写得很直白：没有 Inbox 唯一围栏，两个 WS 客户端或一次重连就能把同一轮 Agent 启动两次。

一轮对话由一个 [ChannelTurnRuntime](../../../src/channel-turn-runtime.ts#L64) 对象持有。`start()` 先 `createChannelTurnRun`，run id 与幂等键都是**确定性派生**的（`channel-turn-v1:provider:accountId:externalMessageId:agentId` 的 sha256 前 32 位），因此同一个逻辑输入一定落到同一行；随后 `claimChannelTurnRunById` 拿租约，默认 lease 45 秒、心跳 12 秒。

出站链路在 [channel-outbox-delivery.ts](../../../src/channel-outbox-delivery.ts#L250)：`deliverChannelOutboxItem` 先 `enqueueChannelOutbox` 落库，再 claim，然后按 `single` 或 `upload_then_send` 两种模式推进 `uploading → uploaded → sending → delivered`；失败时由 `failChannelOutbox` 决定落成 `uncertain`、`retry_wait` 还是 `failed`。

卡片链路在 [feishu-streaming-card.ts](../../../src/feishu-streaming-card.ts)。`StreamingCardController` 通过 `lifecycle.onEvent` 把 `creating / streaming / waiting_user / running / finalizing / completed / aborted / failed` 八种事件交回宿主，宿主在 [channel-turn-runtime.ts](../../../src/channel-turn-runtime.ts#L386) 的 `onCardEvent` 里把事件投影成 `streaming_cards` 行的 revision 递增更新。

恢复链路集中在 [channel-reliability-recovery.ts](../../../src/channel-reliability-recovery.ts)。启动时 `reconcileChannelReliabilityOnStartup` 关掉上一个进程留下的活卡片、作废过期执行围栏，之后才允许恢复 Agent 工作；[index.ts](../../../src/index.ts#L21352) 的注释明确了这个顺序是正确性边界。同一文件还有每 15 秒一次的 live 巡检。

## 源码阅读

先读表。`createChannelReliabilitySchema` 在同一个连接上建五张表：`channel_inbox` 有 `UNIQUE(provider, account_id, external_message_id)`，这是"不重"的第一道闸；`turn_runs` 的 `idempotency_key` 唯一，并且有 `idx_turn_runs_inbox` 的**部分唯一索引**（只在 `inbox_id IS NOT NULL` 时生效），意味一条入站最多对应一轮执行；`channel_outbox` 有 `UNIQUE(turn_run_id, ordinal)` 和 `idempotency_key` 唯一；`streaming_cards` 靠 `revision` 做 CAS；`channel_cursors` 主键是 `(provider, account_id, scope, chat_id)`。

再读 claim。`claimChannelInbox`（[774 行](../../../src/channel-reliability-store.ts#L774)）的候选查询有两个分支：可正常领取的非终态行，以及"租约已过期"的 `processing` 行——后者是崩溃接管。真正的写入是一条带围栏令牌的 CAS：

```sql
UPDATE channel_inbox
SET status = 'processing', lease_owner = ?, lease_token = ?,
    lease_expires_at = ?, attempt = attempt + 1, updated_at = ?
WHERE id = ? AND lease_token = ? AND (
  (status = ? AND status IN ('received','admitted','queued')
    AND available_at <= ? AND lease_owner IS NULL)
  OR (status = 'processing' AND lease_expires_at IS NOT NULL
      AND lease_expires_at <= ?)
)
```

`lease_token = candidate.lease_token` 这一段是关键：谁先 `UPDATE` 成功，令牌就加一，另一个消费者的旧令牌立刻失配。这不是悲观锁，而是一次性的令牌兑换。`turn_runs` 与 `channel_outbox` 的 claim 用同一套写法。

第三读续租的**限制**。`renewChannelInboxClaim`（[887 行](../../../src/channel-reliability-store.ts#L887)）带 `lease_expires_at > now` 条件，注释说"过期的 claim 永远不能复活"。所以在这个模块里，续租和接管是两条互斥的路：能续就说明围栏还活着，一旦过期就只能被别人重新 claim 走，owner 不能自己把租约捡回来。`heartbeatChannelTurnRun`、`markChannelTurnFinalizing`、`completeChannelTurnRun`、`markChannelOutboxUploading`、`completeChannelOutbox` 全部带同样的时间条件。

第四读"完成必须是出站清空的函数"。`completeChannelTurnRun`（[1433 行](../../../src/channel-reliability-store.ts#L1433)）在 `status = 'completed'` 时额外要求 `NOT EXISTS` 任何处于 `pending/claimed/retry_wait/uploading/uploaded/sending/uncertain` 的 outbox 行。也就是说 Agent 跑完不等于 turn 完成，消息还在半路上时 turn 只能停在 `finalizing`。

第五读游标。`advanceChannelCursor`（[484 行](../../../src/channel-reliability-store.ts#L484)）用 UPSERT 加 `WHERE` 守卫实现"只前进不后退"：

```sql
ON CONFLICT(provider, account_id, scope, chat_id) DO UPDATE SET
  cursor = excluded.cursor,
  position = excluded.position,
  tie_breaker = excluded.tie_breaker,
  updated_at = excluded.updated_at
WHERE excluded.position > channel_cursors.position
   OR (excluded.position = channel_cursors.position
       AND excluded.tie_breaker > channel_cursors.tie_breaker)
```

`position` 是 Provider 的单调时间戳或序列号，`tie_breaker` 解决同一时刻的确定性排序，返回的 `advanced` 布尔值告诉调用方这次是真的推进了还是被拒。飞书侧 `rememberTerminalProgress` 把"完成 Inbox"与"推进游标"当成一对可修复操作：崩在中间时，一条重复事件会看到终态行、跳过执行、把游标补上。

最后读载荷去重。`channelPayloadHash`（[280 行](../../../src/channel-reliability-store.ts#L280)）先做 `stableJsonValue` 的键排序递归，再 sha256。没有这一步，`{a:1,b:2}` 与 `{b:2,a:1}` 会被判成两条不同载荷，去重就失效。而 ordinal 也不是自增，`stableChannelOutboxOrdinal` 从语义身份（[channel-outbox-runtime-scope.ts](../../../src/channel-outbox-runtime-scope.ts#L132)）做哈希取前 12 位十六进制，所以模型重试换了 `requestId` 也不会产生第二条消息。

## 机制与边界

**不确定态解决的是"ACK 丢失"这类不可判定问题。** 一旦进入 `sending`，超时、连接断开、进程被杀都无法证明 Provider 没收到。代码把这件事拆成两类错误：`DefinitiveChannelDeliveryError` 表示 Provider 明确拒绝，可以安全 `retry_wait` 或 `failed`；其他一切在 `sending` 之后的普通异常都算 `uncertain`。[channel-outbox-delivery.ts](../../../src/channel-outbox-delivery.ts#L383) 的注释写明了这条判据。

**一条 uncertain 会封住整个 turn。** 三处闸门都在查 `getUncertainChannelOutboxForTurn`：`deliverChannelOutboxItem` 入口直接返回那条 uncertain 结果、不再发送任何兄弟消息；`ChannelTurnRuntime.complete()` 拒绝收尾；[index.ts](../../../src/index.ts#L2612) 的通用侧效闸门也直接 return false。理由是同一条 turn 的输出是用户眼里的一段连续对话，中间漏一条就无法解释顺序。解除封印只能由人做：`listUncertainChannelOutbox` 给运营面，`resolveUncertainChannelOutbox` 用 `expectedRevision` 做 CAS，只允许从 `uncertain` 落到 `delivered`（带 `providerMessageId`）或 `failed`。

**崩溃后的分类由 `reconcileExpiredChannelOutbox` 决定，不是由重试次数决定。** 它把 `claimed/uploading/uploaded` 的过期租约改回 `retry_wait`（发送前，安全重试），把 `sending` 的过期租约改成 `uncertain`（发送后，不可判定）。这一条把"什么时候能自动重发"变成了一个纯数据判定。

**`running` 的 turn 不会被自动接管。** `claimChannelTurnRun` 的候选只取 `status IN ('queued','retry_wait')`，`running/finalizing` 只能被 `interruptExpiredChannelTurnRuns`（[1483 行](../../../src/channel-reliability-store.ts#L1483)）判成 `interrupted` 并写入 `[manual_reconciliation] ...` 错误，理由写在函数注释里：Agent 执行已经开始，副作用不可知，自动重放会造第二条可见输出。

**人工核对的识别靠错误前缀。** `MANUAL_RECONCILIATION_ERROR_PREFIX = '[manual_reconciliation] '`（[1132 行](../../../src/channel-reliability-store.ts#L1132)）与 `requiresManualReconciliation()` 把这件事做成了可查询的语义，而不是靠人读日志。它还保留了 v60 之前"manual reconciliation required"小写子串的兼容判断。

**"已交付但 turn 没完成"在正常运行中是合法的。** 所以 `interruptChannelTurnRunsWithDeliveredEffects` 只在启动时跑，并且显式跳过租约未过期的 `running/finalizing`——另一个服务实例可能还持有它。若在 live 定时器里跑这条，每一个正常 turn 都会在"outbox 已 delivered、turn 尚未 complete"的几十毫秒窗口里被判死。

**live 巡检有启动纪元围栏。** `startChannelReliabilityRecoveryLoop` 记录 `createdBefore = now - 1ms`，只处理这个时间点之前创建的卡片。没有它，一个正常需要 30 秒以上的回答会被 15 秒的巡检定时器中途 abort。

**卡片与 turn 是两台独立状态机。** [channel-turn-runtime.ts](../../../src/channel-turn-runtime.ts#L466) 的注释明确：compact/overflow 之类的 partial 可能提前把 Provider 卡片关掉，而同一个逻辑输入还在跑；只有宿主的 `inputTurnCompleted` 加物理投递 ACK 才能终结 turn。卡片自身的终态靠 `finalizeStreamingCardRecord` 的 `revision` CAS，`updateStreamingCardRecord` 的 WHERE 里带 `status NOT IN ('completed','aborted','failed')`，所以重复 finalize 是幂等的 no-op，而 `claimStreamingCardRecovery` 把卡片置为 `recovering`——故意保持非终态，让下一次巡检还能再试。

**`recovering` 之上的兜底是 `aborted` 而不是 `completed`。** 恢复流程只会把中断的卡片改成 `aborted` 并写 `recovery.reason`；如果卡片连 `messageId` 和 `cardId` 都没有，直接 `failed` 并写 `missing_provider_identity`，因为无法证明 Provider 侧到底有没有那张卡片。

**滚动升级期同一条消息可能被两个进程看到。** 这一点靠四层挡住：Inbox 唯一约束、`turn_runs` 的确定性 id 与幂等键、`idx_turn_runs_inbox` 部分唯一索引、以及 `ChannelTurnRuntime.start()` 里那句"发现已有 delivered 侧效就抑制重放"的预检围栏。

## 需要懂什么

要能解释围栏令牌与锁的区别：锁保护资源，令牌保护**提交权**。在本模块里令牌还连着时间：过期即失去提交权，这一条与 [db.ts](../../../src/db.ts#L5460) 里 `task_runs` 的"过期但未被接管仍可提交"正好相反，是刻意不同的取舍（C09 会展开）。

要能解释为什么游标必须单调且带 tie_breaker：Provider 事件可能乱序到达，`position` 相同的事件需要确定性次序，否则重启后会重复或跳过。

要能解释为什么载荷要规范化再哈希：幂等键的稳定性直接决定去重是否成立，键顺序、`undefined` 与 `null` 的差异都会破坏它。

要能解释三种通道错误的区别：明确拒绝（可重试）、发送前失败（可重试）、发送后不可判定（必须人工核对）。

要能解释 outbox 的 `upload_then_send` 为什么只允许 `image` 和 `file`：文字与卡片没有"上传"阶段，允许它会造出无意义的中间态。

## 需要记住什么

四张业务表加一张游标表，以及它们的唯一约束：`channel_inbox(provider, account_id, external_message_id)`、`turn_runs.idempotency_key` 与 `turn_runs(inbox_id)` 部分唯一、`channel_outbox(turn_run_id, ordinal)` 与 `channel_outbox.idempotency_key`、`channel_cursors(provider, account_id, scope, chat_id)`。

五组状态枚举（照源码）：`ChannelInboxStatus = received | admitted | queued | processing | processed | ignored | failed`；`ChannelTurnRunStatus = queued | running | retry_wait | waiting_user | finalizing | completed | failed | interrupted | cancelled`；`ChannelOutboxKind = text | image | file | card | mutation`；`ChannelOutboxStatus = pending | claimed | retry_wait | uploading | uploaded | sending | delivered | uncertain | failed | cancelled`；`StreamingCardStatus = creating | streaming | recovering | completed | aborted | failed`。

关键常量：turn lease 45 秒、心跳 12 秒；outbox claim 默认租约 60 秒；飞书 Inbox 租约 5 分钟；live 巡检间隔 15 秒。

一句话主链：入站先落库再 claim，出站先落库再发送，发送后的不可判定永不自动重发。

三处 uncertain 闸门：出站入口、turn 收尾、通用侧效闸门。三处都必须记得，否则会误以为只在投递层拦。
