# C04 能力解析管线与精确挂载

> 课程性质：核心
> 返回：[导学](../导学.md)；前置：[C03 上下文工程：Prompt 分层与预算](./C03-上下文工程-prompt-分层与预算.md)；下一课：[C05 工具面：MCP 工具与 IPC 回调](./C05-工具面-mcp-工具与-ipc-回调.md)
> 对应：B3；见 [面经](../面经.md)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

- 能力不是"扫目录全塞进去"，而是**分层候选 → 精确选择 → 带 hash 的清单 → 按清单逐个只读挂载**。
- Skills 的分层顺序（低→高优先级）是 `builtin → host → project(容器内置) → managed(用户) → workspace(项目) → plugin`；同名按后序覆盖前序，冲突如实记录。
- Skill 的 `definitionHash` 是**整个目录 payload** 的逐文件 sha256（忽略 `.git`/`node_modules`/`.cache` 等），不是只 hash `SKILL.md` 元数据。
- 写策略时校验、运行时按清单执行：禁用的选择在解析前就被剔除，**缺失的选择在保存策略那一刻返回 400**，不会在运行时被静默替换成别的能力。
- 变更能力或 Prompt 身份后必须让暖 Runner 失效：`pauseGroupsForMutation`（同步、引用计数、park 后续工作）+ 前后两轮强制停止 + 提交后丢弃旧输入，失败则保持 fail-closed。
- 宿主 Skills 由 `runtime_policy.skills.host` 独立选择，打开 `host_claude` 上下文**不等于**获得宿主 Skills。

## 主链与职责

```
Agent Profile 的 runtime_policy
  ├─ skills.mode/ids      ─┐
  ├─ skills.host          ─┼→ resolveEffectiveSkills(layers) → EffectiveSkillManifest(hash)
  └─ mcp.mode/ids         ─┘      ├─ selected[]（含 path / definitionHash / overrides）
                                  └─ candidates[]（含 excludedReason）
                                        │
宿主 container-runner.buildVolumeMounts ┤→ 每个 selected Skill 一个只读 bind mount
                                        └→ ensureSettingsJson 整体替换 session 的 mcpServers
Runner 启动 → 读 session .claude/skills（容器内由 entrypoint 从只读挂载重建）
```

职责切分很清楚：`effective-skill-resolver` 只做"选谁"，`claude-context-resolver` 做"把选中的东西投影到 session 目录"，`container-runner` 做"真正挂载"，宿主故障与失效策略在 `capability-runtime-mutation`。

## 源码阅读

**一、候选与胜出**（[effective-skill-resolver.ts](../../../src/effective-skill-resolver.ts)）

```ts
options.layers.forEach((layer, precedence) => {
  for (const skill of scanSkillDirectory(layer.root, layer.source)) {
    const candidateId = layer.idPrefix ? `${layer.idPrefix}:${skill.id}` : skill.id;
    const filteredByProfile = /* managed 与 host 各有独立 policy 过滤 */;
    candidates.push({ id: candidateId, source: layer.source, precedence,
      enabled: skill.enabled, definitionHash: hashSkillDirectory(skillPath), /*…*/ });
  }
});
```

关键在注释里写明的语义：**禁用的定义在比优先级之前就被移除，所以它不会变成"墓碑"去挡住低层的同名启用定义**。胜出者是 `precedence` 最大的候选，落选者标 `shadowed`，同名即进 `conflicts`。插件用 `plugin:skill` 限定名，避免与用户 Skill 撞名。manifest 的 `hash` 覆盖 policy、hostPolicy、selected（id/source/definitionHash/overrides）与被排除项，所以"换了哪个来源的同一个名字"也会变 hash。

`reconcileSessionSkills` 负责重建 session 的 `skills/`：上一轮留下的**真实文件/目录**被移动到 `orphaned-skills/<时间戳>/` 而不是删除（Agent 自己写的文件不能凭空消失），符号链接直接清掉；新的用 staging 目录 + rename 原子替换，中途失败回滚 `previous`。`source === 'plugin'` 不建链接——插件由 `options.plugins` 加载，清单只贡献限定名。

**二、MCP 三层与清单**（[mcp-context.ts](../../../src/mcp-context.ts)、[effective-mcp-manifest.ts](../../../src/effective-mcp-manifest.ts)）

`loadClaudeContextMcpServers` 的合并次序是宿主 `settings.json`/`.claude.json` → 项目 `.mcp.json` → 项目 `.claude/settings.json` → `.claude/settings.local.json`；`mergeMcpServerLayers` 再把 LiteClaw 托管的 system/user 作为**最后叠加层**（托管能力不会被"继承宿主配置"替换掉）。`resolveManagedMcpPolicy`（[mcp-utils.ts](../../../src/mcp-utils.ts)）三种模式：`disabled` 给空表、`inherit` 给 system+user、`custom` 逐条解析 `system:` / `user:` 前缀并把找不到的引用收进 `missing`。`buildEffectiveMcpManifest` 只输出 `serverIds` 与 hash——**hash 覆盖完整的 canonical 定义，但返回值里不含命令与密钥**。

**三、缺失即失败**（[agent-profile-policy.ts](../../../src/agent-profile-policy.ts)）

`validateRuntimePolicyReferences` 在写策略时检查：managed Skill 的 id 合法且 `SKILL.md` 存在、host Skill 还要过路径校验、MCP 引用必须在当前可见层里存在、非管理员不得引用 admin-only 的 system MCP。任一不满足，路由返回 `400 invalid_runtime_policy`（见 [agent-profiles.ts](../../../src/routes/agent-profiles.ts)）。这是"精确选择"能成立的前提：**选择在写入时被验证过，运行时才可以按 id 直接挂载**。

**四、逐个只读挂载**（[container-runner.ts](../../../src/container-runner.ts) 的 `buildVolumeMounts`）

```ts
for (const skill of claudeContextPlan.effectiveSkills.selected) {
  if (skill.source === 'plugin') continue;
  let hostPath = skill.path;
  try { hostPath = fs.realpathSync(hostPath); } catch { /* 保留原路径，让 Docker 报确定性错误 */ }
  mounts.push({ hostPath, containerPath: `/workspace/effective-skills/${skill.id}`, readonly: true });
}
```

挂载点注释说明得直接：**每个选中的 Skill 一个只读挂载，entrypoint 只从这一处重建 `/home/node/.claude/skills`，所以上一轮容器留下的真实目录绝不会跨重启存活**。同函数里 `ensureSettingsJson` 以 `replaceMcpServers: true` 整体替换 session 的 `mcpServers`，并用同目录的 `.liteclaw-native-settings.json` 记录"上次投影了什么"，这样下次能只撤回自己写过、且用户没改过的键。

`prepareHostPlugins` 是 Host 模式的对应动作：先 `materializeUserRuntime` 把用户插件快照落到 runtime 目录，再失效命令索引缓存，最后 `loadUserPlugins({runtime:'host'})`；失败只 warn——"少加载插件"优于"整个 Agent 起不来"。

**五、插件与权限概况**：[plugin-manifest.ts](../../../src/plugin-manifest.ts) 读 `.claude-plugin/plugin.json` 与 marketplace 清单；[plugin-materializer.ts](../../../src/plugin-materializer.ts) 每用户快照目录 + runtime marker，用**独立 inode 的拷贝**（reflink 优先）避免 Host 模式写权限反噬 catalog；[plugin-dependency-check.ts](../../../src/plugin-dependency-check.ts) 静态扫 `allowed-tools` 里的 `Bash(xxx:*)` 看容器里有没有该二进制，属于 best-effort 预检；[plugin-expander-core.ts](../../../src/plugin-expander-core.ts) 在消息进 SDK 前展开 `disable-model-invocation` 的插件斜杠命令（三态：miss / expanded / reply）。[session-permissions.sh](../../../container/session-permissions.sh) 与 watcher 处理容器内 uid/gid 与宿主对齐——它决定了只读挂载之外那些可写目录的属主是否对得上。

## 机制与边界

- **候选集永远完整，选择集才精确**：`candidates[]` 保留全部候选与 `excludedReason`（`disabled` / `profile_filtered` / `shadowed`），所以预览页能解释"为什么某个 Skill 没生效"，而不是让它凭空消失。
- **hash 是唯一性判据**：Skill 改一行脚本也会变 `definitionHash`，因此"能力变化"可以被程序判定，不靠用户声明。
- **两把锁一起用**：[capability-lock.ts](../../../src/capability-lock.ts) 的 `withCapabilityScopeLocks` 按 key 字典序加锁，避免"system+user 跨域操作"与单域操作互锁死。
- **暖 Runner 失效**：[capability-runtime-mutation.ts](../../../src/capability-runtime-mutation.ts) 先用 `listCapabilityMutationRuntimeTargets` 找出"策略真能观察到这次变更"的 workspace（`disabled` 直接排除、`custom` 要命中 id），再交给 `quiesceWorkspaceRunnersAroundCommit`（[agent-profile-runtime.ts](../../../src/agent-profile-runtime.ts)）：`pauseGroupsForMutation` 在第一个 await 之前同步上闸 → 停 pre-commit 运行 → 提交并 `deleteWorkspaceSessions` 丢掉 SDK 会话 → 再停一次（覆盖新出现的 JID）→ `resumeGroupsAfterMutation` 放行。提交抛错时用 `blockGroupsForRuntimeSafety` 保持 fail-closed，宁可卡住也不让旧快照继续跑。
- **两条边界别混**：`includeHostClaudeContext`（CLAUDE.md/rules/原生目录）与 `hostSkillPolicy`（宿主 `~/.claude/skills`）是两个开关；`buildClaudeContextPlan` 里 `hostSkillPolicy` 未显式给定时才回落到"跟随 host_claude"，而路由层对非管理员直接 403。

## 需要懂什么

要能讲清"为什么要清单而不是路径集合"：清单带 `hash` 与 `excludedReason`，才能同时支撑三件事——能力预览可解释、暖 Runner 可判定失效、挂载可审计（挂了几项、来自哪层、覆盖了谁）。还要能解释只读挂载与 `reconcileSessionSkills` 的分工：容器模式下宿主只"发布清单"，容器 entrypoint 按清单重建链接；Host 模式才真正 `symlink` 到 session 目录（`materializeLinks: true`）。

## 需要记住什么

1. 分层顺序与覆盖规则：builtin → host → project → managed → workspace → plugin；禁用定义在比优先级前被剔除，不当墓碑。
2. `hashSkillDirectory` 逐文件 sha256 整目录 payload；manifest hash 覆盖 policy + selected + excluded。
3. MCP = 上下文层（宿主/项目，后序覆盖）**叠加**托管层（system/user 最后覆盖）；`custom` 的缺失引用进 `missing`。
4. 缺失/禁用/删除的选择在**保存策略时**返回 400，运行时不会静默替换。
5. 能力或身份变化 → mutation pause → 两次 stop + 会话失效 → 放行；提交失败保持 fail-closed。
