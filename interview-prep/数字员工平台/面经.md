# 面经：数字员工平台（Miniclaw）

> 以下为目标简历与学习口播，供掌握后选用。分析范围：本地仓库 `miniclaw-main` 的宿主主服务、Agent Runner、共享流式契约与 Web 前端关键机制（2026-10-17 静态分析）；七渠道逐个实现、计费细则与 Electron 桌面壳未逐行核验，相关回答只讲机制与边界。本文档默认目标简历模式：仓库已有机制均可进入主稿，职责归因按你自己的实际参与陈述调整。

## 项目简介（简历可用）

基于 Pi Agent Runtime 的自托管多租户 Agent 工作台：为每个 Agent 配置身份、四段 Prompt 与 Skills/MCP/插件能力，在独立容器或宿主机进程中执行，并通过 Web 控制面与飞书、Telegram、QQ、钉钉、微信、Discord、WhatsApp 七个渠道以流式方式交付结果，支持定时任务、长期记忆与用量计费。

## 简历 bullet

- **Agent Runtime 适配层与单轮执行契约：** 把执行引擎收敛在一层运行时中立接口之后（提示、跟进、打断、压缩、事件订阅各自独立），引擎原生事件先归一成运行时事件，再翻译成产品流式事件，因此接入新引擎或调整执行语义不触碰队列、渠道与前端。
  - 运行体以独立进程承载一轮任务：宿主通过标准输入下发结构化输入，进程用固定标记包裹逐条输出结构化结果与流式事件，运行期间从增量目录持续接收新消息并注入当前会话，未确认的消息在运行结束时写回队列重投，进程本身保持存活等待下一批输入。
  - 单轮执行把打断、跟进与收尾放进同一个收敛循环：关闭与中断哨兵各自短路、运行中到达的消息以跟进方式进入同一会话、结果发布做幂等保护，兜底错误优先于队列不变量抛出，保证宿主能区分"供应商报错"和"队列状态不一致"。
- **上下文工程与 Prompt 分层预算：** 系统提示按归属切成平台、Agent、工作区、渠道四类有序块，每块带版本、生效条件、内容哈希与 token 估算，整份计划再算一个总哈希，使"这轮模型看到了什么"可审计、可对比、可在变更后失效旧运行时。
  - 预算在引擎初始化前用保守口径估算（字节数与多字节字符数取大者），越过警戒线记警告、越过硬阈值直接拒绝启动该轮，避免把巨型提示送进模型才发现超限。
  - 每轮再叠加负责人画像块、工作区记忆摘要块与当前渠道格式块，顺序固定且与静态块分离，使同一份人格配置在不同渠道、不同记忆状态下都可复现。
- **能力解析管线与工具面治理：** Skills、MCP 与插件先按来源分层成候选，再按显式选择生成带哈希的有效清单，容器侧逐个只读挂载、宿主侧同步到同一份会话目录，让"选中了什么能力"成为可校验的产物而不是目录扫描的副作用。
  - 精确选择指向的技能被禁用、删除或在镜像中缺失时直接让本次配置失败，不做静默替换；能力清单或提示词身份变化后，旧的暖运行时按生命周期规则失效，避免继续用过期上下文作答。
  - 内置能力以进程内工具形式注册进运行时并统一命名空间，参数在入口用 schema 校验、在实现层再校验一次；有外部副作用的工具（发消息、排任务、读写长期记忆）不在执行体内直接落地，而是通过增量通道回到宿主执行，并按请求标识去重。
- **会话串行队列与运行时生命周期：** 并发边界由序列化键决定而不是会话归属：同一逻辑会话的多个入口共享一个运行时并严格串行，不同会话可并行；容器模式同时受系统并发上限与用户计费并发限制，宿主模式刻意不加应用层并发池，把容量交给操作系统。
  - 失败重试是有界指数退避，上下文溢出的失败跳过退避直接重排；同一会话上出现新用户消息时取消旧退避计时器但保留重试计数，避免"新消息成功一次就把连续异常洗白"。
  - 停止、重启与能力变更走暂停、恢复、丢弃三段：变更前暂停相关运行并保留其待重放输入，提交成功则丢弃旧输入并换新运行时，提交失败则恢复队列；用户主动停止后的短时间内不再自动重排，防止运行时把自己重新拉起来。
- **流式事件契约与可靠投递：** 流式事件类型只有一个真相源，构建期复制到宿主、执行体与前端三端，事件同时携带作用域、展示层级与运行归因标识，前端按层级分层渲染主文本、思考与工具轨迹，宿主按归因标识把一次运行的事件与一次用户轮次对齐。
  - IM 投递用入站、轮次、出站与流式卡片四组持久状态机承载：入站先落库再带租约领取并续约，避免双消费；出站按文本、图片、文件、卡片、变更分类并区分上传与发送阶段；网络超时导致的"可能已发出"单列为不确定态并要求核对，而不是盲目重发造成用户收到两条。
  - 游标推进与卡片终态各自幂等，服务重启后从记录位置继续；一轮对话有独立心跳与过期中断，运行体失联时把轮次收敛为可解释的失败而不是永久挂起。
- **长期记忆与定时运行：** 记忆用结构化知识表加全文索引承载，每条记录带类型、状态、版本与来源，写入走变更请求并携带幂等键与运行时签名鉴权，删除采用软删加墓碑，使召回不再命中而审计仍可追溯。
  - 检索按加权列排序并返回命中片段，让 Agent 在有限上下文里拿到可引用的事实；同一工位共享记忆，平台级负责人画像单独成表并有规范化约束。
  - 定时任务支持周期、固定间隔与一次性三种形态：服务重启时错过的周期任务标记为错过并推进下一次计划，一次性任务仍然补跑；任务与其他运行共用同一套执行超时与队列语义，运行记录与日志分表保存用于排障。
- **多租户隔离与 Agent Profile 治理：** 控制面会话用 HMAC 签名 Cookie，密钥按环境变量、持久文件、首次生成三级来源解析；工作区与渠道资源按创建者隔离且没有管理员全局旁路，越权访问统一返回资源不存在以隐藏存在性。
  - 系统配置、用户与邀请、审计与计费各自走独立权限中间件；敏感写操作先暂停相关运行，提交失败要恢复队列，避免"配置改了但运行体还在用旧策略"。
  - Agent Profile 的四段提示（身份、价值取向、工作流、工具策略）版本化保存，变更前生成能力与上下文的完整预览，运行时据此解析精确能力清单；Web 作为控制面不会篡改由原生渠道首次占有的会话身份。

## 面试问题

### Q1 从执行引擎到产品事件的两级映射
- 对应支柱：B1
- 触发依据：bullet 里"引擎原生事件先归一成运行时事件，再翻译成产品流式事件"，以及"接入新引擎或调整执行语义不触碰队列、渠道与前端"
- 考查目标：是否真的做过执行层抽象，能否说清两层事件模型各自的职责与替换成本
- 学习入口：[C01](guide-agent/C01-runner-进程协议与-ipc-通道.md)、[C02](guide-agent/C02-runtime-适配层与单轮执行.md)

**面试官问题**：你说在执行引擎外面包了一层适配层，为什么需要这一层？直接用引擎提供的会话接口和事件不就行了吗？

**口播版**：能用，但会把引擎的形状泄漏到产品每个角落。我做的是两级事件模型。第一级是运行时中立事件：文本增量、思考增量、工具开始与结束、用量、压缩开始与结束、子代理生命周期、最终结果，这一级的语义只描述"一次模型运行发生了什么"。第二级才是产品流式事件：它要带作用域（主代理、子代理、系统）、展示层级（主文本、细节、调试）和运行归因标识，因为同一个事件在 Web 面板和 IM 卡片里的呈现不一样。中间这层适配换来的东西很具体：接入新引擎只需要实现"创建会话 + 把原生回调映射成运行时事件"，队列、渠道投递、前端渲染一行都不动；反过来产品要加一个新的展示层级，也只改第二级映射。另外一层考虑是收尾语义。引擎的"结束"未必等于"这一轮用户消息处理完了"，因为运行期间还可能有跟进消息进来，所以适配层必须自己定义结果发布和收尾，不能直接把引擎的结束事件当成产品成功。

**追问 1**：你刚才提到"运行期间还可能有跟进消息进来"，那这轮到底什么时候算结束？
**触发依据**：口播里"引擎的结束未必等于这一轮用户消息处理完了"
**口播版**：结束的条件是"引擎不再流式输出 + 没有未完成的输入轮次"。我用一个投递跟踪器维护当前轮次和待处理轮次：运行期间从增量通道拿到的消息会先登记成一轮，再作为跟进内容喂给同一个会话；引擎报结果时，我先把它当作这一轮的结果发布出去，如果跟踪器里还有待处理轮次，就重置发布标记并激活下一轮。这样一句话概括：结果发布是幂等的、可以多次发生的，而"运行结束"要等所有登记过的轮次都有结论。代价是必须保证登记和确认成对出现，否则会出现"永远等不到结束"的悬挂状态，所以我在循环里加了一条不变量检查——引擎已停止流式、也没有新结果、但仍有未确认轮次时，直接抛错让宿主重试，而不是静默挂住。

**追问 2**：那如果进程在处理中途被打断，用户之前发的消息怎么办？
**触发依据**：追问 1 里"登记和确认成对出现"
**口播版**：分两种情况。用户点停止时，我取消当前轮次并把它的投递凭据标记成取消，运行体退出后宿主看到的是"被中断"而不是"成功"，这类输入按产品语义丢弃。能力或配置变更引起的停止不一样——它是为了换运行时，输入不能丢，所以我在暂停时把待重放输入保留下来，替换完成后在新的运行时里重放。运行体这一侧还有兜底：一轮结束时把没有确认的消息重新写回增量目录，宿主重启或进程崩溃后能重新读到，宁可让模型看到一次重复上下文，也不要让用户的消息凭空消失。

**追问 3**：你说适配层让换引擎不影响上层，怎么证明这一点是真的？
**触发依据**：口播里"接入新引擎只需要实现创建会话和事件映射"
**口播版**：看边界的形状。适配层对外只暴露一个会话语义接口：发起一轮、跟进、打断、压缩、订阅事件、释放。里面允许引擎有任何私有概念，但外面拿不到。我在实现里做过一次实证：同一个产品链路里保留了两套运行入口，其中一套是历史引擎的路径，另一套是现在生产用的路径，两者共用同一份输出协议和同一份事件翻译，宿主侧的队列、投递、落库代码完全一致。这件事的反证也很清楚：如果哪天某个事件翻译需要读引擎内部对象才能拿到字段，那说明抽象漏了，得把字段补到中立事件里，而不是让上层去 import 引擎类型。

### Q2 系统提示的组织方式
- 对应支柱：B2
- 触发依据：bullet 里"按归属切成平台、Agent、工作区、渠道四类有序块，每块带版本、生效条件、内容哈希与 token 估算"
- 考查目标：上下文工程的实际做法，是否理解可审计性与预算控制，而不是只会拼模板
- 学习入口：[C03](guide-agent/C03-上下文工程-prompt-分层与预算.md)

**面试官问题**：Agent 的系统提示你是怎么组织的？很多人就是一个大模板字符串加变量替换，你为什么不做成那样？

**口播版**：大模板字符串的三个问题在我们这里都会立刻变成线上问题。第一是不可审计：用户问"我的 Agent 为什么这么说话"，你得能回答这轮到底注入了哪些块、各占多少 token，字符串拼完就查不出来了。第二是不可失效：Agent 人格、技能清单、工作区记忆任何一处变了，正在跑的暖运行时必须失效，否则它还在用旧人格；要知道变没变，就得有内容哈希。第三是不可控预算：平台块、人格块、记忆块、渠道格式块会随租户和渠道组合放大，必须在送模型之前就知道总量。所以我把系统提示做成一份计划：每个块带标识、版本、作用域（主代理还是子代理）、归属（平台、Agent、工作区、渠道）、是否必需、生效条件、内容哈希和字节与 token 估算，整份计划再算一个总哈希。块之间顺序固定，条件不满足的块就不进计划。这样"这轮模型看到了什么"是一个可序列化的产物，能存进审计、能在两个版本之间 diff。

**追问 1**：你说的 token 估算是在什么阶段算的？引擎自己不是会算吗？
**触发依据**：口播里"必须在送模型之前就知道总量"
**口播版**：引擎的上下文用量是权威的，但它是会话建好之后才有的。我需要在建会话之前拦一道，因为提示超限的表现是这一轮直接失败，而失败的位置在模型供应商那边，排查成本很高。所以在计划阶段用保守口径估：按 UTF-8 字节数除以四，再和多字节字符的实际个数比，取大的那个。这个口径对英文偏保守、对中文更保守，正是我要的方向——宁可提前拒，也不要上线才发现。两级阈值：越过警戒线只记警告并继续，越过硬阈值就报错拒绝启动这一轮，让调用方看到明确的失败原因，而不是让模型侧返回一个看不懂的 400。

**追问 2**：那如果某个 Agent 的人格块特别长，一直触发警告，你怎么处理？
**触发依据**：追问 1 的"越过警戒线只记警告并继续"
**口播版**：警告是有用的信号，但不该变成静默降级。我的处理顺序是：先让警告可见（写日志、进上下文审计，前端的能力预览里也能看到每个块的估算），再由产品层决定是提示用户精简还是让运行时自己做压缩。我不会在计划阶段悄悄截断人格块——截断人格等于悄悄换了一个 Agent，这个后果比超限更难排查。真正的兜底在运行时：压缩开关始终打开，阈值由运行时按模型自己的预留策略决定，历史里那些"按百分比触发压缩"的旋钮在当前引擎下只是参考值，不会真的控制行为。这个区别我在文档里写清楚了，就是为了避免有人以为改个百分比就能改压缩时机。

**追问 3**：每轮还要拼记忆和渠道格式，这两块为什么单独拆出来？
**触发依据**：bullet 里"每轮再叠加负责人画像块、工作区记忆摘要块与当前渠道格式块"
**口播版**：因为它们的变化频率和静态块完全不同。静态块在一个会话里基本不变，是会话级的；记忆摘要和工作区状态每轮都可能变，渠道格式取决于这条消息从哪来。混在一起会导致两个坏结果：一是任何一轮的记忆变化都会让整份计划的哈希变掉，暖运行时的失效判断就没法用；二是审计里分不清"模型看到的这段是人格还是记忆"。拆开之后，会话级哈希只覆盖静态块，轮次级内容单独拼在提示末尾并且带自己的标记，顺序固定为画像、记忆、渠道格式、用户输入。顺序固定这件事也有实际意义——它让同一份配置在不同轮次之间的 diff 只出现在真正变化的部分。

### Q3 能力清单与工具面
- 对应支柱：B3
- 触发依据：bullet 里"按显式选择生成带哈希的有效清单，容器侧逐个只读挂载"和"精确选择缺失时直接让本次配置失败"
- 考查目标：能力注入的可验证性、失败策略取舍、工具副作用的边界设计
- 学习入口：[C04](guide-agent/C04-能力解析管线与精确挂载.md)、[C05](guide-agent/C05-工具面-mcp-工具与-ipc-回调.md)

**面试官问题**：一个 Agent 同时挂了技能、MCP 服务和插件，你怎么保证它实际拿到的就是你选的那几个？出现了预期外的能力怎么办？

**口播版**：靠三步把它变成可校验的产物。第一步是分层候选：内置、外部、项目、托管、工作区、用户、插件各自成一个来源层，同名能力按层优先级去重，这一层只负责"可能有哪些"。第二步是精确选择：用户在 Agent 策略里显式选了哪些，就只保留哪些，选择结果连同每个能力目录的内容哈希生成一份有效清单，清单本身也有哈希。第三步才是挂载：容器模式按清单逐个只读挂载，宿主模式把同一份清单同步到会话目录，两种模式用的是同一份清单，不存在"容器里是这批、宿主里是那批"。至于预期外的能力，我的策略是不允许它出现：选择指向的能力被禁用、删除、或者在镜像里根本不存在，这次配置就直接失败，不做静默替换。静默替换的诱惑很大——用户删了个技能，你悄悄给他换成同名的另一个版本，界面上一切正常。但 Agent 的行为会变，而且没人知道为什么变。宁可让保存失败，让用户看到"这个技能不可用"。

**追问 1**：能力清单变了之后，正在运行的会话怎么办？
**触发依据**：口播里"清单本身也有哈希"
**口播版**：不能让旧运行时继续用旧清单，也不能粗暴杀掉正在跑的一轮。做法是把变更当成一次事务：先暂停相关运行（暂停期间新消息标记为待处理，不再拉起新运行），再提交变更，提交成功就丢弃旧运行里挂起的输入并用新清单起新运行，提交失败就恢复队列让原运行继续。用户主动停止和变更引起的停止要区分开：前者丢弃被中断的输入，后者必须保留待重放输入，因为用户没打算放弃那句话。这些状态我都放在队列里显式表达，而不是靠"进程还在不在"来推断。

**追问 2**：那工具呢？你说有副作用的工具回到宿主执行，为什么不直接在运行时里发消息？
**触发依据**：口播里"挂载"之后自然引出的工具执行位置
**口播版**：因为运行体里没有做产品决策所需的信息，也没有权限。运行体知道的是模型想干什么，宿主知道的是这个租户有没有配额、这个会话该投递到哪个渠道的哪个话题、这条消息是不是重复的。所以内置工具分成两类：纯计算的（读文件、搜代码、算东西）直接在运行体里执行；有外部副作用的（给用户发消息、排一个定时任务、写长期记忆、请求人工确认）走增量通道回宿主，宿主执行完把结果写回来。为了不重复执行，每个请求带一个由运行时实例和轮次派生的幂等键，宿主侧按这个键去重。这里有个容易忽略的点：工具的返回值也要能被模型看懂，所以我把工具结果统一包装成文本或图片内容块，而不是让模型去猜一段 JSON 是什么意思。

**追问 3**：如果宿主在执行工具副作用的时候挂了，运行体在等结果，怎么收场？
**触发依据**：追问 2 里"宿主执行完把结果写回来"
**口播版**：运行体这一侧是有超时和取消的，工具执行收到中止信号会把失败返回给模型，模型下一轮会自己决定重试还是换个做法，这一轮不会永久挂住。宿主这一侧靠持久记录：副作用请求和它的结果都落库，进程重启后能看到"这个请求发出去了但没有结果"，这时候不重放副作用，而是把状态标成不确定并要求核对——尤其是发消息这类外部可见的操作，重放的代价是用户收到两条。这条规则在整个系统里是一致的：凡是外部可见的副作用，不确定态要显式表达，宁可让人看一眼，也不要自动重试两次。

### Q4 并发控制与运行时生命周期
- 对应支柱：B4
- 触发依据：bullet 里"并发边界由序列化键决定而不是会话归属"和"宿主模式刻意不加应用层并发池"
- 考查目标：并发建模能力、容量与计费的边界感、故障与停止路径的严谨度
- 学习入口：[C06](guide-agent/C06-会话串行队列与-runner-生命周期.md)

**面试官问题**：多个用户同时用同一个 Agent，你怎么控制并发？怎么保证一个卡住的会话不拖死别人？

**口播版**：先把"并发边界"定清楚：不是按群、不是按用户，而是按序列化键。同一个逻辑会话即使有好几个入口（Web 页面、私聊、某个话题），它们共享同一段上下文，就必须共享同一个运行时并且严格串行，否则两个进程同时推进同一份上下文，模型看到的历史会互相覆盖。不同会话之间没有共享上下文，就应该并行，所以我不设跨会话的应用层并发池——早期版本用过一个全局槽位数，结果是一个空闲但没超时的暖会话能把别人的消息卡住整整一个空闲超时周期，这个坑很典型。但并行不是免费的：容器模式下每个运行占一份真实资源，所以我保留两道闸——系统级容器并发上限和用户计费并发上限；宿主模式下进程由操作系统管，容量交给 OS，不加应用层计数。至于卡死，靠三层：单次运行的超时、空闲回收，以及对"运行体还在但长时间没有任何活动"的判定，判定成立后先要求优雅收尾（写关闭哨兵），收不掉再杀进程树，同时把这一轮收敛成可解释的失败。

**追问 1**：你说的"优雅收尾"具体怎么实现？为什么不直接杀？
**触发依据**：口播里"先要求优雅收尾（写关闭哨兵），收不掉再杀进程树"
**口播版**：直接杀会丢掉两样东西：正在流式输出的内容，以及运行体里那些还没确认的投递。所以先走软路径：往增量目录写一个关闭哨兵，运行体在循环里会检查它，命中就中止当前回合、把未确认消息写回、然后输出一个"已关闭"的终态退出。宿主看到这个终态就知道是正常关闭，不需要重试。只有软路径超时，或者进程已经不响应了，才杀进程树——而且杀之前要把这一轮标成"运行体退出"而不是"用户停止"，因为这两种情况对后续输入的处理完全不同：用户停止要丢弃被中断的输入，异常退出要重新从库里读消息。

**追问 2**：失败重试你说是有界指数退避，那如果一直失败呢？
**触发依据**：口播里"把这一轮收敛成可解释的失败"
**口播版**：退避有上限、重试次数也有上限，到顶之后这一轮不再自动重试，把错误交回给会话，让用户或上层看到明确的失败原因。中间有几个例外要单独处理：上下文溢出不退避，因为等一会儿并不会让上下文变小，直接重排并让运行时压缩；用户刚点过停止的会话短时间内不重排，否则运行体会把自己重新拉起来，表现为"点了停止又自己开始干活"；配置变更期间的失败也不退避，因为失败原因是正在换运行时，等变更完成再重放才是有意义的。还有一个容易被忽略的细节：新用户消息到来时会取消旧的退避计时器，但保留重试计数，不然每次新消息成功一次就把连续异常洗白了，永远触发不了上限。

**追问 3**：那你怎么知道某个运行是真的卡住了，而不是在跑一个很长的工具？
**触发依据**：追问 1 里"软路径超时"
**口播版**：用活动信号而不是用"开始时间"。运行体每次有实际进展（收到模型增量、工具开始或结束、写出一条输出）都会更新活动时间戳，判定卡死看的是"距上次活动过了多久"，而不是"这轮跑了多久"。另外先把候选挑出来，再重新校验一次才开始处理：因为在挑出候选到真正动手之间，运行可能刚好自己活过来了，这时候把它杀掉是纯粹的误伤。这个"候选 + 重校验"的模式在多实例或并发场景里很必要，单靠一次快照做决策迟早会出错。

### Q5 IM 渠道的流式与可靠性
- 对应支柱：B5
- 触发依据：bullet 里"网络超时导致的可能已发出单列为不确定态并要求核对"和"流式事件类型只有一个真相源"
- 考查目标：分布式投递语义、状态机设计、跨端契约的维护方式
- 学习入口：[C07](guide-agent/C07-流式事件契约与三段同步.md)、[C08](guide-agent/C08-渠道可靠投递状态机.md)

**面试官问题**：IM 里让 Agent 回一句话，听起来就是调个接口，你觉得它难在哪？

**口播版**：难在"这句话到底发出去没有"这个问题没有廉价答案。IM 接口的超时语义很讨厌：超时可能意味着没发出去，也可能意味着发出去了但响应没回来。如果超时后重发，用户就会看到两条一样的回复；如果不重发，用户可能永远收不到。所以我把投递做成了持久状态机：入站先落库再带租约领取，领取要续约，防止两个消费者同时处理同一条消息；一轮对话是一条独立记录，有心跳、有终态、有超时中断；出站消息按类型分类，发送分上传和发送两个阶段，每个阶段结束才推进状态；到了超时这种"可能已经成功"的边界，状态不是失败也不是成功，而是单列的不确定态，要求核对而不是自动重发。另一头是流式呈现：IM 的流式不是推流，是反复编辑同一条消息或一张卡片，所以还要处理编辑节流、卡片创建与终态、以及进程崩溃后重新接管一张还在"进行中"的卡片。

**追问 1**：既然有不确定态，那谁来核对？总不能让人天天看吧？
**触发依据**：口播里"要求核对而不是自动重发"
**口播版**：核对是分层的。绝大多数情况能在系统内闭合：发送前记录载荷哈希和消息锚点，超时后先查会话里有没有对应的已发送记录，能查到就判定成功并收敛，查不到才进不确定态。剩下真正需要人的，是那些查不到也重发不了的——通常是平台接口既不支持幂等也不支持查询的场景。这类我按人工对账处理，错误信息带固定前缀，上层能据此把它和普通失败区分开，UI 上也能一眼看出"这条需要人工确认"。这个设计的取舍是明确的：把极少数不确定场景暴露出来，而不是用自动重试把它们变成"偶尔用户收到两条，偶尔丢一条"。

**追问 2**：你提到流式事件只有一个真相源，具体怎么落地？
**触发依据**：口播里"流式事件类型只有一个真相源"
**口播版**：真相源是一份类型定义文件，定义事件类型全集、作用域枚举、展示层级和公共字段。构建时把它复制到三个消费方：宿主的落库与广播、运行体的输出、前端的状态管理。三份是生成物，不允许手改，改副本会在类型检查里被复制一致性校验拦下来。这么做的原因很实际：流式事件是三方唯一共享的数据结构，一旦三份各自演化，症状是"某个事件在 Web 上能显示、在 IM 卡片里丢失"，而且很难定位是谁的问题。带上展示层级之后，宿主不需要知道某个事件该不该给用户看，它只负责转发，前端按层级决定放主文本还是细节面板。这样新增一种事件只要改真相源和两处消费逻辑，不需要动投递链路。

**追问 3**：如果一条轮次运行到一半，运行体和宿主之间的连接断了呢？
**触发依据**：追问 1 里"一轮对话是一条独立记录，有心跳"
**口播版**：靠心跳和过期中断收场。轮次记录定期续心跳，超过阈值没续上就被判定为失联，由恢复逻辑把它收敛成中断终态，并释放它占着的租约，让后续消息可以继续。这里有个顺序要求：先确定这一轮不会再产出新的出站消息，再把轮次标终态，否则会出现"轮次已失败但出站队列还在往里塞"。同样地，重新接管一张进行中的流式卡片时，要先读卡片记录的当前状态，再决定是续写还是收尾，而不是直接新建一张——新建的后果是用户看到两张卡片。

### Q6 记忆方案与定时任务的语义
- 对应支柱：B6
- 触发依据：bullet 里"用结构化知识表加全文索引承载"和"错过的周期任务标记为错过并推进下一次计划"
- 考查目标：检索方案取舍的判断力、写入治理意识、调度语义的严谨度
- 学习入口：[C09](guide-agent/C09-定时任务调度与重启恢复.md)、[C10](guide-agent/C10-长期记忆-fts5-检索与写入治理.md)

**面试官问题**：Agent 的长期记忆，你为什么用全文索引而不是向量检索？服务重启时定时任务怎么保证语义是对的？

**口播版**：两件事分开说。记忆这块，我要的不是"语义最相近"，而是"能被引用、能被修改、能被追责"。所以底层是结构化知识表：每条记忆有类型（事实、决策、教训、待办）、状态、版本、来源和更新时间，检索用全文索引按加权列排序并返回命中片段。向量检索的优势是语义召回，代价是召回结果不可解释、更新后难以确认哪些旧向量失效、跨租户隔离要额外索引结构。我们的场景里，Agent 需要的是"上次这个客户说不接受分期"这种确定事实，不是"意思相近的段落"，所以我选了可审计的那条路，代价是近义召回弱，用类型过滤和列权重来补。调度这块，重启语义必须显式：周期任务错过一次，我不会把错过的全部补跑，因为补跑十个闹钟通知没有意义，而是记一条"错过"并推进到下一个计划点；一次性任务不一样，它代表用户明确要在这个时间点做这件事，所以重启后仍然补跑。这套规则写在调度器里，不是靠部署时不重启来回避。

**追问 1**：记忆写入你说要签名鉴权，为什么？运行体不就在你的进程里吗？
**触发依据**：口播里"每条记忆有类型、状态、版本、来源"
**口播版**：运行体是隔离环境里的进程，它拿到的是任务输入，不是数据库权限。如果让它直连库写记忆，等于把租户边界交给提示词去守——模型被诱导一下就能写别人的记忆。所以写入走请求：宿主给这一轮下发一个实例标识和签名密钥，运行体提交变更请求时带上签名和幂等键，宿主校验签名、校验租户归属，再按版本做乐观并发控制。版本这块不能省：两个会话同时改同一条记忆，后写的如果直接覆盖，前一个 Agent 刚确认的事实就悄悄没了。所以更新要带期望版本，冲突就失败重试。删除也不是真删，是状态置为失效并留墓碑，这样召回不再命中，但审计还能回答"这条记忆什么时候被谁作废的"。

**追问 2**：定时任务的执行和普通对话共用一套队列，会不会互相影响？
**触发依据**：口播里"任务与其他运行共用同一套执行超时与队列语义"
**口播版**：会共享容量，这是有意的。任务运行本质上也是一次 Agent 运行，占同样的资源和同样的模型配额，如果给它单独一个并发池，等于绕开了系统的容量核算，真实成本会被低估。所以任务和对话走同一套超时、同一套容量闸门、同一套队列语义，区别只在输出契约：任务运行用的是"无人等待"的输出格式，它不知道有谁在看，所以要求它在结束时给出结论性内容，而不是反问用户。任务运行有独立的记录和日志表，因为排查方式不同——对话出问题看消息历史，任务出问题要看第几次触发、有没有跑完、失败在哪一步。

**追问 3**：那如果任务一直在失败，怎么避免它无限重试烧钱？
**触发依据**：追问 2 里的"任务运行本质上也是一次 Agent 运行"
**口播版**：靠有界重试加定义指纹。重试次数有上限，到顶之后这一次触发收敛为失败并留记录，下一次按计划正常触发，不会因为上一次失败就改变计划。定义指纹用来区分"同一任务重试"和"任务被改过之后的新版本"——用户改了提示词或者改了计划，旧版本失败的计数不应该继续算在新版本头上，否则用户一改配置就继承了之前所有的失败额度。另外任务运行同样受租户配额约束，配额耗尽时任务不执行并记录原因，而不是排队等一个可能永远不来的额度。

### Q7 多租户权限边界
- 对应支柱：B7
- 触发依据：bullet 里"没有管理员全局旁路，越权访问统一返回资源不存在"
- 考查目标：权限模型设计、越权面识别、配置变更与运行态的一致性
- 学习入口：[C11](guide-agent/C11-多租户隔离与-agent-profile-治理.md)

**面试官问题**：多租户系统里，管理员该不该有全局权限？你们是怎么划的？

**口播版**：分两层看。平台运维层需要全局能力：系统配置、用户与邀请、审计、计费，这些有独立的管理权限，因为它们的语义就是跨租户的。但工作区和渠道资源这一层，我不给管理员全局旁路。原因不是洁癖，是这类资源的权限一旦有旁路，就会出现"管理员能看别人 Agent 的对话历史"这种状态，而这恰恰是自托管产品最敏感的东西——用户把 Agent 放在自己服务器上，图的就是数据边界清楚。所以判断函数只看创建者和显式授权，越权访问统一返回资源不存在而不是 403：404 不泄漏"这个资源存在但不属于你"，能减少一个枚举面。执行模式也要看，宿主模式的工作区额外要求管理员身份，因为它直接跑在有权限的机器上，风险和容器模式不是一回事。

**追问 1**：那敏感配置变更时，正在跑的会话怎么办？配置文件改了但进程还在用旧的，这不就是不一致？
**触发依据**：口播里"工作区和渠道资源这一层不给管理员全局旁路"
**口播版**：所以我把变更纳入事务语义：先暂停相关运行，暂停期间新消息待处理、不拉起新运行；然后提交变更；提交成功就丢弃旧运行挂起的输入、按新配置起新运行；提交失败就把队列恢复回去，让原运行继续。这样外部看到的要么是旧配置的完整行为，要么是新配置的完整行为，不会出现"半个进程用新配置、半个用旧配置"。同样的规则也用在能力变更和 Agent 人格变更上，因为它们都属于"运行态必须和配置一致"的范畴。实现上这些暂停令牌是显式的、可回滚的，不是靠"反正重启一下就好了"。

**追问 2**：你说 Web 是控制面，但它会不会影响会话的渠道身份？
**触发依据**：追问 1 里"运行态必须和配置一致"
**口播版**：不会，这是刻意划的边界。一个逻辑会话第一次被哪个原生渠道占有，会一次性记下来，之后即使从 Web 继续对话，投递目标还是那个原生渠道的话题或私聊。理由很实际：用户是在飞书群里问的问题，你在 Web 上补一句，回复应该回到那个群里，而不是出现在一个只有你自己看得到的页面。反过来，如果 Web 能随意改这个归属，就会出现"Agent 在群里消失了"这种事故。所以 Web 是编排和查看的入口，不是重写会话归属的入口；文件与图片投递也必须用当前轮次携带的渠道上下文，不能从"最近一条群消息"去猜目标。

**追问 3**：这套权限模型你怎么验证它没漏？
**触发依据**：口播里"越权访问统一返回资源不存在"
**口播版**：靠契约测试固定行为，而不是靠人工点。每个资源族都有对应用例：以创建者身份访问、以同租户其他人身份访问、以管理员身份访问、以不存在 ID 访问，四种身份对四类预期（成功、404、404、404），任何一种行为变化都会让用例失败。之所以把管理员也写成用例，是因为"顺手加个旁路"最容易发生在修 bug 的时候，测试是唯一的刹车。另外 ACL 矩阵有一份文档化的对照表，新增路由时要求同步更新——不是为了文档好看，而是为了让"这个接口属于哪一层权限"变成必须回答的问题，而不是默认继承上一层的中间件。

### Q8 产品定位与差异化
- 对应支柱：简介
- 触发依据：项目简介里"自托管多租户 Agent 工作台"与"七个渠道以流式方式交付结果"
- 考查目标：是否理解自己做的东西的定位，能否与常见 Agent 框架/编排工具区分开
- 学习入口：[C01](guide-agent/C01-runner-进程协议与-ipc-通道.md)、[C03](guide-agent/C03-上下文工程-prompt-分层与预算.md)

**面试官问题**：市面上 Agent 框架和编排工具很多，你这个项目的定位差别在哪？

**口播版**：多数框架解决的是"怎么把一个任务编排出来"，我这个项目解决的是"怎么让一个 Agent 长期待在一个组织里干活"。差别体现在四件很工程的事上：一是身份与人格是一等公民，Agent Profile 有四段提示、有版本、有能力策略，"换一个 Agent"是改配置不是改代码；二是执行有工位，容器或宿主进程按工作区隔离文件与能力，重启、超时、卡死都有明确处置；三是入口是组织现有的沟通工具，七个 IM 渠道加 Web 共享同一份流式契约和同一套投递可靠性语义，而不是各写一套；四是长期状态齐全，定时任务、长期记忆、用量计费都在，这些恰恰是"数字员工"和"演示 demo"的分界线。反过来说，它不擅长的是把一个复杂任务拆成任意 DAG 去跑——那是编排引擎的活，我这里的工作流是声明在提示词里的规则，不是可执行引擎。
